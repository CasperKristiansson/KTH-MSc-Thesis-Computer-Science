Master's Thesis Summary

From Experiment to Insight

Benchmarking HDF5/HSDS, Zarr, TileDB, and ROOT/TTree for large-scale synchrotron and neutron-scattering data on AWS

Author: Casper Ove Kristiansson
Affiliation: KTH EECS
Host: Scatterin AB
Supervisors: Sebastian Dalleiger (KTH), Ahmet Bahadir Yildiz (Scatterin AB)

Motivation: beamlines meet object storage

  • Modern beamlines stream multi‑GiB/s, turning single experiments into multi‑TB datasets.
  • Parallel file systems deliver throughput, but thousands of small reads suffer.
  • S3 scales, yet per‑request latency and request cost become visible.
  • Need a side‑by‑side, cloud‑native evaluation for slice latency vs full-scan throughput.
Goal: Identify storage + codec choices that reduce interactive latency while sustaining scan throughput.
Beamline pipelines generate high‑volume, latency‑sensitive data flows.

Research questions & scope

RQ1: For random single‑frame reads on S3, which backend + codec minimize GM latency and control p95?
RQ2: For full‑dataset scans, which backend + codec maximize GM throughput with stable p95?
RQ3: How do layout + codec choices change GETs/GiB and stored size, and explain timings?
Scope & delimitations
  • AWS only (S3 + EC2).
  • One dense detector stack (~20 GiB, ~1300 frames).
  • Codecs: gzip, lz4, zstd.
  • Workloads: single‑frame slices + full scans.
  • Results are descriptive, session‑conditional.

Dataset

Workloads

Frame‑aligned chunks preserve slice‑level comparability.

Formats, codecs, layout parity

  • HDF5 via HSDS: chunk‑per‑frame objects + metadata fan‑out.
  • Zarr v3: chunk‑per‑frame objects, direct S3 access.
  • TileDB: frame‑sized tiles, fragment‑based layout.
  • ROOT/TTree: single object per codec (range‑GET paging).
  • Parquet pilot only: metadata open 3–4 min, single ~34 GiB file → excluded from timed runs.
  • Codecs: gzip, lz4, zstd (same logical chunk size).
Objectization differs by layout (log scale).

Decision matrix (practitioner choices)

Latency‑first (interactive slices)
  • Default: Zarr + zstd
  • If gzip required: TileDB + gzip
  • Avoid: ROOT for frame‑random reads
  • Caution: HSDS + lz4 (storage‑heavy)
Throughput‑first (full scans)
  • Default: TileDB + zstd
  • Option: TileDB + lz4 if CPU‑bound
  • Second choice: Zarr for ecosystem fit

All rankings are descriptive and session‑conditional for this dataset and testbed.

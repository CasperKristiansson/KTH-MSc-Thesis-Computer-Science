\begin{scontents}[store-env=abstracts,print-env=true]
Modern synchrotron and neutron beamlines can stream at gigabytes per second, turning single experiments into multi-terabyte datasets and exposing latency limits of parallel file systems. This thesis benchmarks cloud-native storage layouts on AWS S3 using a single $\sim$20\,GiB, $\sim$1{,}300-frame detector stack, focusing on slice-level latency, scan throughput, and cost drivers. Four backends (HDF5 via HSDS, Zarr v3, TileDB, ROOT/TTree) and three codecs (gzip, LZ4, zstd) are evaluated under two workloads: random single-frame reads and full sequential scans. Client timings are analyzed on a log scale with dependence-robust confidence intervals, with S3 request counts and stored size providing context.

Results are descriptive and session-conditional for this dataset and AWS setup. For interactive slices, Zarr is fastest with zstd (GM $\approx$155 ms) and with LZ4; TileDB is fastest with gzip. For full scans, TileDB delivers 2.2–3.2$\times$ higher throughput than Zarr across codecs (e.g., zstd $\approx$1.06 GiB/s for 20 GiB). ROOT is slow for frame-random reads despite a few GETs, indicating single-object paging and decode overheads. HDF5/HSDS trails on slice latency and scan throughput with LZ4, storing 19.17 GiB versus Zarr 10.40 GiB for the same payload.

The contribution is a reproducible AWS-native benchmarking method and a decision matrix for the tested workloads: choose Zarr+zstd when slice latency dominates and choose TileDB+zstd/LZ4 when throughput dominates.

\chapter{Introduction}
\label{ch:introduction}
Modern synchrotron and neutron experiments generate multi-GiB/s streams of multidimensional detector data. Parallel file systems (Lustre, \gls{GPFS}) deliver high throughput for large, contiguous I/O but often respond poorly to the thousands of small, partial reads required for on-beamline feedback. Cloud object stores such as Amazon \gls{SThree} provide elastic capacity and global access but add per-request latency and fees. Monolithic file-container formats (e.g., \gls{HDFfive}/NeXus) map poorly to object stores without additional translation layers.

Cloud-native layouts—chunked arrays (Zarr), fragmented dense/sparse arrays (TileDB), and tree/column layouts (\gls{ROOT}/\gls{TTree})—offer alternative trade-offs in latency, throughput, compression, CPU, and request intensity. This thesis provides a side-by-side evaluation of four cloud storage backends on \gls{AWS} under two canonical scattering access patterns: random single-frame reads (interactive slices) and full sequential scans (bulk post-processing).

In this benchmark, the choice of layout and codec changes interactive single-frame latency by a factor of $\approx 2.6\times$ across the tested configurations (GM $\approx$155\,ms for Zarr+\texttt{zstd} versus GM $\approx$406\,ms for ROOT+\texttt{gzip}). For bulk processing, TileDB reduces full-scan GM time by $\approx 2.2$--$3.2\times$ relative to Zarr across codecs (e.g., GM $\approx$10.4\,s vs.\ $\approx$30.4\,s under \texttt{zstd}). Cost-relevant proxies also vary materially: request intensity differs by up to $\approx 3$--$4\times$ (GETs/GiB) between layouts for the same workload, and stored size can differ by $\approx 1.8\times$ for the same logical dataset under \texttt{lz4} (e.g., HSDS vs.\ Zarr). These effect sizes illustrate the range observed in this benchmark for how engineering choices in storage layout and compression can change beamline feedback latency, end-to-end pipeline time, and object-store cost posture in an \gls{SThree}-based workflow.


\section{Motivation and Context}
As synchrotron and neutron facilities have evolved, detector technologies and beamline instrumentation have driven data generation rates from megabytes to multiple gigabytes per second. Modern experiments frequently combine multiple detectors and scan axes, such as energy, angle, or polarization. This results in multidimensional datasets that can reach terabyte-scale within minutes, making `download-then-analyze` workflows impractical during beam time \cite{celcer2018gigafrost}.

\subsection{Limitations of Traditional HPC Storage}
Historically, researchers stored beamline data on parallel file systems such as Lustre or \gls{GPFS} and accessed it through \gls{MPIIO} or batch-oriented workflows. These systems perform well for large-block I/O but incur high overhead on thousands of small random reads typical of exploratory slices or metadata queries \cite{narayan2010characterization}. Maintaining on-premises \gls{HPC} arrays entails capital and operational expenditures, as well as additional network complexity.

\subsection{Emergence of Cloud-Native Storage Models}
Cloud object storage, most notably Amazon \gls{SThree}, is now widely used for scientific data. Object stores provide virtually unlimited, durable storage, global namespace access, and a pay‐as‐you‐go billing model that shifts capital costs to operational expenses. However, when monolithic scientific formats such as \gls{HDFfive} or NeXus, originally designed for \gls{POSIX} filesystems that rely on byte-addressable seek semantics, are naively stored on \gls{SThree}, every small slice can trigger hundreds or thousands of \gls{HTTP} Range-GET requests (i.e., \gls{SThree}’s emulation of those seeks). For \gls{SThree}, namespace access results in additional LIST/HEAD calls, which are billed per request.

Researchers have introduced a new generation of cloud-native data models to address these shortcomings. Zarr and related chunked layouts expose each array chunk as an independent object, enabling parallel GET/PUT with a configurable chunk size. Organizations tune chunking to balance object count and transfer efficiency \cite{moore2023ome}. Columnar storage formats such as Apache Parquet organize data in row groups and column stripes, pruning unneeded fields to reduce I/O usage \cite{ivanov2020impact}. TileDB provides dense and sparse array storage with tiled chunking and object-store backends, enabling parallel range reads/writes and reducing metadata and small-read overheads. In parallel, the high-energy physics community has extended \gls{ROOT}’s \gls{TTree} abstractions to object-store backends, preserving branch-level selective reads \cite{abs-2107-07304}.

Each approach offers distinct trade‐offs in latency, throughput, compression efficiency, \gls{CPU} overhead, and cost. Although individual formats have been benchmarked in isolation or within specific domains, to the best of the author’s knowledge, there is no comprehensive, side-by-side evaluation of these backends for scattering-style access patterns on \gls{AWS} \gls{SThree} under a controlled, end-to-end benchmark. Addressing this gap informs both beamline scientists seeking responsive, cost‐effective data access and data‐intensive computing engineers designing next‐generation, cloud‐native scientific platforms.

\subsection{Research Question}
\emph{How do four cloud storage backends—\gls{HDFfive}/\gls{HSDS}, Zarr v3, TileDB, and \gls{ROOT}/\gls{TTree}—compare on \gls{AWS} \gls{SThree} for two scattering access patterns: (1) random single-frame reads for interactive slicing and (2) full sequential scans for bulk processing, under common compression codecs (\texttt{gzip}, \texttt{lz4}, \texttt{zstd})?}

\section{Problem, Purpose, and Goals}
This section defines the problem, states the purpose, and lists the goals. It sets the basis for the comparisons used later in the thesis.

\subsection{Problem}
\label{sec:problem}
Handling multi-terabyte scattering datasets on \gls{AWS} \gls{SThree} reveals several limitations in current data platforms. First, partial reads of beamline slices, such as retrieving a single detector channel or angular data segment, can result in high latency due to the need to perform hundreds, if not thousands, of GET operations and metadata lookups, leading to delayed experimental feedback. Secondly, existing prior prototype evaluations have focused on moderate‐scale workloads. This thesis benchmarks each format on a single \SI{20}{\gibi\byte} detector dataset (\(\sim\)1{,}300 frames) to uncover performance, request behavior, and data ingestion considerations. Thirdly, the interaction between storage formats and compression algorithms (e.g., \texttt{zstd}, \texttt{lz4}, \texttt{gzip}) has not been systematically evaluated, making it unclear which format codec combinations best optimize latency and throughput for \gls{SThree}-based workflows. These industrial challenges raise questions for the data-intensive computing community: How can we systematically leverage and compare different storage backends to generate guidance for scientific users? Which combinations of performance and integration trade-offs matter most when designing cloud-native workflows for interactive, partial-retrieval use cases?

\subsection{Original problem and definition}
This thesis defines the original industrial problem as optimizing the retrieval of small, targeted data slices (e.g., a single angle’s worth of diffraction frames) from multi-terabyte scattering datasets stored on \gls{AWS} \gls{SThree}. “Partial retrieval” denotes reading the required byte ranges or object keys rather than entire files. The study targets cloud-native, object-store workflows.

\subsection{Scientific and engineering issues}
Generalizing beyond the narrow industrial case leads to two broader research issues. For the two dominant access patterns in scattering pipelines, namely interactive single-frame reads and full sequential scans, the thesis asks how storage layouts and codecs trade latency, throughput, request intensity, and stored size on \gls{SThree}. It also asks how different compression algorithms (\texttt{zstd}, \texttt{lz4}, \texttt{gzip}) interact with object-stored data and how those interactions shape end-to-end latency and throughput. These questions are directly relevant to ongoing research in \gls{HPC} and data-intensive computing, where cloud adoption continues to challenge traditional storage paradigms.

\subsection{Purpose}
Scientifically, the study quantifies trade-offs among latency, throughput, compression ratio, and request intensity for a realistic scattering workload on \gls{SThree}, using design-science methodology \cite{hevner2004design}. Outputs include a decision matrix and best-practice guidance.

Secondly, it aims to provide Scatterin AB with a practical, evidence-based framework to optimize its cloud-based data platform for high-throughput synchrotron and neutron-scattering experiments. This work offers concrete guidance on minimizing latency for partial-read use cases, maximizing throughput, and controlling pay-as-you-go costs across varying access patterns.

\subsection{Goals}
This thesis develops an experimentally validated decision framework to guide the selection and configuration of cloud-native storage solutions for scattering datasets on \gls{AWS} \gls{SThree}, evaluated on a single \SI{20}{\gibi\byte} detector stack. Concretely, the work has three operational goals. First, it builds comparable prototypes by ingesting a single \SI{20}{\gibi\byte} dense 3D detector stack (\(\sim\)1{,}300 frames) into four timed backends: \gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{TTree}, while applying consistent chunking and compression (\texttt{zstd}, \texttt{lz4}, \texttt{gzip}) to preserve fairness across formats. Second, it benchmarks two read patterns, full scans and random single-frame reads, while recording stored size, requests per GiB, and client timings, and reporting geometric-mean latency or throughput together with 95th percentiles. Third, it synthesizes the empirical results into a decision matrix that relates workload patterns, compression choices, and integration concerns to format-specific behavior, and then turns that synthesis into ranked best-practice recommendations.

\subsection{Research Questions (RQs)}
To structure the investigation, the thesis poses three research questions. \textbf{RQ1} concerns interactive latency: for random single-frame reads on \gls{SThree}, which backend and codec minimize geometric-mean latency and control $p_{95}$? \textbf{RQ2} concerns bulk throughput: for full-dataset scans, which backend and codec maximize geometric-mean throughput with stable $p_{95}$? \textbf{RQ3} addresses cost posture and mechanisms: how do layout and codec choices change GETs/GiB and stored size, and how do these factors explain client timings?

\section{Methodology and Scope}
This section outlines the benchmarking methodology and the study scope. It specifies datasets, workloads, metrics, and the delimitations for reproducibility.

\subsection{Research Methodology}
We use an \emph{experimental benchmarking} approach within a design–science framework to evaluate four timed storage backends on \gls{AWS} (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{TTree}). Apache Parquet is included only as a single-object pilot (ingest only, no timed runs; Appendix \ref{app:a8-parquet}). The benchmark dataset is a single dense detector stack of approximately \SI{20}{\gibi\byte} (\(\sim\)1{,}300 frames). Two workloads are evaluated: random single-frame reads and full scans. We report geometric-mean latency or throughput with dependence-robust 95\% confidence intervals and $p_{95}$ latency/throughput. Detailed descriptions of infrastructure, randomization, logging, and estimator choices are provided in Chapter \ref{ch:methods} and the Appendix.

\subsection{Delimitations}
This thesis focuses exclusively on cloud-native, object-store–based workflows within the \gls{AWS} ecosystem. Only \gls{AWS} services (\gls{SThree}, \gls{ECtwo}) are considered, so the study does not include Azure, Google Cloud, or on-premises \gls{HPC} clusters. Quantitative results cover four timed formats (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{TTree}), while Apache Parquet appears only as a single-object, ingest-only pilot and is excluded from timed comparisons (Appendix \ref{app:a8-parquet}). The benchmarks use one dense 3D detector dataset of roughly \SI{20}{\gibi\byte} (\(\sim\)1{,}300 frames), and the quantitative evaluation is limited to the two access patterns that dominate user experience and transferred volume in this setting: random single-frame reads (\(\sim\)\SI{15.82}{\mebi\byte} per frame) and full sequential scans. Other patterns, such as metadata-only queries, random single-element lookups, real-time streaming ingestion, and multi-client contention, are treated qualitatively or left to future work. Likewise, the codec comparison is limited to three widely used alternatives, \texttt{zstd}, \gls{LZfour}, and \texttt{gzip}, rather than extending to Snappy, Brotli, bzip2, or ZFP. These delimitations ensure a focused, reproducible comparison of core performance and cost trade-offs for scattering-style object-store access on \gls{AWS}.

\section{Structure of the Thesis}
This thesis is organized into seven main chapters, followed by appendices.

Chapter 1 introduces the motivation, scope, research questions, methodology overview, delimitations, and overall structure. Chapter 2 provides the background by reviewing scientific-data challenges in synchrotron and neutron facilities, traditional \gls{HPC} I/O, and emerging cloud-native formats such as \gls{HDFfive}/\gls{HSDS}, Zarr, Parquet, TileDB, and \gls{ROOT}/\gls{TTree}. Chapter 3 explains the research methodology, including dataset selection, \gls{AWS} infrastructure, ingestion pipelines, access patterns, performance metrics, and statistical procedures, while Chapter 4 describes the implementations used for each backend together with chunking, compression, and workflow automation. Chapter 5 presents the quantitative results and their analysis, and Chapter 6 synthesizes those findings into a decision matrix and discussion of trade-offs, integration complexity, and operational implications. Chapter 7 concludes the thesis by summarizing the main contributions, reflecting on limitations, and outlining future work. The appendices provide detailed benchmark logs, code snippets, and supplementary figures.

Modern synchrotron and neutron facilities stream multi-GiB/s data, producing multi-terabyte experiments that strain large-block assumptions in traditional \gls{HPC} storage. \section{Scientific Context and Workflows}
\label{sec:scientific-context-workflows}
Modern beamlines generate multi–GiB/s data streams and require selective, near-real-time inspection during beamtime.

\subsection{Scientific-Data Context}
\label{sec:scientific-data-context}
Synchrotron light sources and spallation or continuous-beam neutron facilities produce multi-megapixel frames at kilohertz rates, pushing raw data beyond \SI{10}{\giga\byte\per\second} \cite{eriksson2014diffraction}. High-speed area detectors, hybrid photon counters, and \gls{CMOS} cameras convert pulses into image sequences that accumulate to multi-\si{\tera\byte} per day.

Giant accelerator-based light and neutron sources act as kilometer-scale microscopes that let us “see through’’ centimeters of steel, polymers, or living tissue at kilohertz frame rates. By storing ultra-low-emittance electrons (or moderating proton-driven neutrons), the machines deliver beams that are \(\sim10^{10}\!-\!10^{12}\) times brighter than laboratory instruments, unlocking 3-D imaging and diffraction of virtually any material \cite{eriksson2014diffraction}. Each pulse is immediately converted into multi-megapixel images by high-speed area detectors, hybrid photon counters, \gls{CMOS} cameras, or time-pix neutron imagers. Capturing these data allows a single experiment to exceed \SI{10}{\giga\byte\per\second} of raw data.

These facilities have a direct impact on the industry. At the European Synchrotron Radiation Facility, X-ray tomography has revealed how expanded-polypropylene crash foams used in car bumpers collapse under load, informing design rules for next-generation impact absorbers \cite{carnegie2024uninterrupted}. Neutron radiography visualizes sub-second water build-up that strangles polymer-electrolyte fuel cells during winter cold starts, guiding stack architecture and heating strategies for fuel-cell vehicles \cite{yoshimune2024neutron}.

\subsubsection{Typical beamline architecture}
A beamline shapes the beam with mirrors, slits, and monochromators, then positions the specimen on a multi-axis stage. A high-speed detector records 2-D or 3-D data at up to thousands of frames per second. A \gls{DAQ} server buffers frames on local \gls{NVMe} \gls{SSD}s or a burst buffer and writes to storage. Historically, the stream targets a parallel file system (Lustre/\gls{GPFS}), but in recent years object-store workflows have been introduced as an alternative (Figure \ref{fig:beamline-journey}).

Modern beamlines already saturate local networks with sustained data streams of $\mathcal{O}(10^{2})$\,\si{\mega\byte\per\second} per instrument. Looking ahead, diffraction-limited storage rings are projected to drive detector outputs beyond \SI{10}{\giga\byte\per\second} and data volumes of $>\!\SI{10}{\tera\byte}$ per experiment, implying corresponding upgrades to storage and analysis pipelines \cite{eriksson2014diffraction}.

\subsubsection{Dimensionality of datasets}
Indexing a single 2-D detector frame by additional experimental coordinates turns it into a higher-dimensional data object. Each 2-D image becomes a slice in a stacked data cube, while the depth axis stores a third coordinate, such as a rotation angle, energy, or time (Figure \ref{fig:data-cube}). Because modern beamlines vary at least three independent axes, the raw $(x,y)$ detector image is naturally represented as a 4-D (or higher) array:

\begin{itemize}
  \item \textbf{Rotation or scan angle:} a full tomographic or serial-crystallography scan may step the sample (or detector) through $10^{2}$–$10^{4}$ projections to reconstruct 3-D real-space structure or space intensity maps (\emph{rotation} $\times$ \emph{energy} $\times$ \emph{time}) \cite{app11198868}.
  \item \textbf{Energy or wavelength:} in spectro-microscopy and \gls{EXAFS}, the microscope sweeps energy across an absorption edge. At the same time, a fast detector records images, producing hyperspectral cubes with \(\sim\)10–\(10^{2}\) energy points per angle or time step \cite{Briois:uc5005}.
\end{itemize}

When these axes are combined, experiments can generate 5-D or 6-D datasets. For example, a $2048\times2048$ detector recording 1800 rotation angles, 50 energy points, and 20-time delays already contains $\sim150\times10^{9}$ pixels ($\approx$\,\SI{300}{\giga\byte} at 16-bit depth). These arrays enable multivariate analyses but impose heavy storage and I/O demands. Some beamlines further append polarization, external field strength, or environmental parameters (temperature, pressure, electrochemical potential), further increasing data dimensionality and storage complexity.

\subsubsection{Real-world automotive example}
The automotive industry uses neutron radiography to visualize water and ice formation within polymer-electrolyte fuel-cell stacks during rapid cold starts. The study used an operational neutron imaging system to map liquid distribution in a Toyota single cell down to sub-second time scales, informing design tweaks that mitigate performance losses \cite{yoshimune2024neutron}.

\subsection{Experimental Workflows \& Feedback Loops}
\label{sec:experimental-workflows-feedback-loops}
Beam time at synchrotron and neutron facilities is scarce and expensive. Experiments must, therefore, include a \emph{closed data loop} in which raw detector frames are reconstructed, inspected, and, if necessary, used to steer the scan while the sample is still in the beam. A study showed that streaming projections from the beamline to an \gls{HPC} cluster could deliver slice reconstructions within seconds, enabling autonomous adjustment of exposure, angle range, or focus during tomography scans \cite{Bicer2017RealTime}.

At Shanghai Synchrotron Radiation Facility, automated pipelines tied into the metadata catalog provide progress notifications and interactive dashboards for real-time feedback \cite{wang2024accelerating}.

These workflow requirements translate directly into storage-system requirements:

\begin{itemize}
  \item \textbf{Latency}: scientists often request slices of data (quick-look radiographs or azimuthal-integrated diffraction rings). Data retrieval times must stay in the sub-second regime to keep up with the experiments.
  \item \textbf{Throughput}: full 3-D reconstruction or machine-learning inference may pull hundreds of contiguous gigabytes at the end of a scan, often requiring burst bandwidths of $\ge\!\SI{10}{\giga\byte\per\second}$.
  \item \textbf{Scalability \& concurrency}: remote teams viewing the same dataset and automated QC pipelines often need simultaneous small-read streams. Monolithic single-file layouts trigger many Range-GETs per slice and cannot exploit per-chunk concurrency.
  \item \textbf{Online analysis}: real-time processing pipelines (e.g., streaming reconstruction, AI-driven feature extraction) consume data as it arrives. Storage must support continuous, low-overhead partial reads and write-through metadata indexing to feed live analytics without waiting for scan completion.
\end{itemize}

These workflow pressures motivate the performance metrics and storage formats evaluated in this thesis.

\subsubsection{Small-slice interactive reads}
At many beamlines, an \emph{interactive slice} is a reconstructed tomographic plane or detector region of interest. For example, the GigaFRoST camera at \gls{SLS}--\gls{TOMCAT} streams \(2016\times1800\) px, 16-bit projections at \SI{7.7}{\giga\byte\per\second}, so a single projection (or a stack of a few tiled ROIs) naturally falls in this size window \cite{celcer2018gigafrost}. Likewise, the APS nanoprobe workflow achieves live neural-network inference on \(512\times512\) diffraction frames at \(100\,\mathrm{Hz}\) (one frame every \(\SI{10}{\milli\second}\)), establishing a practical millisecond-to-sub-second latency budget for feedback loops \cite{babu2023deep}.

Partial reads are equally critical \emph{after} acquisition. For example, strain- and stress-mapping routines integrate Bragg peaks only within narrow azimuthal sectors (\(\Delta\chi\approx5^{\circ}\)) or select a handful of detector tiles, discarding the rest of the frame. High-energy diffraction microscopy at APS, for instance, reconstructs grain-resolved strain tensors by repeatedly loading just those angular wedges that intersect a given grain’s Debye–Scherrer rings, cutting I/O by an order of magnitude \cite{lienert2011high}.

\subsubsection{Full-dataset sequential scans}
A \emph{full-dataset scan} means streaming every projection or event record, typically \(10^{2}\)–\(10^{3}\,\mathrm{GB}\) per tomographic run or several terabytes per serial-crystallography campaign.

Complete reads underpin high-fidelity analyses that cannot tolerate missing frames. Iterative phase-retrieval and filtered back-projection algorithms in tomography require the entire sinogram for each refinement cycle. In serial femtosecond crystallography, clustering, indexing, and Monte Carlo integration need millions of patterns to converge on accurate structure factors \cite{maiden2009improved}. Full-dataset scans also support \emph{reference reprocessing} and video-style visualization, where sequential reads saturate available bandwidth and compression efficiency, and parallel read pipelines dominate time-to-solution.

\subsubsection{Metadata-driven queries}
A \emph{metadata query} retrieves only descriptive information, sample-environment logs, scan parameters, detector geometry, or a limited set of columns/branches without accessing the large image stacks. Typical payloads are \(\mathcal{O}(10^{1}\!-\!10^{3})\,\mathrm{kB}\), which a live beamline dashboard may issue tens to hundreds of such queries per second during an experiment.

Synchrotron and neutron facilities increasingly push raw detector frames straight into object stores (\gls{AWS} \gls{SThree}, \gls{Ceph}, \gls{MinIO}) to curb on-premise costs and enable remote collaboration. Brookhaven’s \gls{NSLSII}, for example, operates a {\small 5 PB} \gls{MinIO} cluster exposed via the \gls{SThree} \gls{API}, the Bluesky acquisition pipeline writes NeXus event documents there, and downstream notebooks read them over the \gls{WAN} \cite{Lancon2022}. The UK’s Rutherford Appleton Laboratory offers the \gls{ECHO} \gls{Ceph} object store, providing {\small 100 PB} of \gls{SThree} capacity that underpins \gls{IRIS} cloud analysis services and beamline portals \cite{ECHO2025}. In these environments, transferring even a few gigabytes across a \gls{WAN} to inspect scan headers is inefficient when lightweight, metadata-only queries can satisfy the request.


\section{Storage Foundations: HPC vs Object Stores}
\label{sec:storage-foundations}
This section contrasts parallel file systems with cloud object stores to highlight the core trade-offs in throughput and latency. We review how Lustre/GPFS/BeeGFS achieve high sequential I/O and why many small reads and metadata traffic degrade performance, then summarize \gls{SThree} semantics, costs, and latency.

\subsection{Traditional HPC Storage Paradigms}
\label{sec:traditional-hpc-storage-paradigms}
Parallel file systems such as Lustre, IBM \gls{GPFS}, and \gls{BeeGFS} stripe files across many disks and coordinate access with distributed locking, delivering high sequential throughput \cite{schwan2003lustre,schmuck2002gpfs}. These designs degrade under many small reads and heavy metadata traffic, which production traces show small transfers dominate call counts and metadata can consume a large share of requests \cite{bez2022access}.

When the I/O profile shifts from a few large checkpoints to many small look-ups and interactive slices, these design assumptions break down. A study from the Summit and Cori supercomputers shows that small transfers (<\SI{1}{\mega\byte}) account for the overwhelming majority of read and write calls at both the file and process levels, and metadata operations can saturate metadata servers and become a primary scalability bottleneck \cite{bez2022access}.

\subsubsection{Parallel File Systems (Lustre, GPFS, BeeGFS)}
\label{sec:parallel-file-systems}
Lustre, IBM \gls{GPFS} (now Spectrum Scale) \cite{schmuck2002gpfs}, and \gls{BeeGFS} have dominated supercomputing storage for over two decades, consistently delivering throughput of hundreds of gigabytes per second. By striping data across hundreds of disks and coordinating access with distributed locks, these systems excelled at writing multi-gigabyte files sequentially. The same system, however, reveals hidden costs when workloads shift to small, random reads or to remote, \gls{WAN}-mounted access.

Classic \gls{HPC} file systems split responsibility between \emph{metadata servers} (\gls{MDS}) and many \emph{object/data servers} (\gls{OSS} in Lustre, \gls{NSD} servers in \gls{GPFS}, storage targets in \gls{BeeGFS}). Files are \emph{striped} across a few to hundreds of disks in multi-megabyte chunks. Doing this allows a single sequential read or write to optimize the bandwidth of an entire system. \gls{PFS} uses token-based distributed locking to keep \gls{POSIX} consistency on a shared-disk \gls{SAN} \cite{schmuck2002gpfs}. \gls{BeeGFS} achieves similar semantics over Ethernet by separating data and metadata and scaling the service.

Parallel file systems shine whenever an application issues long, contiguous transfers, checkpoints/restarts, volumes, and snapshots. NASA’s \emph{Pleiades} cluster still sustains \(\sim\!1\)\,\si{\giga\byte\per\second} from disk for a single 512-rank IOR stream and bursts to \SI{9}{\giga\byte\per\second} when the same data are serviced out of the page cache \cite{6507507}. Modern flagships go far beyond that; Los Alamos’ \emph{Trinity} Sonexion Lustre tops out near \SI{1.6}{\tera\byte\per\second} for a 78 PB pool \cite{osti_1367056}. Even a single E1000 \gls{OSS} inside NERSC’s \emph{Perlmutter} can saturate \SI{41}{\giga\byte\per\second} read and \SI{27}{\giga\byte\per\second} write to one \gls{OST} \cite{lockwood2024architecture}. These traits explain why parallel file systems remain the choice for bulk sequential scans and multi‐terabyte tomography stacks.

Lustre separates responsibilities between dedicated \emph{metadata servers} (\gls{MDS}) that keep inodes and directory state on one or more \emph{metadata targets} (MDTs) and multiple \emph{object‑storage servers} (\gls{OSS}) that deliver the bulk data stored on \emph{object‑storage targets} (\gls{OST}s).  Files are \emph{striped} across a configurable number of \gls{OST}s (stripe count) with a tunable stripe width, enabling a single sequential transfer to engage hundreds of disks in parallel. The design of flagship systems such as Oak Ridge’s Spider‐3 sustains more than \SI{1}{\tera\byte\per\second} aggregate read bandwidth \cite{braam2019lustre, oral2013olcf}.

IBM \gls{GPFS} employs a distributed \emph{token‑based locking} protocol to coordinate metadata and data updates across all nodes, persisting mutations in replicated journals so that failed servers can recover without full replays. This mechanism provides stronger resilience and copes slightly better with so‑called metadata “storms” than Lustre, though at the cost of a more complex recovery state \cite{schmuck2002gpfs}.

Parallel file systems raise aggregate bandwidth by slicing every file across many Object Storage Targets (\gls{OST}s/\gls{NSD}s). When workloads flip from multi-GB checkpoints to thousands of $4$–$64$\,\si{\kilo\byte} reads, the same striping logic backfires. Intel’s LUG-2018 “Small File I/O” report shows that files smaller than the \gls{DoM} threshold generate disproportionately more RPCs per MiB, leading to significantly reduced bandwidth on multi-\gls{OST} Lustre systems \cite{gmitter2018smallfile}.

Even in a namespace-sharded file system like Lustre’s \gls{DNE}, a camera-style “one-file-per-frame” workflow still concentrates its create/unlink traffic in a single hot directory subtree. Production traces from 60 \gls{HPC} systems show that \SI{64}{\percent} of files are smaller than \SI{64}{\kilo\byte}. When a system is flushed with thousands of tiny \gls{HDFfive} or JPEG files, metadata operations increase exponentially. Based on these 60 different \gls{HPC} systems, research shows that metadata operations can account for up to \SI{80}{\percent} of total file system operations \cite{9768784}.

\Gls{HPC} administrators often impose per-user inode quotas because millions of tiny files overload Meta Target Devices \cite{carns2009small}. Therefore, monolithic containers such as \gls{HDFfive} can be preferred on-prem, whereas object stores favor chunk-per-object layouts (e.g., Zarr).

\subsubsection{POSIX-Centric Scientific Formats}
\label{sec:posix-centric-formats}
Most \gls{HPC} codes write \emph{monolithic containers}, a single \gls{POSIX}-seekable file that includes raw arrays and metadata. \gls{HDFfive} popularised this approach, while NeXus adopts the same file structure with beamline-specific naming conventions. The design is perfect for bulk, sequential, local parallel file system scans. However, the need to search through super-blocks and B-trees for every small slice makes it poorly suited to cloud object stores and interactive, many-small-read workflows, motivating the chunk-per-object formats.

The Hierarchical Data Format 5 (\gls{HDFfive}) stores every dataset, chunk, and attribute in a single byte‐addressable file whose internal super-block, B-trees, and heap tables, with the help of \gls{POSIX}, seek for navigation \cite{howison2010tuning}. Nexus, the de facto standard at many photon and neutron sources, layers a domain system on top of the same \gls{HDFfive} container, retaining identical I/O semantics while prescribing beamline-specific group names and units \cite{konnecke2015nexus}. This “all-in-one” layout simplifies file management but couples performance to the underlying file-system block size and to how well metadata caches handle random seeks.

Out-of-the-box \gls{HDFfive} access (via h5py, MATLAB, etc.) issues many small, non-contiguous \gls{POSIX} reads. Each rank that samples a \SIrange{4}{8}{\mega\byte} slice generates dozens of tiny, <\SI{64}{\kilo\byte} reads, leading to many metadata lookups. Small, non-contiguous selections generate many <\SI{64}{\kilo\byte} reads and metadata lookups, collective I/O reduces but does not eliminate this overhead \cite{Breitenfeld2022Parallel,9499420}. Single-file heritage makes many small-read interactive workloads sensitive to metadata hotspots, motivating chunk-per-object designs.

Even when using collective metadata I/O, each \gls{HDFfive} read still must fetch the superblock and descriptive metadata before reading the raw data. In the CCGrid’21 benchmarks on Summit and Cori, metadata I/O alone accounted for as much as $\approx 58\%$ of the total read time \cite{9499420}. \gls{HDFfive}/NeXus excels for large, sequential scans and single-node post-processing, but its single-file, \gls{POSIX}-style heritage makes it vulnerable to metadata hotspots when handling many small reads, motivating object-store–oriented layouts such as chunk-per-object arrays (e.g., Zarr) and columnar row-group formats (e.g., Parquet).

\subsection{Cloud Object Storage Fundamentals}
\label{sec:cloud-object-storage-fundamentals}
Cloud object stores, exemplified by Amazon \gls{SThree}, provide a flat, immutable-object namespace, global durability, and a pay-as-you-go pricing model. They remove local capacity provisioning constraints but introduce \gls{HTTP}S-level latency and per-request charges that do not exist in local \gls{NVMe} or parallel file systems.

\subsubsection{Architectural model}
Amazon Simple Storage Service (\gls{SThree}) organizes data in \emph{buckets} that share a \emph{flat key namespace within a bucket}, and directory hierarchies are only a key-naming convention. Since December 2020, \gls{SThree} guarantees \emph{strong read-after-write consistency} for all operations, removing the race conditions that earlier eventual-consistency semantics introduced \cite{AWSConsistency2020}.

\subsubsection{Request classes and cost drivers}
Every interaction with \gls{SThree} is an \gls{HTTP}S \gls{API} call in one of four core request classes. Each call is billed in addition to storage (\si{GB}\, month) and data egress charges \cite{AWSS3Pricing2025}.

\subsubsection{Latency characteristics}
Each request traverses a multi-AZ control plane, giving time-to-first-byte latencies of \SIrange{100}{200}{\milli\second} for small objects \cite{AWSS3Performance2024}. In comparison, on-premises \gls{NVMe} RAID or parallel file systems typically deliver sub-millisecond metadata look-ups, and even \gls{AWS}’s own \gls{EFS} \gls{SSD} class reports $\approx\SI{0.25}{\milli\second}$ latencies \cite{AWSEFSLatency}. This gap explains why unmodified \gls{HPC} workloads often perform poorly on \gls{SThree}. \subsubsection{Performance-optimisation layers}
\begin{itemize}
  \item \textbf{Multipart uploads}: split objects ($\ge\SI{100}{\mega\byte}$) into \SIrange{5}{5000}{\mega\byte} parts that upload in parallel and resume after failure \cite{AWSS3MultipartDoc}.
  \item \textbf{Range GETs}: request only required byte spans, ideally aligned with the same \SIrange{8}{16}{\mega\byte} boundaries used during uploads \cite{AWSS3RangeGET}.
  \item \textbf{Prefix parallelism}: \gls{SThree} scales to at least \num{5500} GET/HEAD and \num{3500} write requests per \emph{prefix}. Optimally sharding key lifts can aggregate throughput to multi \si{TB/s} \cite{AWSS3Performance2024}.
\end{itemize}

These optimization strategies allow object storage to approach \gls{HPC}-class throughput, but latency for small, random slice reads remains higher than on local or \gls{NVMe}-backed file systems.

\section{Cloud-Native Models and Compression}
\label{sec:cloud-native-models-compression}
Object stores provide scale but add request latency, immutability, and per-request billing \cite{durbin2020cloud}. Cloud-native models partition arrays or tables into independently addressable objects to exploit concurrency while controlling slice-read cost.

\subsection{Cloud-Native Storage Models}
\label{sec:cloud-native-storage-models}
Cloud object stores such as Amazon \gls{SThree}, Azure Blob Storage, and Google Cloud Storage provide effectively unlimited capacity and global accessibility. However, they introduce request latency, and per-request billing, which clash with the low-latency assumptions of traditional \gls{HPC} formats \cite{durbin2020cloud}. To exploit cloud elasticity without prohibitive slice-read costs, a new generation of \emph{cloud-native storage models} has emerged, each rethinking how scientific arrays or tables are partitioned, compressed, and addressed in an object store.

This thesis does not attempt an extensive survey of all scientific file formats. The goal is to compare a small set of \emph{adoption-realistic} storage models that could reasonably be deployed for multi-terabyte scattering data on Amazon \gls{SThree}, and that span the main design choices that drive object-store performance. The candidate set of storage methods was selected to satisfy three criteria:

\begin{itemize}
  \item \textbf{Practical deployability on \gls{SThree}:} an open specification and a maintained implementation with native object-store support (client-side or via a service layer).
  \item \textbf{Representativeness for the studied workflow:} ability to store either dense detector arrays or associated tabular metadata, and to support the dominant access patterns in this thesis (random frame/slice reads and full sequential scans).
  \item \textbf{Coverage of distinct layout families:} monolithic file layouts (\gls{HDFfive}), chunk-per-object key–value arrays (Zarr), \gls{HDFfive} semantics with sharded chunks/metadata exposed via a REST service (\gls{HSDS}), fragment-based arrays with metadata pruning (TileDB), and single-object page/cluster layouts accessed via range reads (\gls{ROOT}/\gls{TTree}).
\end{itemize}

While a custom storage layout could in principle be engineered for this dataset, it would still have to specify the same core mechanisms as any production format: a chunking granularity, an object naming and sharding scheme, a metadata/index structure, a compression pipeline, and concurrency/consistency semantics. These choices map closely onto the layout families represented above. In particular, Zarr approximates the simplest viable custom design (chunk-per-object with lightweight metadata), while TileDB and \gls{TTree} represent richer indexing and streaming strategies. Designing, implementing, and validating a new storage engine would shift the thesis from comparative evaluation to system construction and would reduce reproducibility for other groups. For these reasons, the study focuses on established formats and uses the experimental results to derive design implications that would also inform any future custom solution.

In addition to the conceptual layout differences, the storage candidates were chosen because they were practical to deploy and benchmark on Amazon \gls{SThree} under a single, reproducible test environment. Specifically, each option maintains a stable S3 I/O path (either direct object access or a stateless service layer), supports partial reads without a POSIX gateway, and exposes tunable physical granularity (chunks/tiles/pages) and standard compression filters used in this thesis. The five candidates also represent distinct \emph{deployment and I/O paths} that an engineering team would realistically choose between:

  \begin{itemize}
	  \item \textbf{\gls{HDFfive}+\gls{HSDS}:} preserves \gls{HDFfive}/NeXus compatibility while adding an explicit REST service that shards chunks and metadata into \gls{SThree} objects.
	  \item \textbf{Zarr:} a serverless, direct-to-\gls{SThree} chunk-per-object store with minimal metadata, representative of the simplest cloud-native array design.
	  \item \textbf{TileDB:} a library-based storage engine that writes immutable fragments plus fragment metadata (enabling pruning and consolidation), representing an “engine + metadata” approach rather than pure chunk key value store.
	  \item \textbf{Parquet:} the dominant columnar format in the cloud analytics stack, included to cover tabular experiment metadata and to document the engineering mismatch between row-group I/O and frame/tile access (the detector-stack mapping is explored only via a single-object pilot; Appendix \ref{app:a8-parquet}).
	  \item \textbf{\gls{ROOT}/\gls{TTree}:} a largely single-object layout with internal paging/clustering accessed via Range GETs, providing a counterpoint to object-sharded designs.
  \end{itemize}

\subsubsection{HDF5 + HSDS}
\label{sec:hdf5-hsds}
The \gls{HDFfive} ecosystem represents the most mature and widely adopted solution for storing complex scientific data, spanning disciplines from climate modeling to synchrotron beamline acquisition \cite{10.1145/1966895.1966900}. However, developers designed the format for low-latency, parallel file systems. When migrated naively to cloud object stores, its monolithic layout magnifies request latency and per-operation costs. To preserve \gls{HDFfive}’s rich data model while overcoming these cloud-specific bottlenecks, the Highly Scalable Data Service (\gls{HSDS}) was created as a stateless REST layer that shards chunks and metadata into individually addressable objects \cite{readey2020hsds}.

Hierarchical Data Format 5 (\gls{HDFfive}) is an open-source container, data model, and I/O library designed to store extensive, multidimensional scientific data efficiently \cite{10.1145/1966895.1966900}. An \gls{HDFfive} file consists of \emph{datasets} (n-dimensional arrays) organized in a \gls{POSIX}-style hierarchy of groups. Datasets may be stored either \emph{contiguously} or as fixed-size \emph{chunks}. Chunking enables transparent filter pipelines (e.g., \texttt{gzip}, \texttt{lz4}, \texttt{zstd}) and independent partial reads/writes. At the same time, the library’s \gls{MPIIO} pathway lets thousands of compute nodes access different chunks concurrently \cite{hdf5_chunking}. These strengths made \gls{HDFfive} the standard library/system used at X-ray, neutron, and electron facilities.

Placing a monolithic \gls{HDFfive} file on Amazon \gls{SThree} causes each \gls{POSIX} \texttt{read()} call to issue a separate \gls{HTTP} Range GET. Therefore, a single \SI{1}{\mega\byte} slice triggers two network round-trips (metadata + data), amplifying latency and incurring request fee costs that traditional \gls{HPC} deployments never experience \cite{hdf5_ros3}. Moreover, the file's internal B-tree indices are optimized for low-latency block storage, not for the \SIrange{100}{200}{\milli\second} object-store round-trip typical of Amazon \gls{SThree}.

The \emph{Highly Scalable Data Service} (\gls{HSDS}) re-implements the \gls{HDFfive} abstraction as a stateless REST \gls{API} \cite{readey2020hsds}. Internally, \gls{HSDS} maps every chunk and metadata item to separate objects (\gls{SThree}, Azure Blob, \gls{MinIO}, or \gls{POSIX}) and maintains small \gls{JSON} documents that map logical dataset coordinates to object keys. This exposes \gls{HDFfive} groups, datasets, and attributes over standard \gls{HTTP} requests.

Production \gls{HSDS} clusters back multi-hundred-terabyte public archives, e.g., NREL’s 500\, TB Wind Toolkit dataset, enabling subsetting without full downloads \cite{draxl2024wtkled}. \gls{HSDS} retains \gls{HDFfive}’s rich ecosystem yet provides proper cloud-native capabilities.

Most Lustre and \gls{GPFS} installations cap the number of inodes a single user may allocate because millions of tiny files saturate the metadata target (MDT) servers long before disk bandwidth runs out \cite{gmitter2018smallfile}. Therefore, a monolithic \gls{HDFfive} container carries a practical on-prem advantage: \emph{one inode per file} and negligible directory pressure. By contrast, chunk-per-object formats such as Zarr can create $10^{5}$–$10^{7}$ objects for a single 1 TB tomography scan, a scenario many \gls{HPC} administrators actively discourage or block via strict inode quotas. The same characteristic becomes an asset in cloud object stores, where inodes do not exist, and latency can be hidden behind massive parallelism for GET/PUT.

\gls{HDFfive}’s internal super-block, heap tables, and fractal B-trees replicate several file-system duties to offer \gls{POSIX}-seekable random access \cite{howison2010tuning}. On low-latency local storage, this overhead is minor; however, when a single 4 MB slice is served from \gls{SThree}, it incurs two round-trips: first to fetch the B-tree node, then the data chunk, doubling both latency and request cost. Chunk-per-object layouts such as Zarr avoid this indirection because the chunk itself is the addressable unit. Columnar and paged formats (Parquet, \gls{ROOT}/\gls{TTree}) instead pay an initial footer/index load and then use Range GETs against contiguous regions within a file.

\subsubsection{Zarr}
\label{sec:zarr}
Zarr is an open-source system for storing chunked, compressed $n$-dimensional arrays as small objects \cite{zarrspecv3}. It partitions each array into regular \emph{chunks} and stores every chunk as an independent object (e.g., a file in a \gls{POSIX} system or a key in Amazon \gls{SThree}). Zarr supports codecs such as \texttt{gzip}, \texttt{lz4}, and \texttt{zstd}, and uses \gls{JSON} metadata files. The format requires no central server, which suits cloud object stores where high-latency, high-throughput parallel access dominates.

Because each chunk maps to a \gls{SThree} key, multiple parallel GETs can execute simultaneously, achieving high aggregate bandwidth. Time-to-first-byte per chunk on \gls{SThree} is typically \SIrange{100}{200}{\milli\second} where concurrency improves throughput rather than single-request latency. Write throughput scales similarly with thousands of concurrent PUTs (one per chunk), enabling high-rate ingestion at modern beamlines with acceptable overheads.

Researchers across various fields have adopted Zarr; \gls{GDAL} provides a native driver for geospatial rasters \cite{gdal2024zarr} while the bioimaging community standardized on \gls{OME}-Zarr for petabyte-scale microscopy archives \cite{moore2023ome}. A NumFOCUS-backed governance model and a public Zarr-specs \gls{RFC} process support long-term stability \cite{zarrspecv3}.

Zarr’s chunk-per-object design aligns well with the partial-read workloads studied in this report. However, its performance depends on chunk size, sharding, and metadata unification.

\subsubsection{Apache Parquet}
\label{sec:apache-parquet}
Apache Parquet is an open, columnar storage format originally developed at Twitter and Cloudera to bring Dremel-style analytics to the Hadoop ecosystem. It organizes a file into one or more \emph{row groups}. Within each row group, every column is stored contiguously as a \emph{column chunk}, compressed using lightweight compression and dictionary encoding. By reading only the required columns and row groups that satisfy a filter predicate, Parquet reduces I/O volume for wide, sparse tables. Parquet supports several compression codecs, such as Snappy, \texttt{gzip}, deflate, and BZIP2 \cite{vohra2016apache}. Within each row group, Parquet applies column-specific encodings—such as dictionary or run-length encoding—and independent compression, further shrinking the on-disk footprint and amplifying the format’s I/O-reduction advantage.

On Amazon \gls{SThree}, each row group is laid out as a large (typically \SIrange{64}{256}{\mega\byte}) contiguous byte range, allowing clients such as Apache Arrow’s vectorized reader or \gls{AWS} Athena to fetch gigabyte-scale slices with a single Range GET. The \gls{AWS} Athena pricing page states that converting data to compressed, columnar formats like Parquet “can save up to \SI{90}{\percent} per query and improve performance” compared with raw \gls{CSV} \cite{aws_athena_pricing}.

Parquet has become the default on-disk file format throughout today’s analytics stack. Apache Spark uses Parquet as the \emph{default data source}, and Apache Iceberg likewise keeps its immutable data files in Parquet \cite{iceberg_spec}. In the in-memory layer, Pandas and Apache Arrow provide first-class readers/writers for Parquet \cite{pandas_read_parquet}. Primary cloud analytics services natively ingest Parquet, including Google BigQuery \cite{bq_parquet}, \gls{AWS} Glue \cite{aws_glue_parquet}, and Amazon Athena \cite{aws-athena-columnar}.

Parquet’s columnar design is well-suited to the tabular metadata portion of scattering experiments, where scientists frequently select a handful of columns across millions of rows. However, its row-group granularity (tens of MB) and lack of native $n$-D chunking can inflate latency for small pixel tiles.


\subsubsection{TileDB}
\label{sec:tiledb}
TileDB is an open-source array storage engine for both dense and sparse data, organizing writes to immutable, timestamped \emph{fragments} \cite{Papadopoulos2016TileDB,TileDBDataLayout}. Each fragment contains attribute data serialized into \emph{data tiles}. For object stores, TileDB uses a virtual filesystem with native backends for \gls{SThree}, Azure Blob Storage, and GCS. On \gls{AWS} \gls{SThree}, it writes using multipart uploads to create append-only fragment objects \cite{TileDBBackends,TileDBS3}. The array directory contains the schema, per-fragment data, and fragment metadata \cite{TileDBFragmentMeta}.

Unlike chunk-per-object layouts, a single fragment typically produces a small, fixed set of objects. It generates one attribute file per attribute, one fragment-metadata file, one write-marker record, and the already-existing schema file. The total object count scales with the number of \emph{fragments} and attributes rather than the number of tiles, which reduces LIST/HEAD amplification on \gls{SThree} for large arrays \cite{TileDBDataLayout,TileDBFragmentMeta}. Excessive fragmentation, however, increases first-open overhead because readers must fetch per-fragment metadata \cite{TileDBConsolidateFragmentMeta}.

Upon opening, TileDB loads fragment metadata and per-tile min-max statistics. The system then queries the pruned fragments and data tiles whose minimum-bounding rectangles (MBRs) do not intersect the requested subarray \cite{TileDBFragmentMeta,TileDBMBR}. Reads support ordered or unordered layouts, multi-range subarrays \cite{TileDBReadLayouts}.

All writes create new immutable fragments and write-marker files, enabling lock-free multiple-reader/multiple-writer behavior and consistent reads at a chosen timestamp range (“time traveling”). Fragment merging helps compact many small fragments into larger ones, allowing space to be reclaimed \cite{TileDBTimeTravel}.

TileDB applies a per-attribute filter pipeline to tiles. Supported compressors include \texttt{gzip}, Zstandard, \texttt{lz4}, RLE, BZIP2, and integer-oriented transforms (bit-shuffle, bit-width reduction, double-delta). Checksums (MD5/SHA-256) are available for integrity \cite{TileDBCompression,TileDBChecksums,TileDBEncryption}.

\subsubsection{ROOT / TTree}
\label{sec:root-rntuple}
\gls{ROOT} is an object-oriented C++ framework developed at \gls{CERN} to handle the petabyte-scale data streams of high-energy-physics experiments \cite{blomer2020evolution}. Its core storage abstraction, \gls{TTree}, stores events as rows and detector variables as \emph{branches}. The format splits each branch into contiguous \emph{baskets}, allowing readers to load them independently. This column-friendly layout lets analysis jobs load only the necessary branches, minimizing I/O and deserialization overhead, a property directly relevant to slice-level scattering analysis.

After two decades of incremental evolution, \emph{\gls{TTree}} showed architectural limits for modern heterogeneous hardware and cloud storage. The \gls{RNTuple} project, therefore, re-implements \gls{ROOT} I/O with a stricter columnar layout, page-based compression, and a self-describing, versioned metadata footer \cite{blomer2020evolution}. Pages (\(\approx\)\,\SIrange{8}{16}{\kilo\byte}) are grouped into clusters so that entirely columnar reads issue a single contiguous request, while sparse event selections fetch only the referenced pages. By decoupling metadata from data pages, \gls{RNTuple} avoids rewriting the entire file when appending events, which is critical for streaming detectors and results in improved partial reads.

Through the generic \gls{ROOT} Page Source interface, pages can reside in \gls{POSIX} files, over \gls{HTTP}(S), or as individual \gls{SThree} objects \cite{rootRNTuple2025}. Scaling studies by Blomer showed near-linear throughput up to \(\mathcal{O}(10^{2})\) concurrent readers on a >100‐core \gls{HPC} cluster served by a \gls{DAOS} object store, achieving an aggregated read rate above \SI{35}{\giga\byte\per\second} before the storage system became the bottleneck \cite{blomer2024root}.

This architecture provides high-throughput, scalable, and selective access to petabyte-scale datasets on \gls{HPC} systems and in the cloud, which is relevant for slice-level scattering analyses.

\subsection{Format design trade-offs for this thesis}
\label{sec:format-tradeoffs}

From a computer-science perspective, the five formats in this study represent different points in a shared design space: how an $n$-dimensional or tabular dataset is mapped to physical storage, how metadata is indexed, and how many objects and round-trips each logical operation induces. This subsection summarises those design choices and how they motivate the experiments.

\subsubsection{HDF5/HSDS}
\gls{HDFfive} defines a hierarchical container of datasets (multidimensional arrays) and groups, backed by a single byte-addressable file. HSDS replaces that monolithic file by sharding each HDF5 chunk and its metadata into separate objects and exposing them via a REST API. Algorithmically, each logical array access becomes:

\begin{itemize}
    \item a metadata lookup in small JSON documents that map indices to object IDs
    \item one or more chunk-object GETs.
\end{itemize}

The strength is a rich, self-describing data model and interoperability with existing HDF5/NeXus tooling. The weakness for this thesis is that HSDS introduces an extra “service layer” hop and many small metadata objects, which can increase both GET counts and per-slice latency compared with formats that go directly from index $\rightarrow$ object key. This motivates testing whether HDF5/HSDS can match newer array formats in terms of slice latency (RQ1) and scan throughput (RQ2) when deployed on Amazon \gls{SThree}.

\subsubsection{Zarr}
Zarr models an $n$-dimensional array as a pure key–value mapping: each regular chunk is stored as an independent object, and a small number of JSON metadata files describe dtype, chunk shape, and codecs. A read of a slice that aligns with $k$ chunks triggers exactly $k$ object GETs, with no intermediate service layer. Zarr’s strengths in this study are:

\begin{itemize}
    \item direct chunk-to-object mapping that enables embarrassingly parallel GETs
    \item minimal per-chunk metadata overhead once the JSON headers are loaded.
\end{itemize}

Weaknesses include large keyspaces (many objects per dataset) and the cost of listing or opening unconsolidated stores. These properties lead directly to the hypotheses that Zarr should perform well for interactive slices (few chunks per frame) and moderately well for full scans, and that its request intensity (GETs/GiB) will be tightly tied to chunking (RQ1–RQ3).

\subsubsection{Parquet}
Parquet models data as a table of rows and typed columns. The file is organized into row groups, and within each row group, each column is stored as a contiguous column chunk with its own encoding and compression. From a layout perspective, the fundamental unit of I/O is the row group (tens to hundreds of MiB), not an $n$-D image tile. This is advantageous for analytics workloads that scan or filter on a subset of columns: a query engine can skip entire row groups and untouched columns. In this thesis, the same design is a weakness for detector frames: loading a single 2-D slice within a row group pulls the entire row group and incurs a high metadata-open cost. These semantics motivated the pilot-only Parquet experiment and its exclusion from timed $n$-D slice/scan benchmarks (documented in Chapters \ref{ch:whatYouDid}–\ref{ch:resultsAndAnalysis}).

\subsubsection{TileDB}
TileDB generalises dense and sparse arrays as a set of immutable fragments. Within each fragment, attribute values are stored in tiles; the fragment directory holds array schema, fragment metadata (including tile ranges and min–max), and one or more attribute files. On object stores, reads proceed in two stages:

\begin{itemize}
    \item load and prune fragment metadata using tile bounds and statistics
    \item issue a small number of large GETs for the relevant attribute tiles.
\end{itemize}

The strengths of this study are:

\begin{itemize}
    \item a low object count that scales with fragment count rather than tile count
    \item efficient full scans where long, contiguous tile ranges can be streamed
\end{itemize}

The drawbacks are higher first-open costs when fragment counts are high and slightly higher per-fragment complexity than in a pure chunk-per-object layout. These design choices make TileDB a strong candidate for high-throughput full scans (RQ2) and for moderate-latency slices that benefit from pruned, long-range reads (RQ1, RQ3).

\subsubsection{ROOT/TTree}
ROOT’s TTree and its modern RNTuple redesign treat data as a columnar event store. Conceptually, each branch is a column; data are organized into small pages grouped into clusters, and a separate index describes which pages belong to which cluster. A read of a contiguous range of events on a few branches can be served by a single or a small number of long-range GETs; a sparse selection of events or an awkward “frame-shaped” slice may touch many small pages. The format’s strengths are:

\begin{itemize}
    \item fine-grained, columnar access for event-style analyses
    \item efficient sequential scans when reading along the event axis
\end{itemize}

The weaknesses of this thesis are that detector frames are not the natural access unit and that sparse, frame-random reads can devolve into many small-range GETs against a single large object. This leads directly to the experimental question of whether TTree can still offer competitive full-scan throughput and what latency penalty it incurs for frame-based slices (RQ1–RQ2).


\subsection{Compression Algorithms Reviewed}
\label{sec:compression-algorithms}
Lossless compression is a first-order lever for improving performance and reducing costs in cloud object–store workflows. Smaller chunks reduce \gls{SThree} egress and request fees, while faster codecs shorten the latency that dominates interactive partial reads in synchrotron experiments.

The focus is on three open-source codecs that form a spectrum of trade-offs: \emph{gzip/DEFLATE} (high ratio, high \gls{CPU}), \emph{\gls{LZfour}} (low ratio, ultra-low latency), and \emph{Zstandard} (\emph{\gls{ZSTD}}, balanced). All four backends under test (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{TTree}) support \texttt{gzip}, \texttt{lz4}, and Zstandard (built-in or via standard filters/plugins).

\subsubsection{gzip}
\label{sec:compression-gzip}
GNU \texttt{gzip} has been the default lossless compression tool on Unix-like systems since 1992. \gls{RFC} 1952 formalizes \texttt{gzip}’s file format and header/trailer structure, and those specifications have remained patent-free and backward-compatible across three decades of scientific workflows \cite{deutsch1996rfc1952}.

The compressor implements the \emph{DEFLATE} scheme, a cascade of \gls{LZseventyseven} sliding-window substitution, followed by static/dynamic Huffman coding, tunable via nine quality levels that trade compression time for compression ratio. Level 6 is the GNU default, while level 1 sacrifices a \(\approx\) 30\% ratio to gain 3–4\(\times\) speed \cite{deutsch1996rfc1952}.

Benchmarks on floating-point climate and remote-sensing datasets stored in \gls{netCDF}-4/\gls{HDFfive} show typical space savings of 1.6–2.2\(\times\) at levels 4–6. In these studies, \texttt{gzip} incurred 2–5\(\times\) higher \gls{CPU} costs than \texttt{lz4}, and decompression throughput saturated around \SI{500}{\mega\byte\per\second} per core \cite{delaunay2019evaluation,chen2023fcbench}.

Native support for \texttt{gzip} exists in all five tested backends. Because \texttt{gzip} compresses each chunk independently, its compression ratio varies with chunk size and should be taken into account in these experiments. In the experiments, \texttt{gzip} is used as a “high-ratio, high-\gls{CPU}” reference, and its mature ecosystem guarantees consistent behavior across all five storage backends. Its well-characterized latency overhead provides a baseline against which to measure the partial-read performance of newer codecs like Zstandard and \texttt{lz4}.

\subsubsection{LZ4}
\label{sec:compression-lz4}
Introduced in 2011, \texttt{lz4} emerged as a lightweight derivative of the Lempel–Ziv (\gls{LZseventyseven}) family, designed to maximize streaming throughput while keeping memory overhead to a minimum. Its open-source framing format defines a compact header, provides optional block and content checksums, and employs a skippable frame mechanism, allowing new features to be added without breaking older decoders. These attributes have led to widespread adoption in operating systems, high-performance storage engines, and scientific data formats where sub-millisecond decode latency is critical.

The codec emphasizes extremely fast byte-wise parsing and a greedy match-finder that limits back-references to \SI{64}{\kilo\byte}. Because of this, the compression runs at $>$\SI{500}{\mega\byte\per\second} per core while decompression routinely exceeds \SIrange{2}{3}{\giga\byte\per\second}, albeit with modest ratios (1.2–1.7\(\times\) on floating-point data) \cite{lz42025,7440278}. A high-compression variant \texttt{lz4hc} improves the ratio by $\sim$15\,\% at 3–5 \(\times\) the \gls{CPU} cost.

Almeida \emph{et al.} compared \gls{LZfour} with \gls{ZLIB} on \gls{ROOT} HEP and climate grids, reporting \SIrange{1.0}{1.2}{\giga\byte\per\second} decompression (versus \SI{120}{\mega\byte\per\second} for \gls{ZLIB}) at the expense of only a 5–10\,\% ratio loss \cite{almeida2014two}. The \gls{VLDB}’24 “\gls{FCBench}” study recently measured the \gls{CPU} variant bitshuffle with \gls{LZfour} across 33 floating-point datasets. The study showed that it sustained \SI{0.9}{\giga\byte\per\second} compression and \SI{1.2}{\giga\byte\per\second} decompression on \SI{64}{\kilo\byte} blocks while achieving a median compression ratio of 1.43 \cite{chen2023fcbench}.

As a codec, \texttt{lz4} filters are first-class options in \gls{HDFfive} (\texttt{H5Z\_LZ4}), Zarr v3, Parquet, and TileDB. Because the \texttt{lz4} \SI{64}{\kilo\byte} match window limits cross-chunk redundancy, chunk sizes above \SIrange{1}{2}{\mega\byte} yield diminishing returns, which for this study aligns well with \gls{SThree} request-cost sweet spots.

In our benchmarks, \texttt{lz4} represents the “low-latency, low-\gls{CPU}” option, serving as the low-latency reference alongside \texttt{gzip} and \texttt{zstd}. The benchmarks examine how far compression ratio can be traded for lower partial-read latency without materially increasing monthly \gls{SThree} storage costs.

\subsubsection{zstd}
\label{sec:compression-zstd}
Zstandard (\texttt{zstd}) was released in 2016 and standardized by the IETF as \gls{RFC} 8878 \cite{collet2021rfc8878}. It combines an \gls{LZseventyseven} dictionary back-reference engine with Finite-State Entropy (\gls{FSE}) coding. It supports window sizes up to 128 MiB and offers 23 quality levels ($-7$ to 22), optional long-range mode, and trained dictionaries (negative values activate ultra-fast modes that trade ratio for speed). Decompression speed is deliberately kept almost constant across levels, whereas compression trades \gls{CPU} for ratio.

According to the \texttt{zstd} manual, the fastest compression mode exceeds \SI{200}{\mega\byte\per\second} per core, while the decoder sustains $>$\SI{500}{\mega\byte\per\second} per core on commodity x86 \gls{CPU}s \cite{zstdman2025}.

Promberger \emph{et al.}\ measured \texttt{zstd} level 2 on a 4.9 GB \gls{LHCb} collision dataset and found that its \emph{compression} throughput was roughly 2–3 \(\times\) higher than that of \emph{\gls{ZLIB}} level 2 while achieving an almost identical compression ratio \cite{promberger2023characterization}.

Delaunay et al. found that “Shuffle + Zstandard-2” compresses \gls{CFOSAT} and \gls{SWOT} remote-sensing files about 1.4 \(\times\) to 7 \(\times\) faster than the mission’s baseline “Shuffle + Deflate-3/4”. It delivers virtually identical space savings, accelerating decompression by up to seven-fold \cite{delaunay2019evaluation}. Across the full 33-dataset \gls{FCBench} suite, the \gls{VLDB}’24 study reports that a \emph{bitshuffle+}\texttt{zstd} pipeline achieves a harmonic-mean compression ratio of 1.47, while sustaining compression and decompression throughputs of $\sim\!\SI{1.4}{\giga\byte\per\second}$ and $\sim\!\SI{1.3}{\giga\byte\per\second}$, respectively  \cite{chen2023fcbench}.

As a codec, \texttt{zstd} is a first-class option in Parquet and TileDB, and is available as an extension for \gls{HDFfive} and Zarr v3. With \gls{FSE} contexts resetting per block, 1–4 MiB chunks maximize the ratio without inflating \gls{SThree} request counts. \texttt{zstd} occupies the “balanced ratio/latency” middle ground between \texttt{gzip} (high ratio, high \gls{CPU}) and \texttt{lz4} (low ratio, low \gls{CPU}) in the study.

\section{Summary and Link to Problem Statement}
\label{sec:summary-problem-statement}

The background above shows how accelerating detector output and evolving collaboration models outpace traditional \gls{HPC} storage, while object storage introduces latency–cost trade-offs. The key insights, mapped directly to the thesis problem, are:

\begin{itemize}
  \item \textbf{Data rates:} Multi-\si{\giga\byte\per\second} streams and multi-\si{\tera\byte} experiments are routine.
  \item \textbf{Mismatch:} Parallel file systems deliver bulk throughput but suffer under many small reads; \gls{SThree} scales throughput via concurrency but has \SIrange{100}{200}{\milli\second} TTFB per request.
  \item \textbf{Rise of object-store–oriented formats:} Chunked arrays (Zarr, HDF5/HSDS), fragment engines (TileDB), and columnar/paged files (Parquet, \gls{ROOT}/\gls{TTree}) trade object count, metadata strategy, and I/O granularity to adapt scientific data access to \gls{SThree}.
  \item \textbf{Thesis contribution and practical significance:} Prototype ingestion for five formats (Parquet as a pilot), quantitative benchmarking of four backends across small-slice and full-scan patterns, and a decision matrix that informs near-real-time experimental feedback, cloud spend, and next-generation scientific data platforms.
\end{itemize}

Taken together, the format descriptions in Section \ref{sec:cloud-native-storage-models} and the trade-offs in Section \ref{sec:format-tradeoffs} suggest that chunk-per-object layouts (Zarr, HDF5/HSDS) should favor interactive slices, fragment-based layouts (TileDB) should favor full scans, and single-file range-read layouts (\gls{ROOT}/\gls{TTree}) may struggle for frame-granularity reads on \gls{SThree}. For Parquet, we report only a single-object pilot mapping of the detector stack (Appendix \ref{app:a8-parquet}); partitioned Parquet variants were not evaluated. Chapters \ref{ch:methods} and \ref{ch:resultsAndAnalysis} formalize these expectations as RQ1–RQ3 and test them empirically on a controlled detector dataset across the four timed backends.

\section{Research Design and Process}
\label{sec:methods-design-process}
We follow a design-science path from idea to evidence: build artifacts, test them, and refine the design based on results.

\subsection{Research Paradigm}
\label{sec:researchParadigm}
This thesis uses an experimental approach within design-science research (\gls{DSR}). We benchmark four cloud-native storage formats (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{TTree}) and three compression algorithms (\texttt{gzip}, \texttt{lz4}, \texttt{zstd}) under controlled workloads and derive guidelines for optimizing cloud-native workflows for data-intensive synchrotron and neutron-scattering experiments.

Within this \gls{DSR} framing, the primary artifacts are (i) the storage and compression configurations that implement alternative cloud-native layouts and (ii) the decision matrix that encodes their performance and cost trade-offs for beamline scientists and engineers working on \gls{AWS} \gls{SThree}.

On the problem-driven side, the study targets three challenges: the massive data volumes generated by modern synchrotron and neutron facilities, the need for rapid, selective retrieval, and the need for cost-efficient cloud storage. On the solution-driven side, it implements and benchmarks cloud-native storage models and compression algorithms to address these challenges.

The research uses an iterative experimentation cycle in which preliminary findings can adjust subsequent tests (Figure \ref{fig:researchprocess}, decision point “Results consistent?”).

\subsection{Research Process}
\label{sec:researchProcess}
Figure \ref{fig:researchprocess} summarizes four stages: planning the experiment, conducting the experiment, analyzing the data, and discussing the results. Together they define the benchmarking framework for the storage formats and codecs on \gls{AWS} \gls{SThree}.

\subsubsection{Step 1: Planning the Experiment}
The planning stage involved several crucial tasks. First, the objectives of the experiment were defined, focusing on the comparison of four timed storage formats (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{TTree}) with Parquet as a pilot-only artifact (no timed runs) and three compression algorithms (\texttt{gzip}, \texttt{lz4}, \texttt{zstd}) concerning performance and compression efficiency for partial retrieval in scattering-style object-store workflows.

Key benchmarking variables are read latency, derived throughput, and request- and byte-based outputs. Compression algorithms were selected because they are widely used in scientific workflows and supported across all tested formats.

\subsubsection{Step 2: Conducting the Experiment}
For each format, one dataset for each codec (\texttt{gzip}, \texttt{lz4}, and \texttt{zstd}) was created. Chunking was fixed per format and held constant across runs. Two access patterns were executed per dataset: full scan of the \SI{20}{\gibi\byte} object and random single-frame reads (\(\sim\)\SI{15.82}{\mebi\byte} per frame). Logged metrics: per-run wall-clock time and per-session \gls{SThree} request counts, bytes, and latency percentiles (Appendix \ref{app:a4-metrics}). QC tests and rerun rules are listed in Appendix \ref{app:a2-run-qc}.

The primary observations in this thesis are run-level wall-clock times for storage \emph{operations} (one random frame read or one full scan). Such timings are strictly positive, typically right-skewed, and often dominated by multiplicative factors (network RTT, request queuing, decompression cost, and library-level overhead). In addition, consecutive runs are not perfectly independent in a cloud setting: HTTP/TLS connections are reused, client-side and library metadata caches warm up, and object-store throughput can vary over time due to shared infrastructure. For these reasons, we analyze $\ln(\text{time})$ and quantify uncertainty with resampling methods (Section \ref{sec:methods-statistical-hypotheses} and Appendix \ref{app:a3-stats}) rather than relying on normal-error, independent-sample assumptions.

An ideal benchmark design would obtain \emph{independent} replications by repeating each cell (format$\times$codec$\times$pattern) across many separate, isolated sessions (e.g., different time windows, fresh processes/containers, or even fresh instances) and by interleaving conditions to average out time-varying cloud effects. This would strengthen generalization beyond a single session and would simplify inference.

In practice, fully independent replications are expensive because the cost scales roughly linearly with the amount of data read and the required setup overhead. In this study, there are 24 cells, each with 5 warm-ups and 50 timed runs; the full-scan workload alone reads approximately $20$~GiB $\times 55 \times 12 = 13{,}200$~GiB ($\approx 12.9$~TiB) from \gls{SThree}. Replicating each cell across, for example, 5 independent sessions to reduce session-specific effects would increase this to $\sim 66$~TiB and multiply \gls{ECtwo} runtime and \gls{SThree} request charges by a similar factor (plus additional restart/cool-down overhead). Given these constraints, we instead run repeated measurements within a controlled session, randomize run order within the session, apply warm-ups to reduce cold-start effects and approach a quasi-steady regime (residual drift may remain), and treat remaining serial dependence explicitly in the uncertainty procedure (moving-block bootstrap). The resulting cross-format contrasts are therefore reported as \emph{descriptive and session-conditional}.

A practical precision target for the primary estimand (GM time/throughput) is relative 95\% CI half-widths of a few percent for full scans and on the order of 10\% for slice reads, while keeping runtime and \gls{SThree} traffic tractable. Because interval width typically shrinks approximately as $1/\sqrt{n}$, increasing beyond $n=50$ yields diminishing precision gains relative to linear cost. With $n=50$ timed runs per cell, the dependence-robust (MBB) GM 95\% CI half-width is 0.15--4.38\% for full scans (median 1.09\%) and 2.06--10.21\% for slice reads (median 4.16\%).

\subsubsection{Step 3: Analyzing the Data}
This step summarizes run-level timings and \gls{SThree} aggregates using the estimands and bootstrap procedures in Section \ref{sec:methods-metrics} and Appendices \ref{app:a2-run-qc}–\ref{app:a4-metrics}.

\subsubsection{Step 4: Discussing the Results}
The last stage interprets the findings for beamline scientists and data engineers by comparing performance and compression trade-offs across the storage configurations. It derives configuration recommendations for high-throughput, low-latency use cases and summarizes them in a decision matrix.

\subsection{Hypotheses}
\label{sec:methods-hypotheses}
Based on the storage models in Section \ref{sec:cloud-native-storage-models}, the format trade-offs in Section \ref{sec:format-tradeoffs}, and the access patterns in Section \ref{sec:access-patterns-scattering}, we formulate the following working hypotheses. Each hypothesis is evaluated descriptively using the estimands in Section \ref{sec:methods-metrics}, where we quantify uncertainty with dependence-robust confidence intervals but do not perform formal null-hypothesis testing or make causal claims.


\subsubsection{RQ1 — Interactive slice latency.}
\begin{description}
  \item[H1.1 (layout vs single-object).] For a fixed codec, formats with per-frame chunks or fragments (HDF5/HSDS, Zarr, TileDB) have lower geometric-mean slice latency than the single-object layout (ROOT/TTree), because they can overlap multiple smaller GETs and reduce metadata seek overheads.
  \item[H1.2 (layout–codec interaction).] For lightweight codecs (\texttt{lz4}, \texttt{zstd}), the per-frame chunk layout with direct object mapping (Zarr) achieves the lowest slice latencies, whereas under \texttt{gzip} the fragment-based layout (TileDB) can outperform Zarr by trading a smaller number of larger GETs for higher decode cost.
  \item[H1.3 (request intensity vs latency).] Within chunked/fragmented stores (HDF5/HSDS, Zarr, TileDB), lower GETs per GiB is associated with lower slice GM latency, whereas ROOT may violate this pattern because its single-object layout incurs paging and decode overhead even at low GETs/GiB.
\end{description}


\subsubsection{RQ2 — Full-dataset throughput.}
\begin{description}
  \item[H2.1 (throughput vs layout).] For any given codec, TileDB’s fragment layout achieves the highest full-scan throughput, followed by Zarr, with HDF5/HSDS and ROOT/TTree substantially slower because of higher request fan-out (HSDS) or single-object paging overhead (ROOT/TTree).
  \item[H2.2 (codec effect on scans).] For each format, \texttt{lz4} and \texttt{zstd} achieve equal or higher full-scan throughput than \texttt{gzip}, because they lower per-chunk decode cost at similar or only moderately larger stored size.
  \item[H2.3 (request intensity vs throughput).] Among chunked/fragmented formats, lower GETs per GiB is associated with higher GM throughput; ROOT/TTree is expected to be an outlier, with low GETs/GiB but relatively low throughput due to constrained parallelism.
\end{description}


\subsubsection{RQ3 — Cost posture and mechanisms.}
\begin{description}
  \item[H3.1 (codec vs storage).] For a fixed format, \texttt{zstd} and \texttt{gzip} achieve similar compression ratios and both store fewer bytes than \texttt{lz4}.
  \item[H3.2 (layout vs request cost).] For a given codec, Zarr and TileDB achieve lower GETs per GiB than HDF5/HSDS at comparable or lower latencies, reflecting their more favorable objectization for this workload.
\end{description}

\subsection{Statistical formulation and evaluation}
\label{sec:methods-statistical-hypotheses}
The hypotheses in this section (H1.1--H3.2) are stated in verbal form. Here, we present their statistical analyses and their evaluation using the estimands and procedures in Section \ref{sec:methods-metrics} and Appendix \ref{app:a3-stats}.

For each cell defined by \emph{format} $f$, \emph{codec} $c$, and \emph{pattern} $p\in\{\text{slice},\text{full}\}$, let $T_{fcp,1},\dots,T_{fcp,n}$ denote the repeated wall-clock times and

\[
Y_{fcp,r} \coloneqq \ln T_{fcp,r}.
\]

The session-conditional log-scale mean

\[
\mu_{fcp} \coloneqq \mathbb{E}\bigl[Y_{fcp,r}\mid\text{session}\bigr]
\]

defines the geometric-mean (GM) time

\[
\theta_{fcp} \coloneqq \exp(\mu_{fcp}),
\]

which is the primary estimand for latency and, via bytes/time, for throughput. For any two formats $f$ and $g$ at fixed $(c,p)$ we define the \emph{GM ratio}

\[
\rho_{f,g;c,p} \coloneqq \frac{\theta_{fcp}}{\theta_{gcp}}.
\]

On the original scale, $\rho_{f,g;c,p}<1$ means that $f$ is faster than $g$, and $\rho_{f,g;c,p}>1$ means that $f$ is slower than $g$. Each verbal hypothesis in H1.1--H3.2 can be written as an inequality on these ratios. For example, for RQ1 under a fixed codec $c$:

\begin{itemize}
  \item H1.1 (\emph{per-frame layouts faster than ROOT}) corresponds to directional hypotheses of the form
  \[
    H_{0}: \rho_{f,\text{ROOT};c,\text{slice}}\ge 1
    \quad\text{vs}\quad
    H_{1}: \rho_{f,\text{ROOT};c,\text{slice}}<1,
  \]
  where $f\in\{\text{HDF5/HSDS},\text{Zarr},\text{TileDB}\}$.

  \item H1.2 (\emph{Zarr fastest for light codecs}) can be written as
  \[
    H_{0}: \rho_{\text{Zarr},f;c,\text{slice}}\ge 1
    \quad\text{vs}\quad
    H_{1}: \rho_{\text{Zarr},f;c,\text{slice}}<1,
  \]
  for $c\in\{\texttt{lz4},\texttt{zstd}\}$ and $f\in\{\text{HDF5/HSDS},\text{TileDB},\text{ROOT}\}$.
\end{itemize}

Analogous formulations apply to H2.1--H2.3 (full-scan throughput) and H3.1--H3.2 (compression and request intensity), where the estimands are GM throughput, compression ratio, or GETs/GiB, rather than GM latency.

\subsubsection{Inference procedure (\emph{test})}
Rather than perform classical null-hypothesis significance tests for many pairwise contrasts, we adopt an \emph{estimation} approach:

\begin{enumerate}
  \item Work on the log scale $Y_{fcp,r}=\ln T_{fcp,r}$ and estimate $\mu_{fcp}$ and its uncertainty using a moving-block bootstrap (MBB) that preserves within-session serial dependence (Appendix \ref{app:a3-stats}).
  \item Back-transform to obtain $\theta_{fcp}$ and dependence-robust 95\% confidence intervals.
  \item Form GM ratios $\rho_{f,g;c,p}$ and corresponding 95\% confidence intervals by subtracting and re-exponentiating log-scale means.
\end{enumerate}

In a fully formal one-sided test of, for example, \emph{$f$ is faster than $g$}, we would reject $H_{0}:\rho_{f,g;c,p}\ge 1$ at the 5\% level whenever the 95\% confidence interval for $\rho_{f,g;c,p}$ lay entirely below~1. In this thesis, we use the same intervals \emph{descriptively}: we report point estimates and confidence intervals for $\theta_{fcp}$ and $\rho_{f,g;c,p}$, and we interpret hypotheses H1.1--H3.2 in terms of which orderings are compatible with these intervals. We do not aggregate these into a single global decision rule, nor do we control a family-wise or false-discovery rate across all contrasts.

\subsubsection{Why bootstrap, and why not \texorpdfstring{$t$}{t}-tests or ANOVA?}
As discussed in Step 2, run-level timings are right-skewed and can exhibit within-session serial dependence due to cache and cloud-variability effects, making independent and identically distributed assumptions fragile. Serial dependence and non-normality in the run-level timing data (Section \ref{sec:results-inventory} and Appendix Table \ref{tab:timing_diag_main}) violate the independence and homoscedastic normal-error assumptions underlying standard $t$-tests and ANOVA. A parametric linear model on $\ln(\text{time})$ could, in principle, be equipped with a dependence structure, but this would require additional modelling choices and diagnostics that are not central to the research questions. The moving-block bootstrap on $\ln(\text{time})$ was chosen because:
\begin{itemize}
  \item it respects the observed lag-1 autocorrelation and within-session serial dependence by resampling blocks rather than individual runs;
  \item it makes no parametric assumption on the marginal distribution beyond approximate stationarity within the timed window; we diagnose run-order drift separately and treat intervals as descriptive when drift is present;
  \item it yields confidence intervals for both cell-wise estimands ($\theta_{fcp}$, $p_{95}$) and derived quantities (ratios, throughput) uniformly.
\end{itemize}

Alternative procedures considered but not used include:
\begin{itemize}
  \item independent-sample $t$-tests or ANOVA on raw or log times (discarded due to serial dependence and skew);
  \item per-cell normal-theory intervals on $\ln(\text{time})$ (discarded because they rely on approximate normality of the sample mean under dependence);
  \item global regression models with format and codec as factors (discarded because formats are executed in separate sessions, so cross-format coefficients would still be session-conditional and require strong assumptions about between-session comparability).
\end{itemize}

In summary, the \emph{statistical hypotheses} behind H1.1--H3.2 are directional statements about GM times, throughputs, and related ratios. They are evaluated descriptively using dependence-robust confidence intervals for these estimands and their ratios. No formal multiple-comparison testing or causal inference is attempted, where all cross-format statements remain descriptive and session-conditional.

\section{Metrics, Statistics, and Scoring}
\label{sec:methods-metrics}
This section turns measurements into evidence by defining estimands, quantifying uncertainty, and scoring alternatives so the decision matrix reflects speed, reliability, and efficiency. The estimators and uncertainty procedures here apply unchanged to RQ1–RQ3 as specified in \ref{sec:methods-rq-map}.

\subsection{Performance Metrics and Evaluation Criteria}
We evaluate each format along four dimensions. \textbf{Latency} is reported for both slice and full-scan workloads as geometric-mean time with dependence-robust 95\% \glspl{CI} on the log scale, together with the 95th percentile and its interval (Appendix \ref{app:a3-stats}). \textbf{Throughput} for full scans is reported as geometric-mean GiB/s derived from bytes divided by time and analyzed on the log scale with MBB 95\% \glspl{CI}. \textbf{Request intensity} is measured as GETs per repetition and GETs per GiB using per-session \gls{SThree} aggregates (Appendix \ref{app:a4-metrics}). \textbf{Compression} is summarized through total stored bytes on \gls{SThree} and compression ratio relative to the raw baseline.

Cross-format contrasts are reported as \emph{descriptive} GM time ratios within each codec$\times$pattern family.

\subsection{Decision-matrix scoring (normalization and weights)}
For downstream selection, we compute normalized 0–100 scores per codec\(\times\)pattern using robust min–max scaling within that family (lower bound = 5th percentile, upper bound = 95th percentile, clipped).

For slice workloads, the score weights GM latency at 0.60, \(p_{95}\) at 0.20, GETs/GiB at 0.10, and stored GiB at 0.10, where lower values are preferred throughout. For full scans, throughput carries weight 0.60, GETs/GiB and stored GiB each carry 0.15, and \(p_{95}\) carries 0.10, with higher throughput preferred and lower values preferred for the remaining criteria.

League tables are ranked by the primary objective (slice: GM latency; full: throughput), with tie-breakers matching those in the Results section.

\subsection{Statistical methods}
Timings are positive and multiplicative, so we analyze $\ln(\text{time})$ per cell (format$\times$codec$\times$pattern).

Primary estimands are:
The primary estimands are geometric-mean (GM) time, reported with 95\% intervals on the log scale and back-transformed; tail latency ($p_{95}$), reported with 95\% intervals on the original scale; and full-scan throughput in GiB/s, computed from bytes divided by time and analyzed on the log scale with the same interval procedure. Bootstrap and sensitivity settings are given in Appendix \ref{app:a3-stats}.

Within each codec$\times$pattern, cross-format contrasts are reported as GM time \emph{ratios} versus Zarr and are \textbf{descriptive, session-conditional}. Diagnostics include Q–Q plots on $\ln(\text{time})$, lag-1 autocorrelation, and a run-order trend test (Appendix \ref{app:a2-run-qc}).

Per-session \gls{SThree} aggregates are used descriptively only; identifiers and statistics are listed in Appendix \ref{app:a4-metrics}. We do not average percentiles across sessions or attach inferential intervals to service metrics. Warm-up and replication policy are defined in Appendix \ref{app:a2-run-qc}.

For all between-format comparisons we treat the \emph{ratio of geometric means} as the primary effect size. For latency, this is the ratio of GM times between two formats on the original scale (for example, GM$_\text{ROOT}$/GM$_\text{Zarr}$), where values below~1 indicate that the numerator is faster. Because we analyse $\ln(\text{time})$, these ratios correspond to differences of means on the log scale. Empirically, response‑time distributions in computer systems are right‑skewed and often close to lognormal, so working on the log scale and reporting geometric means is standard in performance evaluation. For full scans, we use the ratio of GM throughputs in GiB/s (for example, GM$_\text{TileDB}$/GM$_\text{Zarr}$). Nonparametric effect sizes are reported as \emph{median ratios} in the robustness tables.

For each pair of formats within a codec $\times$ pattern, the statistical null is that their log‑scale means are equal (ratio of GMs = 1). The alternative is that the ratio differs from 1. Rather than performing formal tests, we present 95\% confidence intervals for the ratio and interpret them descriptively.

\subsection{Uncertainty in AWS}
\Gls{AWS} introduces time-varying latency and variance that cannot be fully controlled. We mitigated this issue by using a single region with the \gls{SThree} bucket co-located, a Gateway VPC endpoint, and fixed client settings. Operational controls and randomization are documented in Appendix \ref{app:a2-run-qc}. Formats were executed in \emph{separate sessions} with no cross-format overlap. Consequently, cross-format contrasts are \textbf{descriptive, session-conditional}. Inference is limited to within-cell estimands (GM, \gls{Pninetyfive}, throughput) with dependence-robust bootstrap \glspl{CI}. CloudWatch aggregates are per-session and reported descriptively (no inference, no cross-session averaging of percentiles).

Parquet was piloted in a single-object layout but excluded from the timed results due to high metadata open time and rapid object growth observed in the pilot runs. This pilot documents one concrete mapping of an $n$-D detector stack into a single Parquet object and should not be interpreted as a general performance statement about Parquet as a partitioned format family (Appendix \ref{app:a8-parquet}). The pilot and rationale are documented in Chapter \ref{ch:whatYouDid}, where Parquet is presented only qualitatively. Timed comparisons cover four formats: \gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{TTree}.



\section{Data Collection and Reproducibility}
\label{sec:methods-data-reprod}
This section specifies data sources, sampling, instrumentation, and release artifacts needed to rerun the experiments.

The data‐collection plan for this thesis centers on a single dataset built from 80 real seed frames and synthetically expanded to \(\sim\)\SI{20}{\gibi\byte} (\(\sim\)1{,}300 frames). These frames statistically replicate the size, structure, and access patterns of real synchrotron and neutron experiments. Generating the benchmark dataset from a small seed set reduces data sharing burden, and the synthesis procedure is deterministic given the same seeds and software versions (Appendix \ref{app:a7-synthesis}). We also release the raw timing logs and CloudWatch exports used for all reported statistics (Appendix \ref{app:a5b-availability}).
Dataset facts and size definitions are summarized in Appendix Table \ref{tab:dataset_facts}.

\subsection{Data Sources}
Detector stack (raw pixel payload $\sim$\SI{20}{\gibi\byte}): $N{=}1296$ \gls{CBF} frames at 16-bit depth derived from 80 seed frames from one experiment. One frame constitutes one sample and contains $2880\times2880$ pixel features (\(\sim\)\SI{15.82}{\mebi\byte} uncompressed). A jitter–noise routine perturbs intensity, offset, spatial shifts, and noise to synthesize the remaining frames (Appendix \ref{app:a7-synthesis}, Appendix Table \ref{tab:dataset_facts}).

\subsection{Sampling Strategy}
Two patterns were executed on the same dataset. For the slice workload, each run reads one randomly selected frame (\(\sim\)\SI{15.82}{\mebi\byte}) and each backend uses its native physical granularity, so a frame maps to different numbers of objects across formats. For the scanning workload, the entire $N$-frame dataset is read sequentially. Within-session run order was randomized with a fixed seed, and no cross-format concurrency occurred.

\subsection{Instrumentation and Metric Logging}
Full-scan time is measured from entering the scan read routine to completion of the scan with all data materialized/decoded by the client library; slice-read time is measured from entering the single-frame read routine until it returns a fully materialized frame. These timers include network transfer, decompression, and client decode, while log serialization is outside the timer. Throughput equals bytes divided by time. Accordingly, we record client start and stop timestamps together with bytes per run, per-session \gls{SThree} aggregates such as request counts, transferred bytes, and latency percentiles (identifiers and statistics in Appendix \ref{app:a4-metrics}), and \gls{SThree} sizes per format--codec combination for the compression calculations.

\subsection{Validity and Reliability Measures}
No explicit cache-clearing was performed between repetitions, so the reported latency and throughput results should be interpreted as \emph{warm, within-session} behavior rather than cold-open first-touch performance. Cache regime and replication policy are specified in Appendix \ref{app:a2-run-qc}.

\subsection{Reproducibility and availability}
Random seeds are fixed and logged with per-run timers, and CloudWatch aggregates are saved as \gls{JSON} with run IDs. The code and notebooks are released on GitHub at \url{https://github.com/CasperKristiansson/KTH-MSc-Thesis-Computer-Science}. The repository includes (i) seed frames under \texttt{Experiment/Base Data/} and the synthesis procedure (Appendix \ref{app:a7-synthesis}), and (ii) the raw measurement logs used to generate all reported tables and figures (\texttt{Experiment/Experiment Result/}). The full ingested \gls{SThree} dataset prefixes and the \gls{AWS} execution environment are not publicly hosted; rerunning timed experiments therefore requires re-provisioning comparable cloud resources and will reproduce the \emph{workflow} and analysis, not the exact wall-clock timings. Exact package versions and access paths are listed in Appendix \ref{app:a5-libraries}.

\section{Dataset and preprocessing}
All experiments used a single detector stack derived from 80 real \texttt{CBF} frames and expanded to a raw pixel payload of \(\sim\)\SI{20}{\gibi\byte} (\(N{=}1296\approx1{,}300\) frames; Appendix Table \ref{tab:dataset_facts}).

\subsection{Raw structure}
Each detector exposure is a dense two-dimensional frame. The specifications below fix the frame geometry, axis conventions, numeric encoding, byte size, and the theoretical versus empirically observed value range used for all subsequent ingestion and synthetic data generation.

\begin{itemize}
  \item Array shape per frame: $(2880, 2880)$.
  \item Axes: slow = rows, fast = columns (units: pixels).
  \item \texttt{dtype}: \texttt{uint16} (bit depth 16).
  \item Endianness: native little-endian.
  \item Per-frame size: \SI{16588800}{\byte} (\SI{15.82}{\mebi\byte}).
  \item Features per frame: $2880\times2880=8{,}294{,}400$ pixel intensities.
  \item Seed container: \gls{CBF} 1.5 with \texttt{x-CBF\_BYTE\_OFFSET} compression (header convention \texttt{PILATUS\_1.2}); decoded into \texttt{uint16} arrays before synthesis and ingestion.
  \item Value range (theoretical): $[0, 65535]$.
  \item Value range (observed, raw): $[0, 1199]$.
\end{itemize}

\subsection{Preprocessing and synthetic augmentation}
We started from $80$ raw \texttt{CBF} detector frames. Frames were enumerated in zero-based order; the naming convention \texttt{slice\_\{index\}.cbf} fixes the frame-index \,$\rightarrow$\, key mapping used later during ingestion. No resampling, normalization, or pixel edits were applied before augmentation.

\subsubsection{Augmentation method}
To scale the corpus for I/O benchmarking while preserving frame geometry and \texttt{uint16} encoding, additional frames were synthesized from the real frames using simple, distribution-preserving perturbations:

\begin{itemize}
  \item Intensity gain: multiply by $g\in[0.85,1.15]$.
  \item Local contrast scale around the frame mean: factor $c\in[0.9,1.1]$.
  \item Spatial jitter: with probability $0.8$, apply integer circular shifts up to $\pm16$\,px on each axis.
  \item Additive noise: with probability $0.9$, add zero-mean Gaussian noise with $\sigma\approx 20$ counts.
  \item Clip to $[0,65535]$ and cast back to \texttt{uint16}.
\end{itemize}

Random choices used fixed Python and NumPy seeds (Appendix \ref{app:a7-synthesis}). We targeted $N{=}1296$ frames (raw pixel payload \(\sim\)\SI{20.02}{\gibi\byte}; Appendix Table \ref{tab:dataset_facts}) by estimating average slice size and computing the required frame count. Outputs were written as \gls{CBF} frames and then uploaded to \gls{AWS} \gls{SThree} (implementation details in Appendix \ref{app:a7-synthesis}).

\section{Storage layouts, codecs, and objectization}
This section summarizes how the array was mapped to \gls{SThree} for each format.

\subsection{Common design and parity}
\begin{itemize}
  \item Logical array for all stores: $(N,2880,2880)$, $N{=}1296$, \texttt{uint16}.
  \item One frame per chunk/tile: $(1,2880,2880)$ to keep read units comparable.
  \item Codecs targeted: \texttt{gzip}, \texttt{lz4}, \texttt{zstd}. Parquet used only \texttt{gzip} and \texttt{lz4}.
  \item Frame enumeration: zero-based; source files named \texttt{slice\_\{index\}.cbf}.
  \item Concurrency: threaded frame loading; batch writes by contiguous index slices.
\end{itemize}


\subsection{HDF5 via HSDS}
\gls{HSDS} serves \gls{HDFfive} on the \gls{ECtwo} node, where we record domain paths, dataset geometry, chunking, and codec settings. \gls{HSDS} manages \gls{SThree} keys and metadata with one frame per chunk, preserving parity with other stores.

\textbf{Layout:}
\begin{itemize}
  \item Dataset: shape $(N,2880,2880)$, chunks $(1,2880,2880)$, \texttt{uint16}.
  \item Compression: \texttt{gzip}, \texttt{lz4}, or \texttt{zstd} at library default levels.
  \item Objectization: approximately one chunk object per frame plus \gls{HSDS} metadata/index objects.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item Frames were written in batches of $16$ into contiguous slices of the dataset using the \gls{HSDS} client.
  \item Host-level threading parallelized frame decoding and I/O (implementation details in Appendix \ref{app:a6-schemas}).
\end{itemize}

\subsection{Zarr on \texorpdfstring{\gls{SThree}}{S3}}
Zarr uses one chunk per frame where we record store paths, array geometry, chunking parity, codecs, and the write procedure.

\textbf{Layout:}
\begin{itemize}
  \item Array: shape $(N,2880,2880)$, chunks $(1,2880,2880)$, \texttt{uint16}.
  \item Compression: \texttt{gzip}, \texttt{zstd}, or \texttt{lz4} with moderate compression level ($\approx 3$).
  \item Metadata: default Zarr metadata files.
  \item Objectization: approximately one chunk object per frame plus metadata files.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item Frames were written in batches of $16$ as contiguous slices, with threaded frame loading.
\end{itemize}

\subsection{Apache Parquet on \texorpdfstring{\gls{SThree}}{S3} (single-object pilot)}
Frames were tabularized as rows with 2D rows as fixed-size lists. \textit{Note:} Parquet was piloted only in a single-object layout and is excluded from timed results due to an operational stop; see Appendix \ref{app:a8-parquet}.

\textbf{Layout:}
\begin{itemize}
  \item Files: one Parquet file per codec under a dedicated prefix.
  \item Schema: $2880$ columns \texttt{row\_0}\dots\texttt{row\_2879}, each \texttt{list<fixed\_size=2880, uint16>}.
  \item Row groups: one appended row per frame (writer defaults).
  \item Compression: \texttt{gzip} or \texttt{lz4}; dictionaries disabled.
  \item Objectization: single Parquet object per codec.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item For each frame, per-row arrays were assembled into a one-row table and appended to the Parquet file (Appendix \ref{app:a6-schemas}).
\end{itemize}

Parquet was implemented as a single file with $2880$ list-of-$2880$ \texttt{uint16} columns (\texttt{row\_0}\dots\texttt{row\_2879}), one appended row per frame, with \texttt{gzip} and \texttt{lz4} compression where dictionaries disabled.

\textbf{Observed during pilot:}
\begin{itemize}
  \item File size: a single Parquet object of $\sim$\SI{34}{\gibi\byte} for a $\sim$\SI{20}{\gibi\byte} raw stack.
  \item Metadata open: \SIrange{3}{4}{\minute} to load schema, footer, and column indexes on the \gls{ECtwo} test node; repeated attempts to load the \texttt{gzip} file led to instance crashes.
  \item Read smoke test: one frame decoded after metadata load; further timing runs were halted.
\end{itemize}

\textbf{Decision:}
\begin{itemize}
  \item Operational stop after an initial write and smoke read. Rationale: metadata load time and object size would make the full benchmark impractical within the experiment budget.
  \item Consequence: Parquet is omitted from timed latency/throughput results; artifacts are retained for transparency and discussed qualitatively in chapter \ref{ch:discussion}.
\end{itemize}

\subsection{TileDB dense array}
TileDB stores a dense array with frame-sized tiles and immutable fragments; this records the domain, filters, and fragment layout.

\begin{itemize}
  \item URIs: one TileDB array per codec under a dedicated prefix.
  \item Domain dims: \texttt{file: [0,N-1]}, \texttt{y: [0,2879]}, \texttt{x: [0,2879]}.
  \item Tile extents: $(1,2880,2880)$ (full-frame tiles).
\end{itemize}

\textbf{Filters:}
\begin{itemize}
  \item \texttt{gzip} (\texttt{level=3}), \texttt{lz4} (\texttt{level=3}), \texttt{zstd} (\texttt{level=3}) as attribute filter lists.
\end{itemize}

\textbf{Fragments and objectization:}
\begin{itemize}
  \item Writes executed in batches of $16$ frames per task; each task produced a fragment.
  \item Expected fragments: $\lceil N/16\rceil$.
  \item Each fragment contributes internal files (data, metadata, footers) under the array URI.
\end{itemize}

\subsection{ROOT / TTree}
\gls{ROOT} encodes all frames into a single file per codec; this notes the tree layout, compression, and access pattern.

\textbf{Tree layout:}
\begin{itemize}
  \item Files: one \gls{ROOT} file per codec under a dedicated prefix.
  \item \texttt{TTree} \texttt{img\_tree} with one branch \texttt{data} of length $2880\times2880$ \texttt{uint16}; one entry per frame.
\end{itemize}

\textbf{Compression:}
\begin{itemize}
  \item \texttt{gzip}: algorithm \texttt{kZLIB}, level $3$; \texttt{lz4}: \texttt{kLZ4} (default level); \texttt{zstd}: \texttt{kZSTD} (default level).
\end{itemize}

\textbf{Objectization:}
\begin{itemize}
  \item Single \gls{ROOT} object per codec. Selective reads use \gls{HTTP}/\gls{SThree} range-GETs into baskets/pages.
\end{itemize}

\subsection{RQ hooks (layouts)}
\begin{itemize}

  \item \textbf{RQ2 (full scans):} Fragmenting and page/cluster settings that enable long sequential reads.

\end{itemize}

\chapter{Results and Analysis}
\label{ch:resultsAndAnalysis}
This chapter reports the empirical results of benchmarking four storage backends on Amazon \gls{SThree}, \gls{HDFfive} via \gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{TTree} under two workload patterns on a single $\sim$20 GiB detector stack ($\sim$1{,}300 frames, \texttt{uint16}). \subsubsection{S3 object sizes and compression ratios}
\label{subsec:comp_ratio}
This section enumerates the total stored bytes on \gls{SThree} for each {format, codec} and reports compression ratios relative to the uncompressed array baseline. Stored bytes are computed by summing the sizes of all objects under the format–codec prefix (data and metadata files included). The compression baseline is the raw pixel payload of the logical array, not container files. Let $N$ be the number of frames. With frame shape $(2880,2880)$ and 16-bit depth, the baseline size is

\begin{equation}
\label{eq:compression_ratio}
  R_{f,c} \coloneqq \frac{B_{\text{raw}}}{B^{\text{stored}}_{f,c}},\qquad
  B_{\text{raw}} \coloneqq N \times 2880 \times 2880 \times 2 \text{bytes}.
\end{equation}

For $N=1{,}296$, $B_{\text{raw}}=21{,}499{,}084{,}800\ \text{bytes}$ ($\approx 20.02\,\text{GiB}$). Figure \ref{fig:stored_bytes} reports absolute stored size and Figure \ref{fig:compression_rates} shows the corresponding compression ratios.

Figure \ref{fig:stored_bytes} quantifies absolute stored size per format and codec. For this detector stack, zstd and gzip achieve similar total bytes across most backends, while LZ4 tends to store more data, particularly for HDF5/HSDS, TileDB, and ROOT; Zarr is the main exception, where LZ4 is slightly smaller than gzip. This pattern is consistent with codec choice, rather than format, being the dominant determinant of space usage for this workload.

\subsection{Request intensity and S3 service latencies}
We next summarize \gls{SThree} request behavior and service-side latencies to provide context for client timings. We report the number of GETs per session, per repetition, and per GiB. CloudWatch FirstByte/TotalRequest averages and $p_{95}$ are considered descriptive because they are aggregated, session-conditional metrics. Because these are session aggregates, we report \emph{point estimates only}.

\subsubsection{GETs per repetition and per GiB}
We summarize request intensity from CloudWatch \emph{session} aggregates. All $n$ timed runs in a cell (format$\times$codec$\times$pattern) contribute to one set of counts. Let $G$ be \texttt{GetRequestsSum} and $B$ be \texttt{BytesDownloadedSum}. Counts include \gls{SThree} \texttt{GET} only where \texttt{HEAD}/\texttt{LIST}/\texttt{PUT} are excluded. Warm-ups are excluded and separated temporally from the timed window.

\textbf{Per-repetition intensity}:
\begin{equation}
  \label{eq:gets_per_rep}
  \widehat{\lambda}_{\mathrm{rep}}=\frac{G}{n}.
\end{equation}

\textbf{Volume-normalized intensity}:
  \begin{equation}
  \label{eq:gets_per_gib}
  \widehat{\lambda}_{\mathrm{GiB}}=\frac{G\,2^{30}}{B}.
\end{equation}

Here $n$ is the number of timed repetitions in the cell, and $\widehat{\lambda}_{\mathrm{GiB}}$ is measured in GETs per GiB.

Rates are descriptive and session-conditional. Table \ref{tab:req_intensity} lists $\widehat{\lambda}_{\mathrm{rep}}$ and $\widehat{\lambda}_{\mathrm{GiB}}$ for all \{format, codec, pattern\} cells. Figure \ref{fig:reqintensity_box_by_format} summarizes \gls{SThree} request intensity by format, showing the distributions of GETs per repetition and GETs per GiB aggregated across codecs and access patterns. For this workload, Zarr and TileDB cluster toward lower GETs/GiB than HDF5/HSDS, indicating fewer requests for the same volume of data, while ROOT consistently has very low GETs/GiB because it serves from a single object. These differences are used as descriptive context for later latency and throughput patterns, together with layout and codec effects. Detailed per-cell point estimates by codec and pattern are provided in Appendix Figures \ref{fig:reqintensity_perRep_grid} and \ref{fig:reqintensity_perGiB_grid}.

\begin{itemize}

\section{Answers to the research questions}
\label{sec:discussion-bottomline}
This section reports winners by workload and codec, using GM latency (slices) and GM throughput (full scans) with dependence-robust 95\% \glspl{CI} and $p_{95}$ for tail risk. All contrasts are \emph{descriptive} and \emph{session-conditional}.

\subsection{Answer to RQ1 — Interactive slice latency}
\label{sec:ans-rq1}
Single-frame reads have two stress areas: (i) layout/objectization, which sets how many objects and round–trips each request touches, and (ii) decode cost, which depends on the codec and the library path. RQ1 and hypotheses H1.1–H1.3 (Section \ref{sec:methods-hypotheses}) ask how these factors shape slice-level GM latency and $p_{95}$. We judge the winners by geometric mean (GM) latency with dependence-robust 95\% \glspl{CI} and use $p_{95}$ to flag tail risk. The references below point to the slice tables and figures for each codec.

\textbf{Zarr is the fastest in terms of GM slice latency} for \texttt{zstd} in this dataset. Its GM \gls{CI} lies fully below TileDB’s, which is second, followed by \gls{HDFfive}/\gls{HSDS} and then \gls{ROOT}. The $p_{95}$ ordering mirrors the center, indicating Zarr combines a fast typical latency with controlled tails. Mechanistically, this matches a chunk–per–frame layout that amortizes \gls{SThree} RTT via client concurrency, while \texttt{zstd} keeps the decode cost moderate. See Table \ref{tab:slice_zstd_mbb} and Figures \ref{fig:slice_zstd_gm_mbb}, \ref{fig:slice_zstd_p95_mbb}, \ref{fig:slice_zstd_ratios_point}. GM deltas show that Zarr is $\approx 12\%$ faster than TileDB (Table \ref{tab:slice_zstd_mbb}). Together, the three codecs confirm H1.1–H1.2: chunked/fragmented formats consistently beat ROOT on GM latency, Zarr leads for \texttt{zstd} and \texttt{lz4}, and TileDB leads for \texttt{gzip}.

\textbf{Zarr remains fastest on GM latency} under \texttt{lz4}. \textbf{TileDB and \gls{HDFfive}/\gls{HSDS} are close} behind it, with overlapping \glspl{CI} between those two, and \gls{ROOT} is slowest. A trade–off appears in the tails: Zarr’s $p_{95}$ is higher and has wider CIs than TileDB and \gls{HDFfive}/\gls{HSDS}, consistent with \texttt{lz4}’s bias toward decode speed over compactness. If an application is strongly tail–sensitive, TileDB’s lower and more stable $p_{95}$ may offset its slightly higher GM. See Table \ref{tab:slice_lz4_mbb} and Figures \ref{fig:slice_lz4_gm_mbb}, \ref{fig:slice_lz4_p95_mbb}, \ref{fig:slice_lz4_ratios_point}. GM deltas show that Zarr is $\approx 18\%$ faster than TileDB and $\approx 21\%$ faster than \gls{HDFfive}/\gls{HSDS} (Table \ref{tab:slice_lz4_mbb}). This supports H1.1 and H1.2 for \texttt{lz4}: Zarr is the fastest layout on GM latency, while TileDB and HDF5/HSDS sit close behind, and ROOT remains clearly slower.

\textbf{TileDB wins} \texttt{gzip} slices with non-overlapping GM \glspl{CI} versus Zarr. Zarr is next and outperforms \gls{HDFfive}/\gls{HSDS}, where \gls{ROOT} again is slowest by a wide margin. This pattern aligns with \texttt{gzip}’s higher \gls{CPU} cost, which leads to TileDB’s fewer, larger fragments reducing request overhead enough to compensate for \texttt{gzip} decode, while Zarr’s per–frame objects incur more round–trips. Ordering is consistent in $p_{95}$ and in the Zarr–referenced ratio view. See Table \ref{tab:slice_gzip_mbb} and Figures \ref{fig:slice_gzip_gm_mbb}, \ref{fig:slice_gzip_p95_mbb}, \ref{fig:slice_gzip_ratios_point}. GM deltas show that TileDB is $\approx 17\%$ faster than Zarr (Table \ref{tab:slice_gzip_mbb}). These gzip/slice results are consistent with H1.1 (all chunked/fragmented layouts are faster than ROOT) and with H1.2’s expectation that TileDB’s fragment layout can win under \texttt{gzip} by reducing request fan-out.

Across codecs in this dataset, the winner patterns align with evidence of request intensity: lower GETs/GiB contributes, but does not predict slice latency across formats; object size, parallelism, and decode paths matter. At the same time, \gls{ROOT}’s single–object layout shows that “few GETs” does not guarantee speed, because paging and decode path overhead dominate. See Figure \ref{fig:cross_slice_latency_vs_gets} and Table \ref{tab:cross_slice_latency_vs_gets}.

Nonparametric summaries reproduce the same slice rankings by codec, and Harrell–Davis $p_{95}$ with an $\ell$–grid preserves ordering, including the heavier tails for \texttt{lz4}/Zarr. See Figure \ref{fig:np_slice_ratios_grid} and Tables \ref{tab:np_slice_gzip_median}, \ref{tab:np_slice_lz4_median}, \ref{tab:np_slice_zstd_median}, and the tail–sensitivity artifacts in Figure \ref{fig:tail-slice-p95-hd-ci-vs-L} and Tables \ref{tab:tail-slice-gzip-p95-selected}–\ref{tab:tail-slice-zstd-p95-selected}. Throughout this chapter, such “consistency” language refers to agreement in the \emph{ordering of central tendencies} (GM and median) across formats. It does not mean that every GM estimate is exact, especially in more variable cells such as \texttt{lz4} slices for Zarr and TileDB, where the CIs for means and tails are comparatively wide.

\subsection{Answer to RQ2 — Full-dataset throughput}
\label{sec:ans-rq2}
Full–dataset reads test sustained sequential delivery and decode under continuous concurrency. RQ2 and hypotheses H2.1–H2.3 (Section \ref{sec:methods-hypotheses}) focus on GM throughput (GiB/s) with dependence–robust 95\% \glspl{CI} derived from GM time on the log scale, and use $p_{95}$ times to check stability. All cross–format contrasts are \emph{descriptive} and \emph{session–conditional}. Across \texttt{zstd}, \texttt{lz4}, and \texttt{gzip}, \textbf{TileDB leads by a wide margin}, \textbf{Zarr is consistently second}, and \textbf{\gls{HDFfive}/\gls{HSDS} and \gls{ROOT} come last}.

Effect sizes vs Zarr show that TileDB is $\approx$3.16$\times$ faster under \texttt{gzip} (11{,}254 ms vs 35{,}598 ms), $\approx$2.17$\times$ under \texttt{lz4} (13{,}602 ms vs 29{,}483 ms), and $\approx$2.92$\times$ under \texttt{zstd} (10{,}384 ms vs 30{,}365 ms), see Table \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}.

Under \texttt{zstd}, \textbf{TileDB is the clear throughput leader.} Zarr is a distant second, and \gls{HDFfive}/\gls{HSDS} and \gls{ROOT} are far behind. GM time and its \gls{CI} show clean separation, and the ratio view reinforces TileDB’s advantage. $p_{95}$ times follow the same ordering and are far apart in magnitude, particularly between TileDB/Zarr and \gls{ROOT}, which supports the same qualitative throughput ordering for both center and tail in this dataset. See Table \ref{tab:full_zstd_mbb} and Figures \ref{fig:full_zstd_gm_mbb}, \ref{fig:full_zstd_p95_mbb}, \ref{fig:full_zstd_ratios_point}. These full-scan results across codecs support H2.1 (TileDB $>$ Zarr $>$ HDF5/HSDS $>$ ROOT on GM throughput) and H2.2 (both \texttt{lz4} and \texttt{zstd} improve throughput relative to \texttt{gzip} for our throughput metric (downloaded bytes/time)).

Under \texttt{lz4}, \textbf{TileDB remains first and Zarr second.} Faster decode narrows absolute times but does not change ranks. \Gls{HDFfive}/\gls{HSDS} and \gls{ROOT} stay well behind. $p_{95}$ CIs are relatively tight for TileDB and Zarr compared with the gap to \gls{ROOT}, which supports the qualitative picture of TileDB as the highest-throughput format and Zarr second for this workload. See Table \ref{tab:full_lz4_mbb} and Figures \ref{fig:full_lz4_gm_mbb}, \ref{fig:full_lz4_p95_mbb}, \ref{fig:full_lz4_ratios_point}.

Under \texttt{gzip}, \textbf{TileDB still leads and Zarr is second.} \texttt{gzip}’s higher \gls{CPU} cost lifts absolute times for all formats, but ordering is unchanged. \Gls{HDFfive}/\gls{HSDS} and \gls{ROOT} remain the slowest. $p_{95}$ point estimates are ordered in the same way as the GMs, so tail summaries do not contradict the GM-based throughput ordering. See Table \ref{tab:full_gzip_mbb} and Figures \ref{fig:full_gzip_gm_mbb}, \ref{fig:full_gzip_p95_mbb}, \ref{fig:full_gzip_ratios_point}.

In these experiments, throughput patterns align with request intensity and layout: TileDB attains high throughput with moderate GETs/GiB, thanks to fragment–backed long reads. Zarr has higher GETs/GiB yet parallelizes effectively, whereas \gls{HDFfive} via \gls{HSDS} shows higher GETs/GiB but poorer streaming performance. \Gls{ROOT} has few GETs/GiB but still has low throughput because its single–object layout and paging/decode overhead dominate. See Figure \ref{fig:cross_full_throughput_vs_gets} and Table \ref{tab:cross_full_throughput_vs_gets}.

CloudWatch FirstByte and TotalRequest latencies are stable within sessions and do not reflect the large cross–format gaps in client timings, where the dominant drivers are layout and decode rather than differences in \gls{SThree} service timing. See Figures \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}.

Nonparametric centers yield the same ranks across codecs, and the HD $p_{95}$ sensitivity maintains the ordering. See Figure \ref{fig:np_full_ratios_grid} and Tables \ref{tab:np_full_gzip_median}, \ref{tab:np_full_lz4_median}, \ref{tab:np_full_zstd_median}, see also Figure \ref{fig:tail-full-p95-hd-ci-vs-L} and Tables \ref{tab:tail-full-gzip-p95-selected}–\ref{tab:tail-full-zstd-p95-selected}.

\subsection{RQ3 — Cost posture and mechanisms (summary)}
\label{sec:ans-rq3}
Chunk/fragment layouts (Zarr, TileDB) produce low–to–moderate GETs/GiB and are associated with lower GM slice latency and higher scan throughput in this dataset. In contrast, \gls{HSDS} yields higher GETs/GiB, and \gls{ROOT} is the counterexample: few GETs yet slow due to single-object paging and decode (Section \ref{sec:rq3-results}; Figures \ref{fig:cross_slice_latency_vs_gets}, \ref{fig:cross_full_throughput_vs_gets}). Storage posture is codec-driven overall (zstd $\approx$ gzip $<$ lz4), with a significant inflation for \texttt{lz4}+\gls{HSDS} compared with Zarr/TileDB at the same payload (Table \ref{tab:object_counts}, Figure \ref{fig:stored_bytes}, Figure \ref{fig:compression_rates}). \gls{SThree} FirstByte/TotalRequest latencies are stable across sessions and do not explain cross-format gaps; they serve as context only (Figure \ref{fig:cw_firstbyte_grid}, Figure \ref{fig:cw_total_grid}). Mechanistically, objectization determines request patterns, and the codec defines the bytes transferred together; these factors are consistent with the client timings observed in \ref{sec:rq1-results}–\ref{sec:rq2-results}.

These findings address H3.1–H3.2: codec choice (especially \texttt{lz4} vs \texttt{zstd}/\texttt{gzip}) dominates stored GiB, Zarr and TileDB offer a more favorable request+storage posture than HSDS+\texttt{lz4} or ROOT, and the relatively flat CloudWatch service latencies confirm that \gls{SThree} service timing is a background factor rather than a primary driver of client-observed performance.


\section{RQ3 interpretation: mechanisms and cost posture}
\label{sec:discussion-mechanisms-cost}
We explain the observed rankings by linking objectization and GETs per GiB to client timings. CloudWatch service latencies are treated as context, where codec trade-offs and request and storage posture complete the picture.

\subsection{Mechanisms explaining outcomes}
This section explains \emph{why} the observed orderings occur. We link layout-driven objectization and request intensity (GETs/GiB) to client timings, show that \gls{SThree} service latencies are stable and not causal, and summarize codec \gls{CPU}–bytes trade-offs. In this experiment, request intensity contributes to performance within chunked and fragmented stores, but it does not fully predict outcomes: lower GETs/GiB often coincides with higher full-scan throughput and can coincide with lower slice GM latency, yet cases like TileDB vs Zarr show that object size, parallelism, and decode paths can dominate even when GETs/GiB is lower (Figures \ref{fig:cross_slice_latency_vs_gets}, \ref{fig:cross_full_throughput_vs_gets}; Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets}).

\subsubsection{Objectization and layout}
Objectization for each storage backend determines the request pattern. Zarr/\gls{HSDS} materializes roughly one data object per frame (plus metadata), TileDB writes a small number of immutable fragments (each with internal files), and \gls{ROOT}/\gls{TTree} stores a single large object. Per–frame layouts expose more opportunities for client concurrency, fragment layouts trade fewer objects for long sequential reads, and single–object layouts minimize GET count but constrain parallelism to range requests within one key. This matches the data in Table \ref{tab:object_counts} and Figure \ref{fig:object_counts}. In practice, concurrency benefits Zarr and TileDB, while \gls{ROOT} shows few GETs but slow performance because paging and decoding dominate once request latency is amortized.

\subsubsection{Request intensity vs client timing}
In this experiment, lower request intensity is associated with better client outcomes in both chunked and fragmented stores. Fewer GETs/GiB are associated with lower slice GM and higher full-scan throughput for Zarr and TileDB (Figure \ref{fig:cross_slice_latency_vs_gets}, Figure \ref{fig:cross_full_throughput_vs_gets}, Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets}). The pattern is not universal: \gls{ROOT} has very low GETs/GiB yet poor latency and throughput because the single-object layout, small pages, and decode costs limit effective parallelism. GETs/GiB is one factor, but does not predict latency across formats; object size, parallelism, and decode path matter, with layout and decode paths accounting for the rest. These observations are consistent with H1.3: lower GETs/GiB aligns with lower GM slice latency for Zarr and TileDB, while ROOT violates the monotonic trend by combining few GETs with poor latency due to paging and decode overhead.

\subsubsection{Service latencies are not the driver}
CloudWatch \emph{FirstByteLatency} and \emph{TotalRequestLatency} are stable within sessions (both averages and $p_{95}$) and do not track the large cross–format gaps in client timings. The dominant factors are request pattern and decode path rather than “faster \gls{SThree}.” These metrics provide context, not causal evidence (Figures \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\subsubsection{Codec effects}
Codecs trade \gls{CPU} for bytes. \texttt{lz4} minimizes decode time and helps latency where per–chunk \gls{CPU} dominates. \texttt{zstd} strikes a balance between compression and decoding, while \texttt{gzip} yields the smallest stored size but is slower to decode. Stored size is primarily codec–driven (typically \texttt{zstd}\,$\approx$\,\texttt{gzip}\,$<$\,\texttt{lz4}), but format deltas are large under \texttt{lz4}: in our data, \gls{HDFfive} via \gls{HSDS} stored 19.17\,GiB vs Zarr 10.40\,GiB and TileDB 15.56\,GiB (Table \ref{tab:object_counts}, Figures \ref{fig:stored_bytes}, \ref{fig:compression_rates}). \texttt{lz4}+\gls{HSDS} should therefore be treated as storage-heavy. These trade–offs align with the winners in Section \ref{sec:discussion-bottomline} where Zarr leads \texttt{zstd}/\texttt{lz4} slices while TileDB leads \texttt{gzip} slices (Tables \ref{tab:slice_zstd_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_gzip_mbb}). TileDB dominates full-scan throughput across codecs (Tables \ref{tab:full_zstd_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_gzip_mbb}).

As summarized in Figure \ref{fig:codec_summary}, zstd consistently achieves lower or comparable latency and higher throughput than gzip at similar compression ratios. At the same time, LZ4 reduces latency further at the cost of substantially higher storage, especially for HDF5/HSDS. This matches the codec trade-offs described above.

Across formats, zstd consistently outperforms gzip on both slice latency and full-scan throughput, while achieving similar compression ratios (Figure \ref{fig:compression_rates}). LZ4 reduces slice latency further but provides a slight throughput advantage over zstd and incurs noticeably larger stored size, especially for HDF5/HSDS (Figure \ref{fig:stored_bytes}). For this detector stack, this supports choosing zstd as a default codec when both storage and latency matter, with LZ4 reserved for latency-only scenarios and gzip primarily for legacy compatibility.

\subsection{Cost and storage posture}
Stored size is mostly codec-driven, but \texttt{lz4} shows substantial format variation (\gls{HSDS} 19.17\,GiB vs Zarr 10.40\,GiB vs TileDB 15.56\,GiB, see Table \ref{tab:object_counts}). For compact storage, prefer \texttt{zstd} or \texttt{gzip} and avoid \texttt{lz4}+\gls{HSDS} unless storage is unconstrained.

\textbf{Request cost proxy.} For slice-heavy workloads, watch \emph{GETs/GiB}. In this experiment, \textbf{TileDB} and \textbf{Zarr} deliver lower GETs/GiB at competitive or better latency than \textbf{\gls{HDFfive}/\gls{HSDS}}. This indicates a more favorable request-cost posture at equal performance. See Table \ref{tab:cross_slice_latency_vs_gets} and Figure \ref{fig:cross_slice_latency_vs_gets}.

\textbf{Storage cost proxy.} Stored size is mainly \emph{codec-driven}, where \texttt{zstd} and \texttt{gzip} compress more than \texttt{lz4}. Between-format differences at a fixed codec are small and are consistent with additional layout metadata rather than payload differences. See Figures \ref{fig:stored_bytes}, \ref{fig:compression_rates}.

\textbf{Counterexample.} \textbf{\gls{ROOT}} shows that a few requests do not imply speed or efficiency. It has the lowest \emph{GETs/GiB} yet poor slice latency and scan throughput due to single-object paging and decode overhead. See Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets} and the per-codec MBB results (slices: Tables \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb} and full scans tables \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}).


\section{Threats to validity and limits}
\label{sec:threats-validity}
We test whether conclusions hold under alternative centers and dependence. We check shape and serial dependence, confirm medians, and probe tails with the Harrell-Davis estimator.

\subsection{Distribution shape and robustness}
We verify that the modeling choices are appropriate and yield results similar to those of other estimators. We assess shape and serial dependence to justify log–time analysis with the moving–block bootstrap (MBB), then confirm rankings with median centers, and finally test tail stability with Harrell–Davis $p_{95}$.

\subsubsection{Shape and dependence}
Log–time is appropriate, and serial dependence is present. The diagnostics table shows frequent non-normality in the raw time series and improved behavior in $\ln(\text{time})$, while often positive lag-1 autocorrelation is observed across all cells. This both motivates analyzing centers on the log scale and using MBB \glspl{CI} that respect dependence (Appendix Table \ref{tab:timing_diag_main}). Q–Q grids on $\ln(\text{time})$ support the transformation, and run-order traces and the Spearman drift diagnostic indicate that some cells exhibit monotonic run-order trends (Appendix Table \ref{tab:timing_diag_main}); we therefore interpret MBB intervals as dependence-robust, session-conditional summaries of the timed window, not as formal inference under strict stationarity (Appendix Figures \ref{fig:appendix_qq_grid_slice}, \ref{fig:appendix_qq_grid_full}, \ref{fig:appendix_drift_grid_slice}, \ref{fig:appendix_drift_grid_full}). Together, these justify GM on log–time with dependence-robust \glspl{CI}.

\subsubsection{Center robustness}
Median-based rankings match GM across codecs and patterns. Descriptive median ratios reproduce the slice and full-scan orderings, and rank-agreement tables show identical ranks to GM within each codec (Figures \ref{fig:np_slice_ratios_grid}, \ref{fig:np_full_ratios_grid} and Tables \ref{tab:np_slice_gzip_median}, \ref{tab:np_slice_lz4_median}, \ref{tab:np_slice_zstd_median}, \ref{tab:np_full_gzip_median}, \ref{tab:np_full_lz4_median}, \ref{tab:np_full_zstd_median}, and \ref{tab:np_slice_gzip_rank}, \ref{tab:np_slice_lz4_rank}, \ref{tab:np_slice_zstd_rank}, \ref{tab:np_full_gzip_rank}, \ref{tab:np_full_lz4_rank}, \ref{tab:np_full_zstd_rank}). Thus, when we describe rankings as “consistent” across estimators, this refers to the relative ordering of formats, not to low variance or narrow CIs for every GM estimate.

\subsubsection{Tail robustness}
Orderings are stable under Harrell–Davis $p_{95}$ with an $\ell\in\{4,6,8,10\}$ block-length grid, where we report the widest dependence-robust \gls{CI} per cell. The notable exception is \texttt{lz4}/Zarr, which shows heavier tails relative to its peers, but this does not overturn the winner hierarchy established by GM and median centers (Figures \ref{fig:tail-slice-p95-hd-ci-vs-L}, \ref{fig:tail-full-p95-hd-ci-vs-L} and Tables \ref{tab:tail-slice-gzip-p95-selected}, \ref{tab:tail-slice-lz4-p95-selected}, \ref{tab:tail-slice-zstd-p95-selected}, \ref{tab:tail-full-gzip-p95-selected}, \ref{tab:tail-full-lz4-p95-selected}, \ref{tab:tail-full-zstd-p95-selected}).

\subsection{Validity and limits}
We state what the measurements support and where they do not generalize. Internal checks and external scope are made explicit so readers interpret results correctly.

\subsubsection{Internal checks}
All planned runs were completed without failure, and warm-ups were excluded by design. Run order was randomized with a fixed seed. Serial dependence is handled via the moving-block bootstrap, and the log-time choice is supported by shape diagnostics (Section \ref{sec:run-inclusion-and-coverage} and Appendix Table \ref{tab:timing_diag_main}).

\subsubsection{External validity}
Findings reflect an \gls{AWS}-only setup (\gls{SThree} + \gls{ECtwo} + CloudWatch) using one \gls{SThree} bucket in a single region (\texttt{eu-north-1}) and a single \gls{ECtwo} client, with two access patterns and three codecs. No multi-client contention, cross-region traffic, or non-\gls{AWS} object stores were evaluated; performance and cost posture may differ on Azure Blob Storage, Google Cloud Storage, or on-premises \gls{SThree}-compatible systems. We do not include an on-premises baseline (e.g., Lustre/\gls{GPFS} or POSIX file I/O), so results should be interpreted as \emph{within-\gls{SThree}} cross-format comparisons rather than cloud-versus-\gls{HPC} claims. The dataset size is sufficient to expose request/metadata overheads for the tested workloads, but it does not establish asymptotic behavior at multi-terabyte or petabyte scale. Cross-format contrasts are \emph{descriptive} and \emph{session-conditional}. CloudWatch service metrics are used solely for descriptive context, not as causal evidence (Figures \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\section{Deviations and exclusions}
Parquet was piloted only and excluded from timed comparisons. When we scaled to complete ingestion and attempted full-dataset scans, a single large object (\(\sim\)34\,GiB for a \(\sim\)20\,GiB raw stack) incurred 3–4 min metadata open time and intermittent client instability on the \texttt{gzip} file, making it unsuitable for frame-granularity reads and unattractive even for bulk scans in this setup. The root cause is objectization and file semantics: a single-object, columnar Parquet file offers few opportunities for request-level parallelization and concentrates footer/metadata work at open. We therefore retain Parquet as a qualitative caution for $n$-D image stacks on \gls{SThree} single-object layouts and exclude it from quantitative timing (Chapter \ref{ch:resultsAndAnalysis}). This evidence is limited to the tested single-object layout and should not be generalized to partitioned Parquet datasets with tuned file and row-group sizing (data-lake style); evaluating such variants was out of scope.

\chapter{Conclusions and Future Work}
\label{ch:conclusionsAndFutureWork}
Zarr yields the lowest slice latency under \texttt{zstd} and \texttt{lz4}, where TileDB wins slices under \texttt{gzip}. TileDB completes full sequential scans $2.2$--$3.2\times$ faster (lower GM scan time) than Zarr across codecs, with stable tails. \Gls{ROOT} remains slow for frame‑random reads despite a few GETs.

Layout and request behavior explain the backend differences. Per-frame objectization (Zarr, \gls{HDFfive} via \gls{HSDS}) and fragment layouts (TileDB) expose client concurrency, whereas a single-object layout (\gls{ROOT}) minimizes GETs but constrains parallelism and incurs paging/decode overhead. Codec choice trades \gls{CPU} for bytes, with \texttt{zstd} and \texttt{gzip} more compact than \texttt{lz4}. In our data \gls{HDFfive} via \gls{HSDS} with \texttt{lz4} stored 19.17\,GiB versus Zarr 10.40\,GiB and TileDB 15.56\,GiB at the same payload size, indicating a storage-heavy configuration.

Winners are judged by geometric-mean (GM) latency for slices and GM throughput for full scans with dependence-robust 95\% \glspl{CI} and Harrell–Davis $p_{95}$ for tails. Findings reflect an \gls{AWS}-only \gls{SThree} testbed on one region (eu-north-1) and one client, with no on-prem baseline; claims should be read as within-\gls{SThree} cross-format contrasts. CloudWatch service latencies are used as context, not causal drivers.

Conclusions map to RQ1–RQ3 and reference Chapter \ref{ch:resultsAndAnalysis} (sections \ref{sec:rq1-results}, \ref{sec:rq2-results}, \ref{sec:rq3-results}).

\section{Closing synthesis}
Across single-frame slices and full scans, summaries of central tendency (GM and median) show a consistent, session-conditional ordering. For slices, \textbf{Zarr} is fastest under \texttt{zstd} and \texttt{lz4}, while \textbf{TileDB} wins under \texttt{gzip}. \textbf{\gls{HDFfive}/\gls{HSDS}} is slower than Zarr and TileDB but substantially faster than \textbf{\gls{ROOT}}, which is slowest. For full scans, \textbf{TileDB} delivers the highest throughput across all codecs by a wide margin, with \textbf{Zarr} second and \textbf{\gls{HDFfive}/\gls{HSDS}} and \textbf{\gls{ROOT}} far behind. Mechanisms include objectization/request patterns and decode paths: per-frame objects (Zarr/\gls{HSDS}) and fragments (TileDB) enable client concurrency. In contrast, a single object (\gls{ROOT}) minimizes GETs but limits parallelism and pays paging/decode overhead. In this dataset, \emph{few GETs} therefore does not imply speed, which can be seen in the cross-metric views (\ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets}). Cost properties follow: request cost tracks GETs/GiB (important for slice-heavy use), while stored GiB is codec-driven in our measurements (\texttt{zstd}$\approx$\texttt{gzip} $<$ \texttt{lz4}). For workloads similar to this detector stack, these results suggest choosing \texttt{zstd} or \texttt{gzip} when storage dominates and \texttt{lz4} when \gls{CPU}/latency dominates. If one backend must serve both interactive slices and bulk scans, start with \emph{Zarr+\texttt{zstd}} for UI latency, accepting lower scan throughput. However, if scans dominate, choose \emph{TileDB+\texttt{zstd}} and keep frame‑aligned tiles.

\section{Practitioner choices (decision matrix hook)}
This section turns the empirical rankings into concrete decisions. Choices are related to the primary objective of each workload. All evidence is descriptive and session–conditional, and ties back to the league tables and per–codec slice/full results.

\subsection{RQ1 — Interactive slice latency (latency–first)}
For random single-frame reads, the default recommendation is \emph{Zarr + \texttt{zstd}}, which delivers the lowest slice GM with controlled tails in this setting and scales well with client concurrency (Tables \ref{tab:league-slice-zstd}, \ref{tab:slice_zstd_mbb}). If \texttt{gzip} is mandated, \emph{TileDB + \texttt{gzip}} is the better choice because TileDB’s fragment layout offsets \texttt{gzip}’s \gls{CPU} cost and wins on GM with non-overlapping \glspl{CI} versus Zarr (Tables \ref{tab:league-slice-gzip}, \ref{tab:slice_gzip_mbb}). One caution is that \emph{\gls{HSDS}+\texttt{lz4}} becomes unattractive when storage cost matters, since it stored 19.17\,GiB compared with Zarr’s 10.40\,GiB at the same codec (Table \ref{tab:object_counts}). By contrast, \emph{\gls{ROOT}} should be avoided for frame-random reads: few GETs do not translate into low latency when paging and decode dominate (Tables \ref{tab:league-slice-gzip}, \ref{tab:league-slice-lz4}, \ref{tab:league-slice-zstd} and Tables \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb}).

\subsection{RQ2 — Full-dataset throughput (throughput–first)}
For full-dataset scans, the default recommendation is \emph{TileDB + \texttt{zstd}}. TileDB dominates full-scan performance across codecs in this testbed, and \texttt{zstd} provides the best overall scan time while keeping the stored footprint compact. \emph{TileDB + \texttt{lz4}} is worth considering only if the scan becomes CPU-bound in a deployment where the larger stored size and downloaded bytes are acceptable (Tables \ref{tab:league-full-zstd}, \ref{tab:league-full-lz4} and Tables \ref{tab:full_zstd_mbb}, \ref{tab:full_lz4_mbb}). When ecosystem fit matters more than maximizing throughput, \emph{Zarr} remains the second choice across \texttt{zstd}, \texttt{lz4}, and \texttt{gzip}, trading some scan speed for broader tooling while preserving stable streaming behavior (Tables \ref{tab:league-full-gzip}, \ref{tab:league-full-lz4}, \ref{tab:league-full-zstd} and Tables \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}).

\subsection{Weight sensitivity}
Top selections remain stable under the stated weights, as the selected weights do not alter the winners in our data. Where near-ties appear within a codec×pattern bucket, we call them out in the league tables and recommend using the tie-breakers (slice: $p_{95}\!\rightarrow$ GETs/GiB $\rightarrow$ stored GiB and for full scan GM time $\!\rightarrow$ GETs/GiB $\rightarrow$ stored GiB). See the score tables (\ref{tab:scores-slice-gzip}, \ref{tab:scores-slice-lz4}, \ref{tab:scores-slice-zstd}, \ref{tab:scores-full-gzip}, \ref{tab:scores-full-lz4}, \ref{tab:scores-full-zstd}).


\section{Operational implications}
This section converts the Results into backend-specific operational actions. Recommendations cover metadata consolidation, prefix sharding, chunk/tile sizing, fragment consolidation, cache tuning, and read-page batching. Measured object counts justify each item, GETs/GiB, and $p_{95}$ tails.

\subsection{Zarr}
\textbf{Consolidate metadata} to cut LIST/HEAD fan-out and reduce cold-open overhead; unconsolidated layouts inflate object count and amplify per-request latency (Figure \ref{fig:object_counts}). Use stable, logical key naming; S3 no longer requires randomizing prefixes for performance. Only introduce additional prefix sharding if you need to scale very high request rates through parallelism and to keep operational grouping manageable as datasets grow. \textbf{Keep frame–sized chunks} \((1,\cdot,\cdot)\) for frame–granularity reads and adjust only if the access unit changes. \textbf{Monitor tails on \texttt{lz4}}: slice \(p_{95}\) is heavier for Zarr+\texttt{lz4}; prefer \texttt{zstd} for tighter latency envelopes or mitigate with concurrency and consolidated metadata (Figure \ref{fig:slice_lz4_p95_mbb}, Figure \ref{fig:object_counts}).

\subsection{TileDB}
\textbf{Manage fragment counts}: each write produces an immutable fragment, where many small fragments raise metadata work. Schedule \textbf{fragment consolidation} when counts grow to keep open/scan overhead low (Table \ref{tab:object_counts}). \textbf{Align tile extents} to the access unit (frame–aligned tiles for these arrays) to preserve long sequential reads. These practices sustain \textbf{scan dominance} observed across codecs (Figures \ref{fig:full_gzip_gm_mbb}, \ref{fig:full_lz4_gm_mbb}, \ref{fig:full_zstd_gm_mbb}) and the favorable throughput vs GETs/GiB posture (Figure \ref{fig:cross_full_throughput_vs_gets}).

\subsection{HSDS (HDF5)}
\textbf{Account for REST fan–out} and \textbf{many small objects}: chunk and metadata requests add round–trips (Table \ref{tab:object_counts}). Provision and tune \textbf{server–side caches} (dataset/chunk caches) and concurrency to hide latency, and right-size chunks to reduce request pressure where feasible. CloudWatch service latencies are stable across sessions, so speedups must come from reducing fan–out or improving caching, not from “faster \gls{SThree}” (Figures \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\subsection{ROOT/TTree}
\textbf{Batch page reads} and \textbf{avoid per–frame random access}: issue ranged reads and increase read windows so many small pages are fetched together. Prefer workflows that \textbf{scan clusters} over frame–random access for images. Remember that \textbf{few GETs do not imply speed}: single–object layout plus paging/decode keeps latency high despite low GETs/GiB (Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb}).


\section{Future work}
This section highlights the highest-leverage uncertainties revealed by the results and frames them as follow-up studies that either de-risk tail behavior or generalize the findings beyond a single dataset, region, or client.

Several follow-up directions emerge directly from the mechanisms observed here. One is to study multi-client scaling and cache effects for \gls{HSDS} and Zarr, so their impact on GM and $p_{95}$ under contention can be measured explicitly. Another is to evaluate consolidation strategies, specifically Zarr metadata consolidation and TileDB fragment consolidation, and relate them to GETs/GiB, open time, and tail behavior. The experimental matrix should also be widened to include additional codecs and filters such as Snappy, bitshuffle{+}\gls{ZSTD} levels, and ZFP, together with chunk and tile sweeps aligned to the intended access unit. Beyond that, the thesis should be extended to sparse or multi-detector stacks, batched and random windows, mixed read/write workloads, and comparisons across regions, clouds, and on-prem \gls{PFS} deployments while modeling request, storage, and egress cost surfaces for representative usage patterns.

A particularly valuable next step would be a dedicated comparison between conventional HDF5 on high-IOPS \gls{EBS} or \gls{NVMe}-backed \gls{GPFS}/Lustre and HDF5 via \gls{HSDS} on \gls{SThree}, using identical datasets and access patterns. That experiment would separate \emph{format} behavior from \emph{infrastructure} effects and directly test whether block storage can deliver substantially lower slice latency than \gls{SThree}-backed \gls{HSDS} for the same HDF5 layout. A related study should isolate \gls{HSDS} spin-up and control-plane overhead by separating container start-up, metadata warm-up, and steady-state behavior. This thesis focuses on warm, steady-state measurements after warm-ups, so that decomposition would clarify the file sizes, session counts, and query rates at which \gls{HSDS} amortizes its overheads and becomes competitive with alternative layouts. The decision matrix itself could also be extended with weight-sensitivity visualizations, per-site presets, and a one-page selection checklist. Finally, it would be useful to quantify cold-open behavior for Zarr \texttt{consolidate\_metadata()} versus unconsolidated stores and for TileDB fragment consolidation, and to benchmark \gls{ROOT}'s newer \gls{RNTuple} backend under the same S3 testbed so the effect of its redesigned page and cluster layout on frame-random latency, full-scan throughput, and request intensity can be measured directly.

\subsection{Run protocol and quality control}
\label{app:a2-run-qc}
\textbf{Sessions.} One per \{format, codec, pattern\} with no overlap across formats.\\
\textbf{Warm-ups and repetitions.} 5 warm-ups, then $n{=}50$ timed runs per cell with idle gap $\ge$2\,min before timing.\\
\textbf{Cache regime.} No explicit cache-clearing between repetitions (no OS page-cache drops and no manual library-cache resets). Timed runs therefore represent warm, within-session behavior after warm-ups; absolute latencies are likely optimistic relative to cold-open first-touch reads, especially for metadata-heavy layouts.\\
\textbf{Slice warm-ups.} Slice frame indices are sampled without replacement, so warm-ups touch distinct frames; warm-up mainly primes connections and metadata rather than the timed pixel payload.\\
\textbf{Randomization.} Fixed seed with slice pattern uses a precomputed index list; full scan iterates all frames.\\
\textbf{Timer scope.} First dispatch $\rightarrow$ last byte; includes transfer, decompression, client decode.\\
\textbf{Inclusion rules.} Warm-ups excluded; only successful reads included; failures retried.\\
\textbf{QC.} Q–Q on $\ln(\text{time})$, lag-1 autocorrelation, run-order trend. See Figures \ref{fig:appendix_qq_grid_slice}, \ref{fig:appendix_qq_grid_full}, \ref{fig:appendix_drift_grid_slice}, \ref{fig:appendix_drift_grid_full}.

\subsection{Statistical settings}
\label{app:a3-stats}
\textbf{Scale.} Analyze $\ln(\text{time})$; report GM time with 95\% intervals; $p_{95}$ on original scale. Full-scan throughput (GiB/s) derived from bytes/time and analyzed on the log scale.\\
\textbf{Intervals.} Moving-block bootstrap (MBB) with $\ell\in\{4,6,8\}$, $B{=}10{,}000$; report the widest 95\% CI across $\ell$; sensitivity extends to $\ell{=}10$.\\
\textbf{Tails.} Main tables report the empirical (sample) $p_{95}$ with MBB CIs (using $\ell\in\{4,6,8\}$). Harrell–Davis $p_{95}$ with MBB CIs over $\ell\in\{4,6,8,10\}$ is reported as a tail-robustness sensitivity check.\\
\textbf{Contrasts.} Descriptive, session-conditional; ratios reference Zarr within codec$\times$pattern.

\subsection{Instrumentation and metrics}
\label{app:a4-metrics}
\textbf{Source.} Amazon \gls{SThree} server-side request metrics in CloudWatch at 1-minute periods, scoped to bucket and session prefixes. \textbf{Inventory.} Stored bytes and object counts per \{format, codec\} were obtained from S3 inventory listings for the benchmark bucket and prefixes.

\subsubsection*{Identifiers and statistics}
\begin{itemize}
  \item \textbf{GetRequestsSum}: \texttt{GetRequests}, statistic \texttt{Sum} (Count).
  \item \textbf{BytesDownloadedSum}: \texttt{BytesDownloaded}, statistic \texttt{Sum} (Bytes).
  \item \textbf{FirstByteLatencyAverage}/\textbf{P95}: \texttt{FirstByteLatency}, statistics \texttt{Average}/\texttt{p95} (ms).
  \item \textbf{TotalRequestLatencyAverage}/\textbf{P95}: \texttt{TotalRequestLatency}, statistics \texttt{Average}/\texttt{p95} (ms).
\end{itemize}

\subsubsection*{Derivations used}
\[
\text{GETs/run}=\frac{\text{GetRequestsSum}}{n_{\text{runs}}},\quad
\text{GETs/GiB}=\frac{\text{GetRequestsSum}}{\text{BytesDownloadedSum}/2^{30}},\quad
\]

\[
\text{Throughput (GiB/s)}=\frac{\text{BytesDownloadedSum}/2^{30}}{\text{total scan time (s)}}
\]

(See Table \ref{tab:req_intensity} and Table \ref{tab:cw_latencies}.)

\subsubsection*{Client timing logs}
Per \{format, codec, pattern\} cell, the notebook wrote a timing log and a CloudWatch export:

\begin{itemize}
  \item \textbf{Timing logs (client).} One JSON file per cell, with filename pattern \texttt{<format>\_<codec>\_<pattern>\_<run\_id>.json}. Each file contains an array of objects
  \begin{verbatim}
  [ {"i": <rep_index>, "t_total_ns": <int>}, ... ]
  \end{verbatim}
  where \texttt{i} is the repetition index ($1\ldots50$ for timed runs; warm-ups are not logged) and \texttt{t\_total\_ns} is the wall-clock time in nanoseconds for that read.
  \item \textbf{CloudWatch exports (server).} One JSON file per cell with aggregated CloudWatch metrics for the same time window, containing the identifiers listed above (\texttt{GetRequestsSum}, \texttt{BytesDownloadedSum}, \texttt{FirstByteLatencyAverage}/\texttt{P95}, \texttt{TotalRequestLatencyAverage}/\texttt{P95}).
\end{itemize}

\subsection{Per-format schema specifics}
\label{app:a6-schemas}
Common logical shape $(N,2880,2880)$, $N{=}1296$, \texttt{uint16}; one frame per chunk/tile $(1,2880,2880)$.\\
\textbf{\gls{HDFfive}/\gls{HSDS}.} Domain \texttt{/hdf5/\{gzip|lz4|zstd\}/all\_data.h5}; dataset \texttt{/data}; compression \{\texttt{gzip}, \texttt{lz4}, \texttt{zstd}\}. Frames were written in batches of 16 into contiguous slices of the dataset using the \gls{HSDS} client with host-level threading for frame decode and I/O.\\
\textbf{Zarr.} Store \texttt{s3://\dots/zarr/\{gzip|lz4|zstd\}.zarr}; array \texttt{/data}; codecs as above. Frames were written in batches of 16 contiguous slices, with threaded frame loading and a single chunk per frame.\\
\textbf{TileDB.} URI \texttt{s3://\dots/tiledb/\{gzip|lz4|zstd\}.tdb}; domain dims \texttt{file:[0,N-1]}, \texttt{y:[0,2879]}, \texttt{x:[0,2879]}; tile extents $(1,2880,2880)$. Writes were grouped into fragments of 16 frames each, so the expected fragment count is $\lceil N/16\rceil=81$.\\
\textbf{\gls{ROOT}/\gls{TTree}.} File \texttt{s3://\dots/root/\{gzip|lz4|zstd\}.root}; \texttt{TTree img\_tree} with branch \texttt{data} ($2880\times2880$ \texttt{uint16}); one entry per frame. Entries were appended sequentially, one frame per event, with \texttt{gzip}, \texttt{lz4}, or \texttt{zstd} compression.\\
\textbf{Parquet (single-object pilot only).} Single file; 2880 list-of-2880 \texttt{uint16} columns; one row per frame; dictionaries disabled; rows appended sequentially with \texttt{gzip} or \texttt{lz4} compression only.

\subsection{Parquet pilot notes}
\label{app:a8-parquet}
This thesis includes Parquet only as a pilot to document one concrete mapping of an $n$-D detector stack into Parquet and to surface operational pitfalls of a single-object layout on \gls{SThree}. It is not a quantitative benchmark of Parquet as a format family.

\textbf{Tested layout (single-object pilot).}
\begin{itemize}
  \item One Parquet file per codec (one \gls{SThree} object); codecs: \texttt{gzip} and \texttt{lz4} only.
  \item Schema: $2880$ columns \texttt{row\_0}\dots\texttt{row\_2879}, each \texttt{list<fixed\_size=2880, uint16>}; one appended row per frame (\(N{=}1296\)).
  \item Row groups: effectively one row group per frame because each write call appended a one-row table (PyArrow defaults).
\end{itemize}

\textbf{Observed during pilot.}
\begin{itemize}
  \item Stored size grew to a single \(\sim\)\SI{34}{\gibi\byte} object for a \(\sim\)\SI{20}{\gibi\byte} raw stack.
  \item Metadata open required \SIrange{3}{4}{\minute} on the \gls{ECtwo} node; repeated attempts to open the \texttt{gzip} file caused intermittent instability (including instance crashes).
\end{itemize}

\textbf{How to interpret this pilot.} The outcomes above are evidence about a \emph{single-file, single-object} Parquet layout for dense image stacks. In contrast, Parquet is commonly deployed as a \emph{partitioned} dataset of many Parquet data files (often managed by table formats such as Iceberg \cite{iceberg_spec}) with tuned file sizing and row-group sizing for scan/filter workloads; such variants were not evaluated here.

\chapter{Introduction}
\label{ch:introduction}
Modern synchrotron and neutron scattering facilities have dramatically increased data output, generating up to 7.7 GB per second \cite{celcer2018gigafrost}. Traditional HPC file systems such as Lustre and GPFS excel at large, contiguous transfers. However, they struggle when users need on-beamline feedback from thousands of small, partial reads. At the same time, collaborating teams often face network-mounted filesystem bottlenecks and the escalating capital costs of maintaining on-premises systems.

Cloud object storage (e.g., AWS S3) offers a compelling alternative with unlimited capacity, global accessibility, and pay‐as‐you‐go economic models. However, naively mapping monolithic formats such as HDF5 or NeXus onto S3 leads to thousands of range‐GETs for minor chunk accesses, inefficient metadata lookups, and unpredictable request fees \cite{durbin2020cloud}. In response, a new ecosystem of cloud‐native storage models has emerged: chunked arrays (Zarr), columnar layouts (Parquet), zero‐copy IPC (Arrow/Feather), tree‐based event stores (ROOT/RNTuple), each promising different trade‐offs in latency, throughput, compression, CPU overhead, and cost \cite{ambatipudi2023comparisonhdf5zarrnetcdf4,zeng2023empiricalevaluationcolumnarstorage,Lopez_Gomez_2023}.

While isolated evaluations of individual cloud‐native formats have been conducted, a comprehensive, head-to-head comparison of HDF5, Zarr, Parquet, Arrow/Feather, and ROOT on realistic, terabyte-scale scattering datasets in AWS remains lacking. This thesis, therefore, implements and benchmarks each format across multiple compression codecs and access patterns to produce a decision matrix that guides beamline scientists and data-intensive computing engineers.

\section{Background}
As synchrotron and neutron facilities have evolved, detector technologies and beamline instrumentation have driven data generation rates from megabytes to multiple gigabytes per second. Modern experiments frequently combine multiple detectors and scan axes, such as energy, angle, or polarization, resulting in multidimensional datasets that can reach terabyte scales within a single experimental run \cite{celcer2018gigafrost}.

\subsection{Limitations of Traditional HPC Storage}
Historically, researchers stored beamline data on parallel file systems such as Lustre or GPFS and accessed it through MPI-IO or batch-oriented workflows. These systems work great for large‐block I/O operations but have high overhead when serving thousands of small, random reads, typical of exploratory data slices or metadata queries \cite{narayan2010characterization}. Furthermore, maintaining on‐premises HPC arrays entails significant capital and operational expenditures and network‐mount complexity for geographically distributed collaborators (usually seen because experiments happen in only key parts of the world).

\subsection{Emergence of Cloud-Native Storage Models}
Cloud object storage, most notably Amazon S3, has emerged as an attractive alternative in recent years. Object stores provide virtually unlimited, durable storage, global namespace access, and a pay‐as‐you‐go billing model that shifts capital costs to operational expenses. However, monolithic scientific formats such as HDF5 or NeXus for POSIX-style filesystems and storing them naively on S3 generate hundreds or thousands of HTTP range-GET requests per small read, plus extra LIST/HEAD operations for metadata traversal \cite{durbin2020cloud}.

Researchers have introduced a new generation of cloud-native data models to address these shortcomings. Zarr and similar chunked array formats expose each multidimensional chunk as an independent object, enabling massive parallel GET/PUT operations and delivering aggregate bandwidths comparable to HPC filesystems when chunks are set to a few megabytes each. \cite{moore2023ome}. Columnar storage formats such as Apache Parquet organize data in row groups and column stripes, pruning unneeded fields to reduce I/O usage \cite{ivanov2020impact}. Apache Arrow delivers zero‐copy, in‐memory serialization that minimizes CPU overhead and achieves sub‐millisecond data transfer \cite{10.1145/3527199.3527264}. In parallel, the high‐energy physics community has extended ROOT’s TTree and RNTuple abstractions to object‐store backends, preserving branch‐level selective reads while retaining local filesystem performance characteristics \cite{DBLP:journals/corr/abs-2107-07304}.

Each approach offers distinct trade‐offs in latency, throughput, compression efficiency, CPU overhead, and cost. Although individual formats have been benchmarked in isolation or within specific domains, there is no comprehensive, side‐by‐side evaluation of realistic, terabyte‐scale scattering datasets in AWS. Addressing this gap will inform both beamline scientists, seeking responsive, cost‐effective data access, and data‐intensive computing engineers, designing next‐generation, cloud‐native scientific platforms.


\section{Problem}
\label{sec:problem}
Handling large-scale scattering datasets on AWS S3 reveals several limitations in current data platforms. First, partial reads of beamline slices, such as retrieving a single detector channel or angular data segment, can result in high latency due to the need to perform hundreds, if not thousands, of GET operations and metadata lookups, leading to delayed experimental feedback. Secondly, existing prior prototype evaluations have focused on moderate‐scale workloads. There is limited empirical data on true terabyte-scale (1 TB+) scattering experiments. This thesis, therefore, benchmarks each format on multi-terabyte datasets to uncover performance, resource usage, and data ingestion bottlenecks. Thirdly, the interaction between storage formats and compression algorithms (e.g., zstd, LZ4, gzip) has not been systematically evaluated, making it unclear which format codec combinations best optimize latency, throughput, and cost for large-scale S3‐based workflows.

These industrial challenges raise questions for the data-intensive computing community: How can we systematically leverage and compare different storage backends to generate guidance for scientific users? Which combinations of performance, cost, and integration trade-offs matter most when designing cloud-native workflows for interactive, partial-retrieval use cases? \emph{How do five candidate formats (HDF5, Zarr, Parquet, Arrow/Feather, ROOT) compare on AWS regarding performance, scalability, cost, and compression efficiency for partial-retrieval workloads on large-scale scattering datasets?}. Answering this question will enable the development of best practices for data handling at synchrotron and neutron facilities and provide transferable insights to other big-data science domains, improving experimental productivity and resource efficiency, especially in cloud computing.

\subsection{Original problem and definition}
This thesis defines the original industrial problem as optimizing the retrieval of small, targeted data slices (e.g., a single angle’s worth of diffraction frames) from multi-terabyte scattering datasets stored on AWS S3. “Partial retrieval” refers to reading only the necessary object segments by byte range or object key rather than downloading entire files. This scope excludes batch transfers or on-premises filesystem solutions. It focuses solely on cloud-native, object-store workflows.


\subsection{Scientific and engineering issues}
Generalizing beyond the narrow industrial case leads to several key research questions:

\begin{itemize}
 \item Which access patterns (e.g., small random reads vs.\ large sequential scans, metadata index scalability) stress each format’s architecture the most?
 \item How do different compression algorithms (zstd, LZ4, gzip) interact with object-stored data, and how does it affect end-to-end latency and throughput?
\end{itemize}

These questions are directly relevant to ongoing research in HPC and data-intensive computing, where cloud adoption continues to challenge traditional storage paradigms.




\section{Purpose}
The purpose of this thesis is twofold. First, this study seeks to advance the scientific and engineering understanding of cloud‐native storage paradigms within the data‐intensive computing community. Drawing on design–science research methodologies \cite{hevner2004design}, it will experimentally quantify the trade‐offs among compression efficiency (zstd, LZ4, gzip), performance of retrieval, and economic metrics (request fees, egress charges) for terabyte‐scale, multidimensional datasets. The decision matrix and best‐practice recommendations will inform beamline scientists seeking rapid feedback during experiments and guide platform architects in building next‐generation, cloud‐optimized scientific workflows.

Secondly, it aims to provide Scatterin AB with a practical, evidence-based framework to optimize its cloud-based data platform for large‐scale synchrotron and neutron scattering experiments. By implementing and benchmarking five distinct storage approaches (HDF5/HSDS, Zarr, Parquet, Arrow/Feather, ROOT/RNTuple) on AWS S3, this work will deliver concrete guidance on how to minimize latency for partial‐read use cases, maximize throughput, and control pay‐as‐you‐go costs under varying access patterns.



\section{Goals}
This paper aims to develop a comprehensive, experimentally validated decision framework that guides the selection and configuration of cloud‐native storage solutions for large‐scale AWS synchrotron and neutron scattering datasets. To achieve this, the following sub‐goals are defined:

\begin{enumerate}
  \item \textbf{Prototype Development}
  \begin{itemize}
    \item Ingest a representative $\sim$1 TB dataset (tabular metadata and dense multidimensional arrays) into each of five storage backends: HDF5/HSDS, Zarr, Parquet, Arrow/Feather, ROOT/RNTuple.
    \item Implement consistent chunking and compression (zstd, LZ4, gzip) to ensure fair comparisons across formats.
  \end{itemize}

  \item \textbf{Quantitative Benchmarking}
  \begin{itemize}
    \item Measure read and write latency for both partial‐slice and full‐scan workloads.
    \item Evaluate compression efficiency (size reduction vs.\ CPU time) for each algorithm.
    \item Compute the one‐month total cost of ownership (TCO) in AWS hot, warm, and cold storage tiers, incorporating request fees and egress charges.
  \end{itemize}

  \item \textbf{Decision Matrix and Guidelines}
  \begin{itemize}
    \item Synthesize results into a matrix correlating workload patterns (partial vs.\ bulk reads, compression) with format‐specific performance, cost, and ease of integration.
    \item Formulate best‐practice recommendations for beamline scientists and data‐intensive computing engineers.
  \end{itemize}
\end{enumerate}




\section{Research Methodology}

This study adopts an \emph{experimental benchmarking} approach within a design–science framework to evaluate five storage backends on AWS. Our methodology comprises four main components:

\begin{enumerate}
  \item \textbf{Data ingestion and environment setup}
  \begin{itemize}
    \item Acquire two datasets representative of synchrotron and neutron experiments: a tabular dataset (1 M × 20) and a dense 3D array ($\sim$1 TB).
    \item Provision EC2 instances with both RAM‐disk and S3‐backed configurations, using Terraform for reproducible infrastructure \cite{hashicorp2025terraform}.
    \item Implement ingestion pipelines for HDF5, Zarr, Parquet, Arrow/Feather, ROOT/RNTuple, mapped over compression algorithms (zstd, LZ4, gzip).
  \end{itemize}

  \item \textbf{Performance testing}
  \begin{itemize}
    \item Define two access patterns: \emph{small‐slice reads} (4–8 MB chunks) and \emph{bulk scans} (full dataset sequential read).
    \item Execute $n=50$ randomized runs per format, per pattern, on both RAM‐disk and S3, measuring median and 95th‐percentile latency, throughput (MB/s), compression ratio, and CPU utilization.
  \end{itemize}

  \item \textbf{Scientific method framework}
  \begin{itemize}
    \item \textbf{Variables and hypotheses:} Independent variable: storage format (five approaches). Dependent variables: latency, throughput, compression ratio, cost.
    Hypothesis (per metric): The mean (or distribution) differs across at least two formats at $\alpha=0.05$.
    \item \textbf{Design and data:} $n=50$ randomized runs per format on EC2 (both RAM-disk and S3). We justified the sample size by performing a preliminary power analysis to achieve 80\% power to detect a medium effect (Cohen’s $f=0.25$).
    \item \textbf{Analysis and decision rule:}
    \begin{enumerate}
      \item \textbf{Assumption checks:}
        \begin{itemize}
          \item Normality of residuals: Shapiro–Wilk test \emph{plus} Q–Q plots (since Shapiro–Wilk can flag minor deviations at $n>50$).
          \item Homogeneity of variance: Levene’s test.
        \end{itemize}
      \item \textbf{Primary test:}
      \begin{itemize}
        \item If normality and homogeneity hold: one-way ANOVA $\to$ Tukey HSD post-hoc.
        \item Otherwise: Kruskal–Wallis test $\to$ Dunn’s post-hoc with Holm correction.
      \end{itemize}
      \item \textbf{Reporting:}
      Effect sizes (e.g., \ $\eta^2$ for ANOVA or Cliff’s $\delta$ for nonparametric) and 95\% confidence intervals.
    \end{enumerate}
  \end{itemize}


  \item \textbf{Cost modeling}
  \begin{itemize}
    \item AWS Pricing to compute a one-month TCO scenario for hot (S3 Standard), warm (Infrequent Access), and cold (Glacier) tiers, including request and egress fees.
  \end{itemize}
\end{enumerate}

The code and infrastructure are versioned and configured in a public Git repository. Benchmark parameters and raw measurements will be archived and made available alongside the thesis. This rigorous methodology lets us derive statistically sound, actionable guidelines for selecting cloud-native storage formats in large-scale scientific workflows.



\section{Delimitations}

This thesis focuses exclusively on cloud-native, object-store–based workflows within the Amazon Web Services (AWS) ecosystem. Specifically, five storage backends are evaluated, HDF5, Zarr, Parquet, Arrow/Feather, and ROOT/RNTuple, by ingesting and benchmarking two representative datasets (tabular and dense arrays) on EC2 instances with S3 storage. The following boundaries apply:

\begin{itemize}
	\item \textbf{Cloud provider scope:} Only AWS services (S3, EC2) are considered. No experiments involve Azure, Google Cloud, or on-premises HPC clusters.
 	\item \textbf{Storage formats:} The study is limited to the five specified formats. Other emerging or domain-specific formats (e.g., Avro, ORC, CBF, NeXus variants) fall outside the scope.
 	\item \textbf{Workload types:} Benchmarks cover two data sets of scattering data: a 1 M × 20 tabular dataset and a 3D dense array.
 	\item \textbf{Access patterns:} Evaluation targets small-chunk partial reads (4–8 MB) and full-dataset scans. This study excludes other patterns (e.g., random single-element lookups and real-time streaming ingestion).
 	\item \textbf{Compression algorithms:} This study applies three widely used codecs (zstd, LZ4, and gzip) and does not compare other options such as Snappy, Brotli, bzip2, ZFP.
\end{itemize}

These delimitations ensure a focused, reproducible comparison of core performance and cost trade-offs for large-scale scientific data storage in AWS.



\section{Structure of the thesis}

This thesis is organized into seven main chapters, followed by appendices:

\begin{description}
  \item[Chapter 1: Introduction] Presents the motivation, scope, research question, methodology overview, delimitations, and outlines the thesis structure.
  \item[Chapter 2: Background] Reviews scientific data challenges in synchrotron and neutron facilities, surveys traditional HPC I/O and emerging cloud‐native formats (HDF5/HSDS, Zarr, Parquet, Arrow/Feather, ROOT/RNTuple), and identifies gaps in existing benchmarks.
  \item[Chapter 3: Research Methodology] Details the experimental design: dataset selection, AWS infrastructure setup, ingestion pipelines, access patterns, performance metrics, statistical tests, and cost/sustainability modeling.
  \item[Chapter 4: Implementation] Describes prototype implementations for each storage backend, reproducible chunking and compression, and automation of ingestion and test workflows.
  \item[Chapter 5: Results and Analysis] Presents quantitative results, latency distributions, throughput curves, compression ratios, and TCO estimates, followed by statistical comparisons and effect‐size interpretations.
  \item[Chapter 6: Decision Matrix and Discussion] Synthesizes findings into a format‐selection matrix, discusses trade‐offs, integration complexity, and sustainability implications, and provides guidelines for beamline scientists and data engineers.
  \item[Chapter 7: Conclusions and Future Work] Summarizes key contributions, reflects on limitations, and proposes directions for extending the study (e.g., \ multi‐cloud comparisons, additional compression algorithms, real‐time streaming ingestion).
  \item[Appendices] Include detailed benchmark logs, AWS Terraform templates, code snippets, and supplementary figures.
\end{description}

\section{Scientific-Data Context}
\label{sec:scientific-data-context}
Synchrotron light sources and spallation/continuous‐beam neutron facilities have evolved into “mega‐pixel movies“ of matter that stream raw images at gigabytes per second speeds. This section sets the stage for the storage challenge by outlining how modern beamlines generate multi-TB/day data, describing the acquisition hardware that drives these rates, and giving a concrete, industry example that shows why fast, selective read-back of that data matters in practice.

\subsection{Synchrotron and Neutron Facilities}
\label{sec:synchrotron-neutron-facilities}

Giant accelerator-based light and neutron sources act as kilometer-scale microscopes that let us “see through’’ centimeters of steel, polymers, or living tissue at kilohertz frame rates. By storing ultra-low-emittance electrons (or moderating proton-driven neutrons), the machines deliver beams that are \(\sim10^{10}\!-\!10^{12}\) times brighter than laboratory instruments, unlocking 3-D imaging and diffraction of virtually any material \cite{eriksson2014diffraction}. Each pulse is immediately converted into multi-megapixel images by high-speed area detectors, hybrid photon counters, CMOS cameras, or time-pix neutron imagers. Capturing these data allows a single experiment to exceed 10 GB/s \(^{-1}\) of raw data.

The industrial impact is tangible. At the European Synchrotron Radiation Facility, X-ray tomography has revealed how expanded-polypropylene crash foams used in car bumpers collapse under load, informing design rules for next-generation impact absorbers \cite{carnegie2024uninterrupted}. Neutron radiography visualizes sub-second water build-up that strangles polymer-electrolyte fuel cells during winter cold starts, guiding stack architecture and heating strategies for fuel-cell vehicles \cite{yoshimune2024neutron}.


\subsubsection{Typical beamline architecture}
Synchrotron and spallation neutron facilities generate intense, tightly focused beams of X-rays or neutrons that travel down a specialized experimental “beamline.” First, the beam passes through a set of front-end optics mirrors, slits, and monochromators, to shape its size, divergence, energy, and flux. Next, a precision sample stage (multi-axis translation stage) positions the specimen with sub-micrometer accuracy and may rotate it to capture different orientations. Immediately downstream, a high-speed detector records two- or three-dimensional diffraction or imaging data at rates up to thousands of frames per second.

To handle this torrent of data, a dedicated data-acquisition (DAQ) server sits between the detector and the facility network. The DAQ server buffers raw frames on local NVMe SSDs or a burst-buffer appliance, performing initial checks (e.g., dropped-frame detection, coarse image correction) before storing the data. Traditionally, the data stream goes directly into a parallel file system such as Lustre or GPFS, making it available to downstream analysis clusters. Figure \ref{fig:beamline-journey} shows this data path into a single schematic, highlighting the fork between traditional parallel file systems and emerging object-store workflows.

Modern beamlines already saturate local networks with sustained data streams of $\mathcal{O}(10^{2})$ MB s$^{-1}$ per instrument. For example, the Advanced Photon Source Upgrade anticipates \SI{172}{MB.s^{-1}} per double sector and \SI{4}{GB.s^{-1}} facility-wide \cite{veseli2019data}. Looking ahead, diffraction-limited storage rings are projected to drive detector outputs beyond \SI{10}{GB.s^{-1}} and data volumes of \SI{>10}{TB} per experiment, showcasing the need for radical upgrades to storage and analysis pipelines \cite{eriksson2014diffraction}.

\subsubsection{Dimensionality of datasets}
Indexing a single 2-D detector frame by additional experimental coordinates collected during beamtime turns it into a \emph{genuinely higher-dimensional data object}. Figure \ref{fig:data-cube} makes this concrete: each 2-D image becomes one colour-coded slice in a stacked data cube, while the depth axis stores a third coordinate such as rotation angle, energy, or time. From this perspective, every pixel expands into a voxel that contains its spectrum, angular position, or temporal history, laying the foundation for true 4-D and 5-D analyses. Because modern beamlines routinely vary at least three independent axes, the raw $(x,y)$ detector image is naturally in higher dimensions, such as a 4-D (or higher-D) array:

\begin{itemize}
  \item \textbf{Rotation or scan angle:} a full tomographic or serial-crystallography scan may step the sample (or detector) through $10^{2}$–$10^{4}$ projections to reconstruct 3-D real-space structure or space intensity maps (\emph{rotation} $\times$ \emph{energy} $\times$ \emph{time}) \cite{app11198868}.
  \item \textbf{Energy or wavelength: } spectro-microscopy and EXAFS experiments, the microscope continuously sweeps the X-ray energy across an absorption edge. At the same time, a fast detector captures a rapid series of images. This procedure produces hyperspectral cubes with $\sim$10–$10^{2}$ energy points per angle or time step \cite{Briois:uc5005}.
\end{itemize}

When these axes are combined, experiments routinely generate 5-D or 6-D datasets; for example, a $2048\times2048$ detector recording 1800 rotation angles, 50 energy points, and 20-time delays already contains $\sim150\times10^{9}$ pixels ($\approx$\,300\, GB at 16-bit depth). Such “data objects’’ are significant for multivariate analyses (e.g., \ correlating oxidation state with 3-D morphology over time) but place extreme demands on storage systems. Some beamlines further append polarization, external field strength, or environmental parameters (temperature, pressure, electrochemical potential), pushing data dimensionality and storage complexity even higher.

\subsubsection{Real-world automotive example}
The auto industry increasingly deploys neutron radiography to visualize water and ice formation inside polymer-electrolyte fuel-cell stacks during rapid cold starts. The study used an operational neutron imaging system to map liquid distribution in a Toyota single cell down to sub-second time scales, informing design tweaks that mitigate performance losses \cite{yoshimune2024neutron}.


\subsection{Experimental Workflows \& Feedback Loops}
\label{sec:experimental-workflows-feedback-loops}
Beam time at synchrotron and neutron facilities is hard to get and expensive. Experiments must, therefore, include a \emph{closed data loop} in which raw detector frames are reconstructed, inspected, and, if necessary, used to steer the scan while the sample is still in the beam. There have been multiple ways in which studies have tried to come up with a good solution with real-time feedback to combat this. A study showed that streaming projections from the beamline to an HPC cluster could deliver slice reconstructions within seconds, enabling autonomous adjustment of exposure, angle range, or focus during tomography scans \cite{Bicer2017RealTime}.

Shanghai Synchrotron Radiation Facility pushes this concept further: automated pipelines tied into the metadata catalog issue progress notifications and interactive dashboards to users, allowing real-time feedback \cite{wang2024accelerating}.

\subsubsection{Implications for the storage stack}
\begin{itemize}
  \item \textbf{Latency}: scientists often request slices of data (quick-look radiographs or azimuthal-integrated diffraction rings). Data retrieval times must stay in the sub-second regime to keep up with the experiments.
  \item \textbf{Throughput}: full 3-D reconstruction or machine-learning inference may pull hundreds of contiguous gigabytes at the end of a scan often includes burst bandwidths of \(\ge\!10\) GB\,s\(^{-1}\).
  \item \textbf{Scalability \& concurrency}: remote teams viewing the same dataset and automated QC pipelines often need simultaneous small-read streams. This often penalizes monolithic file formats that require entire files to be downloaded or incur seek-heavy range requests.
  \item \textbf{Online analysis}: real-time processing pipelines (e.g., streaming reconstruction, AI-driven feature extraction) consume data as it arrives. Storage must support continuous, low-overhead partial reads and write-through metadata indexing to feed live analytics without waiting for scan completion.
\end{itemize}

These workflow pressures dictate the performance metrics used later in this thesis and motivate the evaluation of cloud-native, chunk-addressable storage formats that promise millisecond-scale partial retrieval.


\section{Traditional HPC Storage Paradigms}
\label{sec:traditional-hpc-storage-paradigms}
For the past decades, scientific supercomputers have relied on
\emph{parallel file systems}, where Lustre and IBM’s General
Parallel File System (GPFS) has stood out. These systems have allowed pushing checkpoint files and simulation outputs across hundreds of disks at tens of GB s$^{-1}$ aggregate bandwidth \cite{schwan2003lustre,schmuck2002gpfs}. By stripping data over many objects, storage targets and coordinating access via distributed locks became ideally matched workloads that wrote multi-gigabyte files in large, contiguous chunks.

Those design assumptions are strained when the I/O profile flips from “few huge checkpoints” to many tiny look-ups and interactive slices. A study from the Summit and Cori supercomputers shows that small transfers (< 1 MB) still account for the overwhelming majority of read and write calls at both the file and process levels. At the same time, in large-scale HPC deployments, metadata operations alone can account for a considerable part of the file-system requests, often saturating the metadata servers and emerging as a primary scalability bottleneck \cite{bez2022access}. As beamlines, AI workflows, and remote collaborators pile on, the gap between traditional parallel-file-system design and real-time, small-slice demands only widens.

The remainder of this section revisits how parallel file systems achieve their impressive bulk throughput and why those mechanisms falter under modern, latency-sensitive access patterns. Thus, it motivates the cloud-native alternatives examined later in this chapter.


\subsection{Parallel File Systems (Lustre, GPFS, BeeGFS)}
\label{sec:parallel-file-systems}

Lustre, IBM GPFS (now Spectrum Scale), and BeeGFS have dominated supercomputing storage for over two decades, consistently delivering hundreds of gigabytes per second of throughput. By striping data across hundreds of disks and coordinating access with distributed locks, these systems excelled at writing multi-gigabyte files sequentially. The same system, however, reveals hidden costs once workloads pivot to small, random reads or remote, WAN-mounted access.

\subsubsection{Architecture and striping model}
Classic HPC file systems split responsibility between \emph{metadata servers} (MDS) and many \emph{object/data servers} (OSS in Lustre, NSD servers in GPFS, storage targets in BeeGFS). Files are \emph{striped} across a few to hundreds of disks in multi-megabyte chunks. Doing this allows a single sequential read or write to optimize the bandwidth of an entire system. PFS uses token-based distributed locking to keep POSIX consistency on a shared-disk SAN \cite{schmuck2002gpfs}. BeeGFS achieves similar semantics over Ethernet by separating data and metadata and scaling the service.

\subsubsection{Bulk Sequential I/O: High Throughput on Parallel File Systems}
Parallel file systems shine whenever an application issues long, contiguous transfers, checkpoints/restarts, volumes, and snapshots. NASA’s \emph{Pleiades} cluster still sustains, \(\sim\!1\) GB s$^{-1}$ from disk for a single 512-rank IOR stream and bursts to 9 GB s$^{-1}$ when the same data are serviced out of the page cache \cite{6507507}. Modern flagships go far beyond that, where Los Alamos’ \textit{Trinity} Sonexion Lustre tops out near 1.6 TB s$^{-1}$ for a 78 PB pool \cite{osti_1367056}. Even a single E1000 OSS inside NERSC’s \textit{Perlmutter} can saturate 41 GB s$^{-1}$ read and 27 GB s$^{-1}$ write to one OST \cite{lockwood2024architecture}. These traits explain why parallel file systems remain the choice for bulk sequential scans and multi‐terabyte tomography stacks.

\subsubsection{Weaknesses for many-small reads}
Parallel file systems raise aggregate bandwidth by slicing every file across many Object Storage Targets (OSTs/NSDs). When workloads flip from multi-GB checkpoints to thousands of $4$–$64$\,\si{\kilo\byte} reads the same striping logic backfires when workloads issue thousands of sub-megabyte reads. Intel’s LUG-2018 “Small File I/O” report shows that files smaller than the DoM threshold generate disproportionately more RPCs per MiB, leading to significantly reduced bandwidth on multi-OST Lustre systems \cite{gmitter2018smallfile}.

Even in a namespace-sharded file system like Lustre’s DNE, a camera‐style “one-file-per-frame” workflow still concentrates its create/unlink traffic on one hot directory subtree. Production traces from 60 HPC systems show that 64 \% of files are smaller than 64 KB. When a system gets flushed with thousands of tiny HDF5 or JPEG files, the operations on the metadata will increase exponentially. Based on these 60 different HPC systems, research shows that metadata operations can account for up to 80\% of total file system operations \cite{9768784}.

\subsection{POSIX-Centric Scientific Formats}
\label{sec:posix-centric-formats}
Most HPC codes write \textit{monolithic containers}, a single POSIX-seekable file that includes raw arrays and metadata. HDF5 popularised this approach, while NeXus adopts the same file structure with beamline-specific naming conventions. The design is perfect for bulk, sequential, local parallel file systems scans. However, the need to search through super-blocks and B-trees for every small slice makes it poorly suited to cloud object stores and interactive, many-small-read workflows, motivating the chunk-per-object formats.

\subsubsection{Monolithic container philosophy}
The Hierarchical Data Format~5 (HDF5) stores every dataset, chunk, and attribute in a single byte‐addressable file whose internal super-block, B-trees, and heap tables, with the help of POSIX, seek for navigation \cite{howison2010tuning}. Nexus, the de facto standard at many photon and neutron sources, layers a domain system on top of the same HDF5 container, retaining identical I/O semantics while prescribing beamline-specific group names and units \cite{konnecke2015nexus}. This “all-in-one” layout simplifies the file management, but couples performance to the underlying file-system block size and how well metadata caches handle random seeks.

\subsubsection{Serial and MPI-IO access}
Out-of-the-box HDF5 (used via h5py, MATLAB, etc.) issues are independent of POSIX. Each rank that samples a 4–8~MB slice generates dozens of tiny, <64~kB reads, leading to many metadata lookups. Performance tuning guides from the HDF Group note that such traffic can result in many minor accesses and that parallel file systems do not do well with small I/O \cite{Breitenfeld2022Parallel}. Parallel HDF5 wraps the same container in MPI-IO so that all processes participate collectively. Doing so when users provide non-contiguous selections, ROMIO gathers them into a single larger request (data sieving and collective buffering).

Even when using collective metadata I/O, each HDF5 read still must fetch the superblock and descriptive metadata before reading the raw data. In the CCGrid’21 benchmarks on Summit and Cori, metadata I/O alone accounted for as much as ~58\% of the total read time \cite{9499420}. HDF5/NeXus excels for large, sequential scans and single-node post-processing. However, their single-file, POSIX heritage makes interactive, many-small-read workloads vulnerable to metadata hot spots. These limitations motivate the chunk-per-object designs of Zarr, Parquet, and the other cloud-native formats evaluated in this report.


\section{Cloud Object Storage Fundamentals}
\label{sec:cloud-object-storage-fundamentals}
Cloud object stores, presented by Amazon S3, sit at the core of the storage formats benchmarked in this thesis. Amazon S3’s defining features are a flat, immutable-object namespace, global durability, and a pay-as-you-go pricing model. Amazon S3, therefore, removes local capacity provisioning constraints, but the system does introduce HTTPS-level latency and per-request charges that do not exist in local NVMe or parallel file systems. Grasping these trade-offs is therefore vital before interpreting the performance results.

\subsection{Architectural model}
Amazon Simple Storage Service (S3) organizes data in \emph{buckets} that share a \emph{flat global namespace}, and directory hierarchies are only a key-naming convention. Objects are \emph{immutable}, meaning any modification creates a new version of that object/file. Since December 2020, S3 guarantees \emph{strong read-after-write consistency} for all operations, removing the race conditions that earlier eventual-consistency semantics introduced \cite{AWSConsistency2020}.


\subsection{Request classes and cost drivers}
Every interaction with S3 is an HTTPS API call in one of four core request classes. Each call is billable in addition to storage (\si{GB}\,month) and data-egress charges \cite{AWSS3Pricing2025}.

\subsection{Latency characteristics}
Each request traverses a multi-AZ control plane and TLS handshake, giving time-to-first-byte latencies of \SIrange{100}{200}{\milli\second} for small objects \cite{AWSS3Performance2024}. In comparison, on-premises NVMe RAID or parallel file systems typically deliver sub-millisecond metadata look-ups, and even AWS’s own Elastic File System (EFS) SSD class reports $\approx\SI{0.25}{\milli\second}$ latencies \cite{AWSEFSLatency}. This gap explains why typical ported HPC workloads feel slow and perform poorly on S3. Figure \ref{fig:latency-ladder} visualizes the comparison on a log scale, showing how the jump from \SI{0.1}{ms} NVMe reads \cite{haas2023modern} to \SI{0.25}{ms} EFS reads \cite{aws_efs_latency} and finally to \SI{100}-\SI{200}{ms} S3 requests \cite{aws_s3_latency} forces any cloud-native workflow to be able to handle round-trip cost through chunking, caching, and request batching.

\subsection{Performance-optimisation layers}
\begin{itemize}
  \item \textbf{Multipart uploads}: split objects ($\ge\SI{100}{\mega\byte}$) into \SIrange{5}{5000}{\mega\byte} parts that upload in parallel and resume after failure \cite{AWSS3MultipartDoc}.
  \item \textbf{Range GETs}: request only required byte spans, ideally aligned with the same \SIrange{8}{16}{\mega\byte} boundaries used during uploads \cite{AWSS3RangeGET}.
  \item \textbf{Prefix parallelism}: S3 scales to at least \num{5500} GET/HEAD and \num{3500} write requests per \emph{prefix}. Optimally sharding key lifts can aggregate throughput to multi \si{TB/s} \cite{AWSS3Performance2024}.
\end{itemize}

These optimization strategies allow object storage to approach HPC-class \emph{throughput}. However, the inherent network-centric part of the system keeps \emph{latency} for small, random slice reads higher than local or NVMe-backed file systems. This constraint motivates the chunking and indexing strategies evaluated in this report.



\section{Cloud-Native Storage Models}
\label{sec:cloud-native-storage-models}
Cloud object stores such as Amazon S3, Azure Blob, and Google Cloud Storage deliver effectively unlimited capacity and global accessibility. But they do not come without many drawbacks, such as request latency, immutable‐object semantics, and per‐request billing. Some drawbacks clash with the low‐latency, mutable-file assumptions baked into traditional HPC formats \cite{durbin2020cloud}. To exploit cloud elasticity without prohibitive slice-read costs, a new generation of \emph{cloud-native storage models} has emerged, each rethinking how scientific arrays or tables are partitioned, compressed, and addressed in an object store.

The remainder of this section surveys five representative approaches: HDF5 served through the Highly Scalable Data Service (HSDS), Zarr's chunk-per-object layout, Apache Parquet's columnar row-group design, Apache Arrow/Feather's zero-copy IPC stream, and CERN's page-oriented ROOT/RNTuple format. Each part highlights how each approach maps its internal data units onto cloud objects, what compression and indexing strategies it employs, and which trade-offs in latency and throughput.

\subsection{HDF5 + HSDS}
\label{sec:hdf5-hsds}
The HDF5 ecosystem represents the most mature and widely adopted solution for storing complex scientific data, spanning disciplines from climate modeling to synchrotron beamline acquisition \cite{10.1145/1966895.1966900}. However, developers designed the format for low-latency, parallel file systems. When migrated naively to cloud object stores, its monolithic layout magnifies request latency and per-operation costs. To preserve HDF5’s rich data model while overcoming these cloud-specific bottlenecks, the Highly Scalable Data Service (HSDS) was created as a stateless REST layer that shards chunks and metadata into individually addressable objects \cite{readey2020hsds}.

\subsubsection{HDF5 fundamentals}
Hierarchical Data Format~5 (HDF5) is an open-source container, data model, and I/O library designed to efficiently store extensive, multidimensional scientific data \cite{10.1145/1966895.1966900}. An HDF5 file consists of \emph{datasets} (n-dimensional arrays) organized in a POSIX-style hierarchy of groups. Datasets may be either \emph{contiguously} or as fixed-size \emph{chunks}. Chunking enables transparent filter pipelines (e.g., gzip, lz4, zstd) and independent partial reads/writes. At the same time, the library’s MPI-IO pathway lets thousands of compute nodes access different chunks concurrently \cite{hdf5_chunking}. These strengths made HDF5 the standard library/system used at X-ray, neutron, and electron facilities.

\subsubsection{Cloud usage}
Placing a monolithic HDF5 file on Amazon S3 causes each POSIX \emph{read()} call to issue a separate HTTP Range GET. Therefore, a single 1 MB slice triggers two network round-trips (metadata + data), amplifying latency and incurring request fee costs that traditional HPC deployments never experience \cite{hdf5_ros3}. Moreover, the file's internal B-tree indices are optimized for low-latency block storage, not for the 10-ms (or higher) object-store round-trip typical of Amazon S3.

\subsubsection{HSDS: a layered service}
The \emph{Highly Scalable Data Service} (HSDS) re-implements the HDF5 abstraction as a stateless REST API \cite{readey2020hsds}. Internally, HSDS maps every chunk and metadata into separate objects (S3, Azure Blob, MinIO, or POSIX) and maintains a small JSON document that maps logical dataset coordinates to object keys. This approach allows traversing the HDF5 “groups” and “datasets.” With HSDS, reading or writing array slices and modifying attributes through standard HTTP requests is possible.

\subsubsection{Operational experience}
Production HSDS clusters are now back multi-hundred-terabyte public archives, for instance, NREL’s 500 TB Wind Toolkit Long-Term Ensemble dataset, which users can subset without downloading entire files \cite{draxl2024wtkled}. HSDS retains HDF5’s rich ecosystem yet promises proper cloud-native capabilities.

\subsection{Zarr}
\label{sec:zarr}

Zarr is an open-source system that builds on the fundamentals of storing chunked, compressed $n$-dimensional arrays in a directory-type layout of small objects \cite{zarrspecv3}. The system partitions each array into regular \emph{chunks} and stores every chunk as an independent object (e.g., a file in a POSIX system, a key in Amazon S3). Zarr supports compression with popular codecs such as gzip, lz4, or zstd and utilizes JSON metadata files. The format requires no central server, making it attractive for cloud object stores where high-latency, high-throughput parallel access dominates.

\subsubsection{Cloud-native performance}
Because each chunk maps to an S3 key, thousands of range-GETs can execute in parallel, achieving high bandwidth \cite{aws2023zarr}. Latency for interactive slice retrieval falls to the low milliseconds. Write throughput scales similarly via thousands of concurrent PUTs (one per chunk), enabling real-time ingestion at modern beamlines without seeing too many performance drawbacks.

\subsubsection{Growing ecosystem}
Researchers across various fields have adopted Zarr; GDAL provides a native driver for geospatial rasters \cite{gdal2024zarr} while the bioimaging community standardized on OME-Zarr for petabyte-scale microscopy archives \cite{moore2023ome}. A NumFOCUS-backed governance model and a public Zarr-specs RFC process ensure long-term stability in the system \cite{zarrspecv3}.

Zarr’s chunk-per-object design aligns perfectly with the partial-read workloads studied in this report. However, its performance depends on chunk size, sharding, and metadata unification.

\subsection{Apache Parquet}
\label{sec:apache-parquet}
Apache Parquet is an open, columnar storage format originally developed at Twitter and Cloudera to bring Google Dremel–style analytics to the Hadoop ecosystem. The Parquet format organizes a file into one or more \emph{row groups} where, within each row group, every column is stored contiguously as a \emph{column chunk} and encoded with lightweight compression and a dictionary encoding scheme. Because the system only reads the required columns and the row groups that satisfy a filter predicate, Parquet dramatically reduces I/O volume for wide, sparse tables. Parquet supports several compression codecs, such as Snappy, GZIP, deflate, and BZIP2 \cite{vohra2016apache}. Within each row group, Parquet applies column-specific encodings—such as dictionary or run-length encoding—and independent compression, further shrinking the on-disk footprint and amplifying the format’s I/O-reduction advantage.

\subsubsection{Cloud-native performance}
On Amazon S3, each row group is laid out as a large (typically 64–256 MB) contiguous byte range, allowing clients such as Apache Arrow’s vectorized reader or AWS Athena to fetch gigabyte-scale slices with a single Range GET. The AWS Athena pricing page states that converting data to compressed, columnar formats like Parquet “can save up to 90 \% per query and improve performance” compared with raw CSV \cite{aws_athena_pricing}.

\subsubsection{Ecosystem adoption}
Parquet has become the default on-disk file format throughout today’s analytics stack. Apache Spark uses Parquet as the \emph{default data source}, and Apache Iceberg likewise keeps its immutable data files in Parquet \cite{iceberg_spec}. In the in-memory layer, Pandas and Apache Arrow provide first-class readers/writers for Parquet \cite{pandas_read_parquet}. Primary cloud analytics services ingest Parquet natively, including Google BigQuery \cite{bq_parquet}, AWS Glue \cite{aws_glue_parquet}, and Amazon Athena \cite{aws-athena-columnar}.

Parquet’s columnar design is perfect for the tabular metadata portion of scattering experiments, where scientists frequently select a handful of columns across millions of rows. However, its row-group granularity (tens of MB) and lack of native $n$-D chunking can inflate latency for small pixel tiles.


\subsection{Apache Arrow / Feather}
\label{sec:apache-arrow-feather}

Apache Arrow is an open, columnar \emph{in-memory} format that stores each column in a contiguous, 64-byte aligned buffer, enabling data to be accessible across languages and processes with \emph{zero copy} \cite{arrow_format}. Arrow, therefore, removes the (de) serialization overhead typical of row-oriented interchange formats such as CSV, JSON, or Avro, and it guarantees forward compatibility via a self-describing schema embedded in every record batch. Feather persists the same IPC message stream to disk, adding a footer with random-access offsets and optional LZ4/ZSTD compression \cite{arrow_feather_doc}. Because Feather pages are memory-mappable, tools like Pandas and Polars can open multi-gigabyte tables in milliseconds without parsing text or allocating intermediate buffers.

\subsubsection{Performance of Arrow utilizing Feather}
McKinney and Richardson's study shows that Feather V2 using LZ4 or ZSTD compression can outperform Parquet (with Snappy) in read and write throughput on large, mixed-type datasets. In their benchmarks on a 1.52 GB loan‐performance table and a 2.54 GB taxi‐trip table, reading compressed Feather V2 was faster than reading Snappy-compressed Parquet, and writing compressed Feather V2 was quicker than writing uncompressed Parquet \cite{feather_v2_urs}. This indicates that simpler, high-speed codecs (LZ4/ZSTD) plus Arrow’s IPC layout can substantially reduce end‐to‐end I/O time. These CPU and transport gains make Arrow attractive for full-scan analytics and machine-learning pipelines in the cloud.

\subsubsection{Ecosystem adoption}
Arrow/Feather underpins the binary interchange layer of pandas \cite{pandas2024}, R’s arrow package \cite{arrowR2024}, and the Polars DataFrame engine \cite{polars2025}. Cloud warehouses, including Snowflake and Google BigQuery, expose high-bandwidth Arrow Flight connectors, while Apache Spark, Flink, and Kafka Connect use Arrow internally to shuffle columnar batches \cite{vohra2016apache}.

Arrow’s zero-copy design promises the \emph{lowest CPU overhead} for bulk reads. Still, its record-batch grouping (typically 64 kB–8 MB) means smaller slices cannot be fetched better in some cases than the surrounding batch.

\subsection{ROOT / RNTuple}
\label{sec:root-rntuple}
ROOT is an object-oriented C++ framework developed at CERN to handle the petabyte-scale data streams of high-energy-physics experiments \cite{blomer2020evolution}. Its core storage abstraction, \emph{TTree}, stores events as rows and detector variables as \emph{branches}. The format splits each branch into contiguous \emph{baskets}, allowing readers to load them independently. This column-friendly layout lets analysis jobs load only the needed branches, minimizing I/O and deserialization overhead, a property directly relevant to slice-level scattering analysis.

\subsubsection{RNTuple redesign}
After two decades of incremental evolution, \emph{TTree} showed architectural limits for modern heterogeneous hardware and cloud storage. The RNTuple project, therefore, re-implements ROOT I/O with a stricter columnar layout, page-based compression, and a self-describing, versioned metadata footer \cite{blomer2020evolution}. Pages (\(\approx\) 8–16 kB) are grouped into clusters so that entirely columnar reads issue a single contiguous request, while sparse event selections fetch only the referenced pages. By decoupling metadata from data pages, RNTuple avoids rewriting the entire file when appending events, which is critical for streaming detectors and results in improved partial reads.

\subsubsection{Object-store back-end}
Through the generic \emph{RPageSource} interface, pages can reside in POSIX files, over HTTP(S), or as individual S3 objects \cite{rootRNTuple2025}. Scaling studies by Blomer showed near-linear throughput up to \(\mathcal{O}(10^{2})\) concurrent readers on a >100‐core HPC cluster served by a DAOS object store, achieving an aggregated read rate above 35 $\text{GB\,s}^{-1}$ before the storage system became the bottleneck \cite{blomer2024root}.

This architecture thus provides high-throughput, scalable, and selective access to petabyte-scale datasets, whether on HPC or in the cloud, making RNTuple a promising foundation for modern, slice-level scattering analyses.


\section{Compression Algorithms Reviewed}
\label{sec:compression-algorithms}
Lossless compression is a first-order lever for both performance and cost in cloud object–store workflows. Smaller chunks reduce S3 egress and request fees, while faster codecs shorten the latency that dominates interactive partial reads in synchrotron experiments.

We therefore focus on three open-source codecs that form a spectrum of trade-offs: \emph{gzip/DEFLATE} (high ratio, high CPU), \emph{LZ4} (low ratio, ultra-low latency), and \emph{Zstandard} (\emph{zstd}, balanced). HDF5, Zarr, Parquet, and Arrow natively support all of them, remain patent-free, and offer mature implementations on every central platform, which is critical for reproducible HPC benchmarking.

\subsection{gzip}
\label{sec:compression-gzip}
GNU \emph{gzip} has been the default lossless compressor on Unix‐like systems since 1992. RFC 1952 formalizes gzip’s file format and header/trailer structure, and those specifications have remained patent-free and backward-compatible across three decades of scientific workflows \cite{deutsch1996rfc1952}.

\subsubsection{Algorithmic design}
The compressor implements the \emph{DEFLATE} scheme, a cascade of LZ77 sliding-window substitution followed by static/dynamic Huffman coding tunable via nine quality levels that trade compression time for ratio. Level 6 is the GNU default, while level 1 sacrifices a \(\approx\) 30\% ratio to gain 3–4× speed \cite{deutsch1996rfc1952}.

\subsubsection{Performance on scientific data}
Benchmarks on floating-point climate and remote-sensing datasets stored in netCDF-4/HDF5 show typical space savings of 1.6–2.2× at levels 4–6. However, this did show that with compression, the CPU costs were 2–5× higher than LZ4, and decompression throughput that saturates a single 10 Gb s$^{-1}$ core around 500 MB s$^{-1}$ \cite{delaunay2019evaluation,chen2023fcbench}.

\subsubsection{Integration with chunked formats}
Gzip has native support in the five different backends we will test: HDF5, netCDF-4, Parquet, and Arrow IPC. Because gzip compresses each chunk independently, its compression ratio varies with chunk size and needs to be considered during these experiments. In our experiments, we use Gzip as a “high-ratio, high-CPU” reference, and its "old" ecosystem guarantees consistent behavior across all five storage back-ends. It's well-characterized latency overhead provides a clear baseline against which to measure the partial-read performance gains of newer codecs like Zstandard and LZ4.

\subsection{LZ4}
\label{sec:compression-lz4}
LZ4 emerged in 2011 as a lightweight derivative of the Lempel–Ziv (LZ77) family, designed to maximize streaming throughput while keeping memory overhead to a minimum. Its open-source framing format defines a compact header, provides optional block and content checksums, and employs a skippable frame mechanism, allowing adding new features without breaking older decoders. These attributes have led to widespread adoption in operating systems, high-performance storage engines, and scientific data formats where sub-millisecond decode latency is critical.

\subsubsection{Algorithmic profile}
The codec emphasizes extremely fast byte-wise parsing and a greedy match-finder that limits back-references to 64 kB. Because of this, the compression runs at $>$500 MB s$^{-1}$ per core while decompression routinely exceeds 2–3 GB s$^{-1}$, albeit with modest ratios (1.2–1.7× on floating-point data) \cite{lz42025,7440278}. A high-compression variant \texttt{lz4hc} improves the ratio by $\sim$15 \% at 3–5× the CPU cost.

\subsubsection{Empirical results on scientific workloads}
Almeida \emph{et al.} compared LZ4 with ZLIB on ROOT HEP and climate grids, reporting 1.0–1.2 GB s$^{-1}$ decompression (versus 120 MB s$^{-1}$ for ZLIB) at the expense of only a 5–10 \% ratio loss \cite{almeida2014two}. The VLDB’24 “FCBench” study recently measured the CPU variant bitshuffle with LZ4 across 33 floating-point datasets. The study showed that it sustained 0.9 GB s$^{-1}$ compression and 1.2 GB s$^{-1}$ decompression on 64 kB blocks while achieving a median compression ratio of 1.43 \cite{chen2023fcbench}.

\subsubsection{Integration in storage formats}
LZ4 filters are first-class options in HDF5 (\texttt{H5Z\_LZ4}), Zarr v3, Parquet, and Arrow IPC. Because the LZ4 64 kB match window limits cross-chunk redundancy, chunk sizes above 1–2 MB yield diminishing returns, which for this study will align well with S3 request-cost sweet spots.

LZ4 represents the “low-latency, low-CPU”, serving as the low-latency reference with gzip and zstd in our benchmarks. The study will quantify how much compression ratio we can trade for sub-second partial reads without materially increasing monthly S3 storage costs.

\subsection{zstd}
\label{sec:compression-zstd}
Zstandard (\emph{zstd}) was released by Collet in 2016 and standardized by the IETF as RFC 8878 \cite{collet2021rfc8878}. It combines an LZ77 dictionary back-reference engine with Finite-State Entropy (FSE) coding. It supports window sizes up to 128 MiB and offers 23 quality levels ($-7$ to 22), optional long-range mode, and trained dictionaries (negative values activate ultra-fast modes that trade ratio for speed). Decompression speed is deliberately kept almost constant across levels, whereas compression trades CPU for ratio.

\subsubsection{Throughput and ratio characteristics}
According to the \emph{zstd} manual, the fastest compression mode exceeds 200 MB s$^{-1}$ per core, while the decoder sustains $>$500 MB s$^{-1}$ per core on commodity x86 CPUs \cite{zstdman2025}.

Promberger \emph{et al.}\ measured \emph{zstd} level 2 on a 4.9 GB LHCb collision dataset and found that its \emph{compression} throughput was roughly 2–3 × higher than that of \emph{zlib} level 2 while achieving an almost identical compression ratio, \cite{promberger2023characterization}.

Delaunay et al. found that “Shuffle + Zstandard-2” compresses CFOSAT and SWOT remote-sensing files about 1.4 × to 7 × faster than the mission’s baseline “Shuffle + Deflate-3/4”. It delivers virtually identical space savings, accelerating decompression by up to seven-fold \cite{delaunay2019evaluation}. Across the full 33-dataset \emph{FCBench} suite, the VLDB’24 study reports that a \emph{bitshuffle+zstd} pipeline achieves a harmonic-mean compression ratio of 1.47, while sustaining compression and decompression throughputs of $\sim1.4\ \text{GB\,s}^{-1}$ and $\sim1.3\ \text{GB\,s}^{-1}$, respectively  \cite{chen2023fcbench}.

\subsubsection{Integration in scientific formats}
zstd is a first-class codec in Parquet, Arrow IPC, and available as extensions for HDF5 and Zarr v3. With FSE contexts resetting per block, 1–4 MiB chunks maximize the ratio without inflating S3 request counts. Zstd occupies the “balanced ratio/latency” middle ground between gzip (high ratio, high CPU) and LZ4 (low ratio, low CPU) in the study.

\subsection{Small-slice interactive reads}
At many beamlines, an \emph{interactive slice} is a reconstructed tomographic plane or detector region of interest. For example, the GigaFRoST camera at SLS–TOMCAT streams \(2016\times1800\) px, 16-bit projections at \(7.7\,\mathrm{GB\,s^{-1}}\), so a single projection (or a stack of a few tiled ROIs) naturally falls in this size window \cite{celcer2018gigafrost}. Likewise, the APS nanoprobe workflow achieves live neural-network inference on \(512\times512\) diffraction frames at \(100\,\mathrm{Hz}\) (one frame every \(10\,\mathrm{ms}\)), establishing a practical millisecond-to-sub-second latency budget for feedback loops \cite{babu2023deep}.

Partial reads are equally critical \emph{after} acquisition. For example, strain- and stress-mapping routines integrate Bragg peaks only within narrow azimuthal sectors (\(\Delta\chi\approx5^{\circ}\)) or select a handful of detector tiles, discarding the rest of the frame. High-energy diffraction microscopy at APS, for instance, reconstructs grain-resolved strain tensors by repeatedly loading just those angular wedges that intersect a given grain’s Debye–Scherrer rings, cutting I/O by an order of magnitude \cite{lienert2011high}. These workflows, therefore, see many benefits of simply loading in partial slices of data rather than complete datasets.

\subsection{Full-dataset sequential scans}
A \emph{full-dataset scan} means streaming every projection or event record, typically \(10^{2}\)–\(10^{3}\,\mathrm{GB}\) per tomographic run or several terabytes per serial-crystallography campaign. Full dataset scans, therefore, require moving data from storage to the compute tier in a single, sequential pass.

Complete reads underpin high-fidelity analyses that cannot tolerate missing frames. Iterative phase-retrieval and filtered back-projection algorithms in tomography require the entire sinogram for each refinement cycle. In serial femtosecond crystallography, clustering, indexing, and Monte Carlo integration need millions of patterns to converge on accurate structure factors \cite{maiden2009improved}. Full dataset scans are also required when, for example, doing \emph{reference re-processing} of an experiment. Tasks such as simply displaying the image in one continuous video require loading the entire data set. Sequential scans saturate available bandwidth, compression efficiency, and parallel read pipelines dominate time-to-solution.


\subsection{Metadata-driven queries}
A \emph{metadata query} retrieves only descriptive information, sample-environment logs, scan parameters, detector geometry, or a thin set of columns/branches without touching the heavy image stacks. Typical payloads are \(\mathcal{O}(10^{1}\!-\!10^{3})\,\mathrm{kB}\), which a live beamline dashboard may issue tens to hundreds of such queries per second during an experiment.

Synchrotron and neutron facilities increasingly push raw detector frames straight into object stores (AWS S3, Ceph, MinIO) to curb on-premise costs and enable remote collaboration. Brookhaven’s NSLS-II, for example, operates a {\small 5 PB} MinIO cluster exposed via the S3 API; the Bluesky acquisition pipeline writes NeXus event documents there, and downstream notebooks read them over the WAN \cite{Lancon2022}. The UK’s Rutherford Appleton Laboratory offers the {\it ECHO} Ceph object store, providing {\small 100 PB} of S3 capacity that underpins IRIS cloud analysis services and beamline portals \cite{ECHO2025}. In these environments, transferring even a few gigabytes across a WAN to inspect scan headers is untenable, especially when lightweight, metadata-only queries can satisfy the request.


\section{Summary and Link to Problem Statement}
\label{sec:summary-problem-statement}

The preceding background underscores how accelerating detector output and evolving collaboration models outpace traditional HPC storage solutions while object storage introduces its latency-cost trade-offs. The key insights, mapped directly to the thesis problem, are:

\begin{itemize}
  \item \textbf{Escalating data rates at modern synchrotron and neutron facilities:} Multi-GB\,s$^{-1}$ streams and multi-TB experiments are now routine, stressing conventional storage and analysis pipelines.
  \item \textbf{Mismatch between traditional HPC file systems and interactive beamline needs:} Lustre and GPFS deliver excellent bulk throughput, but they incur high latency and overload metadata servers when scientists issue thousands of small, random reads for on-beamline feedback.
  \item \textbf{Cloud object storage offers scale and global access, \emph{but at a cost}:} AWS S3 provides unlimited capacity and pay-as-you-go economics, but at the cost of introducing higher per-request latency and billing overhead, making naïve monolithic (HDF5/NeXus) deployments inefficient.
  \item \textbf{Rise of cloud-native, chunk- or column-based formats:} Zarr, Parquet, Arrow/Feather, and ROOT/RNTuple reorganize data into independently addressable objects, promising lower slice-read latency and better cost control.
  \item \textbf{Central research question:} \emph{How do HDF5/HSDS, Zarr, Parquet, Arrow/Feather, and ROOT/RNTuple compare, under identical compression settings, on latency, throughput, compression ratio, and AWS cost for partial-retrieval workloads?}
  \item \textbf{Thesis contribution and objectives:} Prototype ingestion for all five formats, quantitative benchmarking across small-slice and full-scan patterns, and a decision matrix translating results into actionable best practices.
  \item \textbf{Practical significance for beamline scientists and data engineers:} Enables near-real-time experimental feedback, reduces cloud spend, and informs the design of next-generation scientific data platforms.
\end{itemize}

\subsection{Data Ingestion and Configuration}
Two representative datasets were used for the benchmarking experiments: a tabular dataset (1M × 20) and a 3D dense array (1 TB), simulating typical scattering data produced in synchrotron and neutron facilities, and analysis of results. The datasets are ingested into the five storage formats, ensuring that each format is optimal for chunking and compression. For instance, HDF5/HSDS and ROOT/RNTuple required special configurations for handling hierarchical and event-based data, respectively, while Zarr and Parquet utilized chunked and columnar layouts, respectively. The datasets are then compressed using the three compression algorithms (gzip,  LZ4, and zstd), each selected for its different trade-offs between compression efficiency, CPU utilization, and throughput.

\subsection{Experimental Parameters and Workloads}
The primary aim of the experiment is to compare the performance of the five storage formats under two different access patterns: small-slice reads and full-dataset sequential scans. These access patterns reflect typical usage scenarios in beamline experiments, where scientists need quick access to specific data slices for real-time feedback or to process entire datasets for post-experiment analysis.

\subsubsection{Small-Slice Reads}
In a small-slice access pattern, data retrieval is performed on small slices (ranging from 2 to 8 MB) representing portions of multidimensional data, such as individual detector channels or angular segments of diffraction data. It will also represent, for example, grabbing 10 rows from the tabular dataset. This pattern simulates the real-time, interactive data retrieval during and after experiments.

\subsubsection{Full-Dataset Sequential Scans}
The entire dataset is accessed sequentially in this pattern, simulating bulk data processing for tasks such as full tomographic reconstructions or machine learning inference. This pattern stresses the storage system's bandwidth capacity, requiring high throughput to process large volumes of data efficiently.

\subsection{Performance Metrics and Evaluation Criteria}

The performance of each storage format is evaluated using the following metrics:
\begin{itemize}
  \item Read/Write Latency: The time it takes to retrieve a small slice or the entire dataset.
  \item Throughput: The data transfer rate, measured in MB/s, for both small-slice reads and full-dataset scans.
  \item Compression Efficiency: The ratio of compressed data size to the original data size and the CPU usage associated with compression and decompression.
  \item Cost of Ownership: The total cost of using each format in AWS S3, including request fees (GET, PUT), egress charges, and storage costs.
\end{itemize}


\subsection{Statistical Analysis and Evaluation}
The data collected from the experiments is analyzed using statistical methods such as one-way ANOVA to compare the performance of the storage formats across different metrics. Post-hoc tests, such as Tukey HSD, are applied to identify significant differences between the storage solutions. Effect sizes and confidence intervals are calculated to assess the statistical significance of the results, ensuring that the conclusions drawn from the analysis are reliable.


\section{Data Collection}
\label{sec:dataCollection}
The data‐collection plan for this thesis centers on two \emph{synthetically generated} datasets that statistically replicate the size, structure, and access patterns of real synchrotron and neutron experiments. Generating the datasets on demand (rather than distributing raw beamline files) avoids licensing constraints and guarantees that every experiment can be reproduced bit-for-bit.

\subsection{Data Sources}
\begin{itemize}
  \item \textbf{Dense 3-D array ($\sim$1 TB)}
        A $4148\times4362\times13{,}800$ int32 volume that mimics the axial resolution, noise spectrum, and grey-level histograms of the EIGER2 X 16M \cite{dectris_eiger2xe16m}. Voxels are synthesized with a mixed Poisson–Gaussian detector model followed by ring-artifact modulation.
  \item \textbf{Tabular ($10^{6}\!\times\!20$ rows)}
        A synthetic data‐generation pipeline is implemented that draws each of the 20 columns, such as motor positions, beam energy, exposure time, temperature, stress, strain, etc.
\end{itemize}

The Python generators and seed values are included in the project repository, allowing any reader to recreate identical input objects with a single command.


\subsection{Sampling Strategy}
Both datasets are accessed under two patterns: interactive slice and full–dataset scan. For the slice workload, the 3-D volume is deterministically divided into contiguous sub-volumes of \(\,1\text{–}50\,\mathrm{MB}\), and each tile is aligned so that it occupies exactly one storage-format chunk; every system therefore retrieves the same byte ranges, isolating per-request latency.

For the scanning workload, the entire \( \sim\!1\,\mathrm{TB} \) tomography cube (and the whole analysis table) is streamed sequentially, allowing sustained throughput, parallel-read scalability, and compression efficiency to dominate the timing profile. No down-sampling or filtering is applied in either pattern, ensuring that genuinely large-scale behavior is exposed.




\subsection{Instrumentation and Metric Logging}
\begin{enumerate}
  \item \textbf{Client-side parameters} log start/stop timestamps, bytes transferred, and CPU cycles for every GET/PUT
  \item \textbf{CloudWatch and S3 Server Access Logs} capture server-side latencies, throttle events, and per-request diagnostics for cross-validation.
  \item \textbf{Cost} is sourced from hourly Cost and Usage Reports (CUR), attributing storage GB-days and request counts
\end{enumerate}



\subsection{Validity and Reliability Measures}
\begin{itemize}
  \item \textbf{Warm-up runs}: the first ten iterations of the caches and TCP pools are discarded.
  \item \textbf{Replication}: every \{\emph{format, codec, pattern}\} tuple is executed $n=50$ times. Medians and P95s are reported with 95 \% CIs.
\end{itemize}



\section{Data Analysis Methodology}
\label{sec:plannedDataAnalysis}
The analysis phase will transform the raw data collected during benchmarking into statistical evidence that discriminates between storage–compression combinations and translate the findings into an actionable decision matrix for beamline workflows.

\subsection{Pre-Processing and Screening}

All raw logs (\texttt{CSV} from the Python harness and \texttt{JSON} from CloudWatch Insights) will be merged on the composite key \texttt{\{format,\, codec,\, pattern,\, dataset\,run\_id\}} in a Pandas. Outliers beyond \(\pm3\sigma\) of the median deviation will be removed to protect parametric tests.

\subsection{Assumption Checks}

For each performance metric, median latency, 95$^{\text{th}}$-percentile latency, throughput, compression ratio, CPU time, and residuals will be assessed for normality (Shapiro–Wilk, $n>50$) and Levene’s test. Q–Q plots will complement the numeric tests because Shapiro–Wilk can over-reject at large sample sizes \cite{razali2011power}.

\subsection{Primary Hypothesis Tests}

\begin{itemize}
    \item If assumptions hold, a \textbf{one-way ANOVA} will be performed separately for each access pattern, treating \emph{storage format} (five levels) as the independent factor.
    \item If either assumption fails, the non-parametric \textbf{Kruskal–Wallis} test will replace ANOVA.
    \item The global null \(H_{0}:\mu_{M,A}=\mu_{M,B}\;\forall\,A,B\) will be rejected at \(\alpha = 0.05\).
\end{itemize}

\subsection{Post-Hoc Comparisons}

Significant omnibus results will trigger pairwise contrasts:

\begin{itemize}
  \item \emph{Parametric branch}: Tukey HSD with family-wise error control.
  \item \emph{Non-parametric branch}: Dunn’s test with Holm adjustment.
\end{itemize}

Effect sizes will accompany $p$-values: \(\eta^{2}\) for ANOVA and Cliff’s \(\delta\) for Kruskal–Wallis pairs, providing practical significance alongside statistical significance \cite{cohen2013statistical}.


\subsection{Multi-Criteria Structure}
The evaluation framework operationalizes the thesis goal of delivering \emph{actionable guidance} to beamline scientists and data engineers by translating raw benchmark results into a transparent, multi-criteria scorecard.

\begin{enumerate}[label=\textbf{F\arabic*.}, leftmargin=*, itemsep=0.2em]
  \item \textbf{Performance}
        \begin{enumerate}[label=\alph*)]
          \item Median slice-read latency
          \item 95$^{\text{th}}$-percentile latency
          \item Sequential-scan throughput
        \end{enumerate}
  \item \textbf{Compression Efficiency}
        — space-savings ratio versus raw HDF5.
  \item \textbf{CPU Overhead}
        — mean user+sys time per GiB read/write on AWS EC2.
  \item \textbf{AWS Cost}
        — 10 TB retrieved
  \item \textbf{Ecosystem Maturity}
        — qualitative score (0-1) derived from GitHub activity, maintainers, language bindings, and release cadence.
\end{enumerate}

Metrics in F1–F4 are normalized to \([0,1]\) via min-max scaling; F5 is mapped linearly from the 1–5 rubric.

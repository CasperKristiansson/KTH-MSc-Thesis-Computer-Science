\begin{scontents}[store-env=abstracts,print-env=true]
Modern synchrotron and neutron beamlines stream at gigabytes per second, turning single experiments into multi-terabyte datasets and exposing latency limits of parallel file systems. This thesis evaluates which cloud-native storage solution on AWS S3 minimizes slice-level latency while preserving scan throughput and controlling costs. Four back ends (HDF5 via HSDS, Zarr v3, TileDB, ROOT/RNTuple) and three codecs (gzip, LZ4, zstd) are benchmarked on a 20 GiB, $\sim$1{,}300-frame detector stack under two workloads, random single-frame reads and full sequential scans. Client timings are analyzed on a log scale with dependence-robust confidence intervals, with S3 request counts and stored size providing context.

Results are descriptive and session-conditional. For interactive slices, Zarr is fastest with zstd (GM $\approx$155 ms) and with LZ4, where TileDB wins with gzip. For full scans, TileDB delivers 2.2–3.2$\times$ higher throughput than Zarr across codecs (e.g., zstd $\approx$1.06 GiB/s for 20 GiB). ROOT is slow for frame-random reads despite a few GETs, indicating single-object paging and decode overheads. HDF5/HSDS trails on slice latency and scan throughput; with LZ4, it stored 19.17 GiB versus Zarr 10.40 GiB for the same payload.

The contribution is a reproducible AWS-native method and a decision matrix: choose Zarr+zstd when slice latency dominates and choose TileDB+zstd/LZ4 when throughput dominates.
\end{scontents}

\chapter{Introduction}
\label{ch:introduction}
Modern synchrotron and neutron experiments generate multi-GiB/s multidimensional detector data. Parallel file systems (Lustre, \gls{GPFS}) deliver high throughput for large, contiguous I/O but respond poorly to thousands of small, partial reads required for on-beamline feedback. Cloud object stores such as Amazon S3 provide elastic capacity and global access, but add per-request latency and fees. Monolithic file-container formats (e.g., \gls{HDFfive}/NeXus) map poorly to object stores without additional indirection.

Cloud-native layouts—chunked arrays (Zarr), fragmented dense/sparse arrays (TileDB), and tree/column layouts (\gls{ROOT}/\gls{RNTuple})—offer alternative trade-offs in latency, throughput, compression, CPU, and request intensity. This thesis provides a side-by-side evaluation of realistic scattering data on \gls{AWS}.


\section{Motivation and Context}
As synchrotron and neutron facilities have evolved, detector technologies and beamline instrumentation have driven data generation rates from megabytes to multiple gigabytes per second. Modern experiments frequently combine multiple detectors and scan axes, such as energy, angle, or polarization. This results in multidimensional datasets that can reach terabyte-scale within minutes, making `download-then-analyze` workflows impractical during beam time \cite{celcer2018gigafrost}.

\subsection{Limitations of Traditional HPC Storage}
Historically, researchers stored beamline data on parallel file systems such as Lustre or \gls{GPFS} and accessed it through \gls{MPIIO} or batch-oriented workflows. These systems perform well for large-block I/O but incur high overhead on thousands of small random reads typical of exploratory slices or metadata queries \cite{narayan2010characterization}. Maintaining on-premises \gls{HPC} arrays entails capital and operational expenditures, as well as additional network complexity.

\subsection{Emergence of Cloud-Native Storage Models}
Cloud object storage, most notably Amazon \gls{SThree}, is now widely used for scientific data. Object stores provide virtually unlimited, durable storage, global namespace access, and a pay‐as‐you‐go billing model that shifts capital costs to operational expenses. However, monolithic scientific formats such as \gls{HDFfive} or NeXus, initially designed for \gls{POSIX} filesystems that rely on byte-addressable seek semantics, are naively stored on \gls{SThree}, and every small slice triggers hundreds or thousands of \gls{HTTP} range-GET requests (\gls{SThree}’s emulation of those seeks). For \gls{SThree}, namespace access results in additional LIST/HEAD calls, which are billed per request.

Researchers have introduced a new generation of cloud-native data models to address these shortcomings. Zarr and related chunked layouts expose each array chunk as an independent object, enabling parallel GET/PUT; chunk size is configurable, and organizations tune chunking to balance object count and transfer efficiency \cite{moore2023ome}. Columnar storage formats such as Apache Parquet organize data in row groups and column stripes, pruning unneeded fields to reduce I/O usage \cite{ivanov2020impact}. TileDB provides dense and sparse array storage with tiled chunking and object-store backends, enabling parallel range reads/writes and reducing metadata and small-read overheads. In parallel, the high-energy physics community has extended \gls{ROOT}’s \gls{TTree} and \gls{RNTuple} abstractions to object-store backends, preserving branch-level selective reads \cite{abs-2107-07304}.

Each approach offers distinct trade‐offs in latency, throughput, compression efficiency, \gls{CPU} overhead, and cost. Although individual formats have been benchmarked in isolation or within specific domains, there is no comprehensive, side-by-side evaluation of realistic terabyte-scale scattering datasets on \gls{AWS}. Addressing this gap informs both beamline scientists seeking responsive, cost‐effective data access and data‐intensive computing engineers designing next‐generation, cloud‐native scientific platforms.

\subsection{Research Question}
\emph{How do four cloud storage backends—\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{RNTuple}—compare on \gls{AWS} for partial-retrieval workloads on a large scattering dataset under common compression (\texttt{gzip}, \texttt{lz4}, \texttt{zstd})?}

\section{Problem, Purpose, and Goals}
This section defines the problem, states the purpose, and lists the goals. It sets the basis for the comparisons used later in the thesis.

\subsection{Problem}
\label{sec:problem}
Handling large-scale scattering datasets on \gls{AWS} \gls{SThree} reveals several limitations in current data platforms. First, partial reads of beamline slices, such as retrieving a single detector channel or angular data segment, can result in high latency due to the need to perform hundreds, if not thousands, of GET operations and metadata lookups, leading to delayed experimental feedback. Secondly, existing prior prototype evaluations have focused on moderate‐scale workloads. There is limited empirical data on true terabyte-scale (1 TB+) scattering experiments. This thesis benchmarks each format on a single \SI{20}{\gibi\byte} detector dataset (\(\sim\)1{,}300 frames) to uncover performance, request behavior, and data ingestion considerations. Thirdly, the interaction between storage formats and compression algorithms (e.g., \texttt{zstd}, \texttt{lz4}, \texttt{gzip}) has not been systematically evaluated, making it unclear which format codec combinations best optimize latency and throughput for large-scale \gls{SThree}-based workflows. These industrial challenges raise questions for the data-intensive computing community: How can we systematically leverage and compare different storage backends to generate guidance for scientific users? Which combinations of performance and integration trade-offs matter most when designing cloud-native workflows for interactive, partial-retrieval use cases?


\subsection{Original problem and definition}
This thesis defines the original industrial problem as optimizing the retrieval of small, targeted data slices (e.g., a single angle’s worth of diffraction frames) from multi-terabyte scattering datasets stored on \gls{AWS} \gls{SThree}. “Partial retrieval” denotes reading the required byte ranges or object keys rather than entire files. The study targets cloud-native, object-store workflows.




\subsection{Scientific and engineering issues}
Generalizing beyond the narrow industrial case leads to several key research questions:

\begin{itemize}
 \item Which access patterns (e.g., small random reads vs.\ large sequential scans, metadata index scalability) stress each format’s architecture the most?
 \item How do different compression algorithms (\texttt{zstd}, \texttt{lz4}, \texttt{gzip}) interact with object-stored data, and how does it affect end-to-end latency and throughput?
\end{itemize}

These questions are directly relevant to ongoing research in \gls{HPC} and data-intensive computing, where cloud adoption continues to challenge traditional storage paradigms.

\subsection{Purpose}
Scientifically, the study quantifies trade-offs among latency, throughput, compression ratio, and request intensity for a realistic scattering workload on S3, using design-science methodology \cite{hevner2004design}. Outputs include a decision matrix and best-practice guidance.

Secondly, it aims to provide Scatterin AB with a practical, evidence-based framework to optimize its cloud-based data platform for large-scale synchrotron and neutron-scattering experiments. This work offers concrete guidance on minimizing latency for partial-read use cases, maximizing throughput, and controlling pay-as-you-go costs across varying access patterns.

\subsection{Goals}
This thesis develops an experimentally validated decision framework to guide the selection and configuration of cloud-native storage solutions for large-scale \gls{AWS} synchrotron and neutron-scattering datasets. To achieve this, the following sub‐goals are defined:

\begin{enumerate}
  \item \textbf{Prototype Development}
  \begin{itemize}
    \item Ingest a single \SI{20}{\gibi\byte} dense 3D detector stack (\(\sim\)1{,}300 frames) into four timed backends: \gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{RNTuple}.
    \item Implement consistent chunking and compression (\texttt{zstd}, \texttt{lz4}, \texttt{gzip}) to ensure fair comparisons across formats.
  \end{itemize}

  \item \textbf{Quantitative Benchmarking}
  \begin{itemize}
    \item Measure read latency for two patterns: full scan and random single‐frame reads.
    \item Record stored size, requests per GiB, and client timings; report geometric-mean latency/throughput and 95th percentiles.
  \end{itemize}

  \item \textbf{Decision Matrix and Guidelines}
  \begin{itemize}
    \item Synthesize results into a matrix correlating workload patterns (partial vs.\ bulk reads, compression) with format‐specific performance, and ease of integration.
    \item Formulate best‐practice recommendations ranked by measured latency, throughput, and requests per GiB.
  \end{itemize}
\end{enumerate}

\subsection{Research Questions (RQs)}
To structure the investigation, the following research questions are posed:

\begin{itemize}
  \item \textbf{RQ1:} Interactive latency: For random single-frame reads on S3, which backend and codec minimize geometric-mean latency and control $p_{95}$?
  \item \textbf{RQ2:} Bulk throughput: For full-dataset scans, which backend and codec maximize geometric-mean throughput with stable $p_{95}$?
  \item \textbf{RQ3:} Cost posture and mechanisms: How do layout and codec choices change GETs/GiB and stored size, and how do these factors explain client timings?
\end{itemize}

\section{Methodology and Scope}
This section outlines the benchmarking methodology and the study scope. It specifies datasets, workloads, metrics, and the delimitations for reproducibility.

\subsection{Research Methodology}
We use an \emph{experimental benchmarking} approach within a design–science framework to evaluate four timed storage backends on \gls{AWS} (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{RNTuple}). Apache Parquet is included as a pilot (ingest only, no timed runs). The benchmark dataset is a single dense detector stack of approximately \SI{20}{\gibi\byte} (\(\sim\)1{,}300 frames). Two workloads are evaluated: random single-frame reads and full scans. We report geometric-mean latency or throughput with dependence-robust 95\% confidence intervals and 95th-percentile checks. Detailed descriptions of infrastructure, randomization, logging, and estimator choices are provided in Chapter \ref{ch:methods} and the Appendix.


\subsection{Delimitations}
This thesis focuses exclusively on cloud-native, object-store–based workflows within the \gls{AWS} ecosystem. Specifically, four storage backends are \emph{timed}, and Apache Parquet is used in a pilot ingest-only experiment. Benchmarks use one dense 3D detector dataset ($\sim$20 GiB, $\sim$1{,}300 frames). The following boundaries apply:

\begin{itemize}
        \item \textbf{Cloud provider scope:} Only \gls{AWS} services (\gls{SThree}, \gls{ECtwo}) are considered. No experiments involve Azure, Google Cloud, or on-premises \gls{HPC} clusters.
        \item \textbf{Storage formats:} The study is limited to the four specified formats. Other emerging or domain-specific formats (e.g., Avro, \gls{ORC}, \gls{CBF}, NeXus variants) fall outside the scope.
 	      \item \textbf{Dataset:} Benchmarks cover a single 3D dense detector dataset.
        \item \textbf{Access patterns:} Evaluation targets full-dataset scans and random single-frame reads (\(\sim\)\SI{15.82}{\mebi\byte} per frame). This study excludes other patterns (e.g., random single-element lookups and real-time streaming ingestion).
        \item \textbf{Compression algorithms:} This study uses three widely used codecs (\texttt{zstd}, \gls{LZfour}, and \texttt{gzip}) and does not compare other options, such as Snappy, Brotli, bzip2, or ZFP.
\end{itemize}

These delimitations ensure a focused, reproducible comparison of core performance and cost trade-offs for large-scale scientific data storage in \gls{AWS}.

\section{Structure of the Thesis}

This thesis is organized into seven main chapters, followed by appendices:

\begin{description}
  \item[Chapter 1: Introduction] Presents the motivation, scope, research question, methodology overview, delimitations, and outlines the thesis structure.
  \item[Chapter 2: Background] Reviews scientific data challenges in synchrotron and neutron facilities, surveys traditional \gls{HPC} I/O and emerging cloud‐native formats (\gls{HDFfive}/\gls{HSDS}, Zarr, Parquet, TileDB, \gls{ROOT}/\gls{RNTuple}), and identifies gaps in existing benchmarks.
  \item[Chapter 3: Research Methodology] Details the experimental design: dataset selection, \gls{AWS} infrastructure setup, ingestion pipelines, access patterns, performance metrics, and statistical tests.
  \item[Chapter 4: Implementation] Describes prototype implementations for each storage backend, reproducible chunking and compression, and automation of ingestion and test workflows.
  \item[Chapter 5: Results and Analysis] Presents quantitative results, latency distributions, throughput curves, compression ratios, and \gls{TCO} estimates, followed by statistical comparisons and effect‐size interpretations.
  \item[Chapter 6: Decision Matrix and Discussion] Synthesizes findings into a format‐selection matrix, discusses trade‐offs, integration complexity, and sustainability implications, and provides guidelines for beamline scientists and data engineers.
  \item[Chapter 7: Conclusions and Future Work] Summarizes key contributions, reflects on limitations, and proposes directions for extending the study (e.g., \ multi‐cloud comparisons, additional compression algorithms, real‐time streaming ingestion).
  \item[Appendices] Include detailed benchmark logs, code snippets, and supplementary figures.
\end{description}

\chapter{Background}

Modern synchrotron and neutron facilities stream multi-GiB/s data, producing multi-terabyte experiments that strain large-block assumptions in traditional \gls{HPC} storage. Chapter \ref{ch:introduction} posed the core question: which cloud-native layout minimizes partial-read latency on \gls{AWS}? Building on that foundation, Sections \ref{sec:cloud-native-storage-models}–\ref{sec:compression-algorithms} introduce the five storage formats examined in this thesis: \gls{HDFfive} + \gls{HSDS}, Zarr, Parquet, TileDB, and \gls{ROOT} / \gls{RNTuple}. These file formats are matched with the three compression algorithms (\texttt{gzip}, \gls{LZfour}, \texttt{zstd}) that modulate their performance. Section \ref{sec:access-patterns-scattering} characterizes the access patterns typical of scattering analysis.





\section{Scientific Context and Workflows}
\label{sec:scientific-context-workflows}
Modern beamlines generate multi–GiB/s data streams and require selective, near-real-time inspection during beamtime.

\subsection{Scientific-Data Context}
\label{sec:scientific-data-context}
Synchrotron light sources and spallation or continuous-beam neutron facilities produce multi-megapixel frames at kilohertz rates, pushing raw data beyond \SI{10}{\giga\byte\per\second} \cite{eriksson2014diffraction}. High-speed area detectors, hybrid photon counters, and \gls{CMOS} cameras convert pulses into image sequences that accumulate to multi-\si{\tera\byte} per day.

Giant accelerator-based light and neutron sources act as kilometer-scale microscopes that let us “see through’’ centimeters of steel, polymers, or living tissue at kilohertz frame rates. By storing ultra-low-emittance electrons (or moderating proton-driven neutrons), the machines deliver beams that are \(\sim10^{10}\!-\!10^{12}\) times brighter than laboratory instruments, unlocking 3-D imaging and diffraction of virtually any material \cite{eriksson2014diffraction}. Each pulse is immediately converted into multi-megapixel images by high-speed area detectors, hybrid photon counters, \gls{CMOS} cameras, or time-pix neutron imagers. Capturing these data allows a single experiment to exceed \SI{10}{\giga\byte\per\second} of raw data.

These facilities have a direct impact on the industry. At the European Synchrotron Radiation Facility, X-ray tomography has revealed how expanded-polypropylene crash foams used in car bumpers collapse under load, informing design rules for next-generation impact absorbers \cite{carnegie2024uninterrupted}. Neutron radiography visualizes sub-second water build-up that strangles polymer-electrolyte fuel cells during winter cold starts, guiding stack architecture and heating strategies for fuel-cell vehicles \cite{yoshimune2024neutron}.


\subsubsection{Typical beamline architecture}
A beamline shapes the beam with mirrors, slits, and monochromators, then positions the specimen on a multi-axis stage. A high-speed detector records 2-D or 3-D data at up to thousands of frames per second. A \gls{DAQ} server buffers frames on local \gls{NVMe} \gls{SSD}s or a burst buffer and writes to storage. Historically, the stream targets a parallel file system (Lustre/\gls{GPFS}), but in recent years object-store workflows have been introduced as an alternative (Figure \ref{fig:beamline-journey}).

Modern beamlines already saturate local networks with sustained data streams of $\mathcal{O}(10^{2})$\,\si{\mega\byte\per\second} per instrument. For example, the Advanced Photon Source Upgrade anticipates \SI{172}{\mega\byte\per\second} per double sector and \SI{4}{\giga\byte\per\second} facility-wide \cite{veseli2019data}. Looking ahead, diffraction-limited storage rings are projected to drive detector outputs beyond \SI{10}{\giga\byte\per\second} and data volumes of $>\!\SI{10}{\tera\byte}$ per experiment, implying corresponding upgrades to storage and analysis pipelines \cite{eriksson2014diffraction}.

\subsubsection{Dimensionality of datasets}
Indexing a single 2-D detector frame by additional experimental coordinates turns it into a higher-dimensional data object. Each 2-D image becomes a slice in a stacked data cube, while the depth axis stores a third coordinate, such as a rotation angle, energy, or time (Figure \ref{fig:data-cube}). Because modern beamlines vary at least three independent axes, the raw $(x,y)$ detector image is naturally represented as a 4-D (or higher) array:

\begin{itemize}
  \item \textbf{Rotation or scan angle:} a full tomographic or serial-crystallography scan may step the sample (or detector) through $10^{2}$–$10^{4}$ projections to reconstruct 3-D real-space structure or space intensity maps (\emph{rotation} $\times$ \emph{energy} $\times$ \emph{time}) \cite{app11198868}.
  \item \textbf{Energy or wavelength:} in spectro-microscopy and \gls{EXAFS}, the microscope sweeps energy across an absorption edge. At the same time, a fast detector records images, producing hyperspectral cubes with \(\sim\)10–\(10^{2}\) energy points per angle or time step \cite{Briois:uc5005}.
\end{itemize}

When these axes are combined, experiments can generate 5-D or 6-D datasets; for example, a $2048\times2048$ detector recording 1800 rotation angles, 50 energy points, and 20-time delays already contains $\sim150\times10^{9}$ pixels ($\approx$\,\SI{300}{\giga\byte} at 16-bit depth). These arrays enable multivariate analyses but impose heavy storage and I/O demands. Some beamlines further append polarization, external field strength, or environmental parameters (temperature, pressure, electrochemical potential), further increasing data dimensionality and storage complexity.

\subsubsection{Real-world automotive example}
The automotive industry uses neutron radiography to visualize water and ice formation within polymer-electrolyte fuel-cell stacks during rapid cold starts. The study used an operational neutron imaging system to map liquid distribution in a Toyota single cell down to sub-second time scales, informing design tweaks that mitigate performance losses \cite{yoshimune2024neutron}.


\subsection{Experimental Workflows \& Feedback Loops}
\label{sec:experimental-workflows-feedback-loops}
Beam time at synchrotron and neutron facilities is scarce and expensive. Experiments must, therefore, include a \emph{closed data loop} in which raw detector frames are reconstructed, inspected, and, if necessary, used to steer the scan while the sample is still in the beam. A study showed that streaming projections from the beamline to an \gls{HPC} cluster could deliver slice reconstructions within seconds, enabling autonomous adjustment of exposure, angle range, or focus during tomography scans \cite{Bicer2017RealTime}.

At Shanghai Synchrotron Radiation Facility, automated pipelines tied into the metadata catalog provide progress notifications and interactive dashboards for real-time feedback \cite{wang2024accelerating}.

\subsubsection{Implications for the storage stack}
\begin{itemize}
  \item \textbf{Latency}: scientists often request slices of data (quick-look radiographs or azimuthal-integrated diffraction rings). Data retrieval times must stay in the sub-second regime to keep up with the experiments.
  \item \textbf{Throughput}: full 3-D reconstruction or machine-learning inference may pull hundreds of contiguous gigabytes at the end of a scan, often includes burst bandwidths of $\ge\!\SI{10}{\giga\byte\per\second}$.
  \item \textbf{Scalability \& concurrency}: remote teams viewing the same dataset and automated QC pipelines often need simultaneous small-read streams. Monolithic single-file layouts trigger many Range-GETs per slice and cannot exploit per-chunk concurrency.
  \item \textbf{Online analysis}: real-time processing pipelines (e.g., streaming reconstruction, AI-driven feature extraction) consume data as it arrives. Storage must support continuous, low-overhead partial reads and write-through metadata indexing to feed live analytics without waiting for scan completion.
\end{itemize}

These workflow pressures motivate the performance metrics and storage formats evaluated in this thesis.

\subsubsection{Small-slice interactive reads}
At many beamlines, an \emph{interactive slice} is a reconstructed tomographic plane or detector region of interest. For example, the GigaFRoST camera at \gls{SLS}--\gls{TOMCAT} streams \(2016\times1800\) px, 16-bit projections at \SI{7.7}{\giga\byte\per\second}, so a single projection (or a stack of a few tiled ROIs) naturally falls in this size window \cite{celcer2018gigafrost}. Likewise, the APS nanoprobe workflow achieves live neural-network inference on \(512\times512\) diffraction frames at \(100\,\mathrm{Hz}\) (one frame every \(\SI{10}{\milli\second}\)), establishing a practical millisecond-to-sub-second latency budget for feedback loops \cite{babu2023deep}.

Partial reads are equally critical \emph{after} acquisition. For example, strain- and stress-mapping routines integrate Bragg peaks only within narrow azimuthal sectors (\(\Delta\chi\approx5^{\circ}\)) or select a handful of detector tiles, discarding the rest of the frame. High-energy diffraction microscopy at APS, for instance, reconstructs grain-resolved strain tensors by repeatedly loading just those angular wedges that intersect a given grain’s Debye–Scherrer rings, cutting I/O by an order of magnitude \cite{lienert2011high}.

\subsubsection{Full-dataset sequential scans}
A \emph{full-dataset scan} means streaming every projection or event record, typically \(10^{2}\)–\(10^{3}\,\mathrm{GB}\) per tomographic run or several terabytes per serial-crystallography campaign.

Complete reads underpin high-fidelity analyses that cannot tolerate missing frames. Iterative phase-retrieval and filtered back-projection algorithms in tomography require the entire sinogram for each refinement cycle. In serial femtosecond crystallography, clustering, indexing, and Monte Carlo integration need millions of patterns to converge on accurate structure factors \cite{maiden2009improved}. Full-dataset scans also support \emph{reference reprocessing} and video-style visualization, where sequential reads saturate available bandwidth and compression efficiency, and parallel read pipelines dominate time-to-solution.


\subsubsection{Metadata-driven queries}
A \emph{metadata query} retrieves only descriptive information, sample-environment logs, scan parameters, detector geometry, or a limited set of columns/branches without accessing the large image stacks. Typical payloads are \(\mathcal{O}(10^{1}\!-\!10^{3})\,\mathrm{kB}\), which a live beamline dashboard may issue tens to hundreds of such queries per second during an experiment.

Synchrotron and neutron facilities increasingly push raw detector frames straight into object stores (\gls{AWS} \gls{SThree}, \gls{Ceph}, \gls{MinIO}) to curb on-premise costs and enable remote collaboration. Brookhaven’s \gls{NSLSII}, for example, operates a {\small 5 PB} \gls{MinIO} cluster exposed via the \gls{SThree} \gls{API}; the Bluesky acquisition pipeline writes NeXus event documents there, and downstream notebooks read them over the \gls{WAN} \cite{Lancon2022}. The UK’s Rutherford Appleton Laboratory offers the \gls{ECHO} \gls{Ceph} object store, providing {\small 100 PB} of \gls{SThree} capacity that underpins \gls{IRIS} cloud analysis services and beamline portals \cite{ECHO2025}. In these environments, transferring even a few gigabytes across a \gls{WAN} to inspect scan headers is inefficient when lightweight, metadata-only queries can satisfy the request.



\section{Storage Foundations: HPC vs Object Stores}
\label{sec:storage-foundations}
This section contrasts parallel file systems with cloud object stores to highlight the core trade-offs in throughput and latency. We review how Lustre/GPFS/BeeGFS achieve high sequential I/O and why many small reads and metadata traffic degrade performance, then summarize \gls{SThree} semantics, costs, and latency.

\subsection{Traditional HPC Storage Paradigms}
\label{sec:traditional-hpc-storage-paradigms}
Parallel file systems such as Lustre, IBM \gls{GPFS}, and \gls{BeeGFS} stripe files across many disks and coordinate access with distributed locking, delivering high sequential throughput \cite{schwan2003lustre,schmuck2002gpfs}. These designs degrade under many small reads and heavy metadata traffic; production traces show small transfers dominate call counts and metadata can consume a large share of requests \cite{bez2022access}.

When the I/O profile shifts from a few large checkpoints to many small look-ups and interactive slices, these design assumptions break down. A study from the Summit and Cori supercomputers shows that small transfers (<\SI{1}{\mega\byte}) account for the overwhelming majority of read and write calls at both the file and process levels, and metadata operations can saturate metadata servers and become a primary scalability bottleneck \cite{bez2022access}.

\subsubsection{Parallel File Systems (Lustre, GPFS, BeeGFS)}
\label{sec:parallel-file-systems}
Lustre, IBM \gls{GPFS} (now Spectrum Scale) \cite{schmuck2002gpfs}, and \gls{BeeGFS} have dominated supercomputing storage for over two decades, consistently delivering throughput of hundreds of gigabytes per second. By striping data across hundreds of disks and coordinating access with distributed locks, these systems excelled at writing multi-gigabyte files sequentially. The same system, however, reveals hidden costs when workloads shift to small, random reads or to remote, \gls{WAN}-mounted access.


\paragraph{Architecture and striping model}
Classic \gls{HPC} file systems split responsibility between \emph{metadata servers} (\gls{MDS}) and many \emph{object/data servers} (\gls{OSS} in Lustre, \gls{NSD} servers in \gls{GPFS}, storage targets in \gls{BeeGFS}). Files are \emph{striped} across a few to hundreds of disks in multi-megabyte chunks. Doing this allows a single sequential read or write to optimize the bandwidth of an entire system. \gls{PFS} uses token-based distributed locking to keep \gls{POSIX} consistency on a shared-disk \gls{SAN} \cite{schmuck2002gpfs}. \gls{BeeGFS} achieves similar semantics over Ethernet by separating data and metadata and scaling the service.

\paragraph{Bulk Sequential I/O: High Throughput on Parallel File Systems}
Parallel file systems shine whenever an application issues long, contiguous transfers, checkpoints/restarts, volumes, and snapshots. NASA’s \emph{Pleiades} cluster still sustains, \(\sim\!1\)\,\si{\giga\byte\per\second} from disk for a single 512-rank IOR stream and bursts to \SI{9}{\giga\byte\per\second} when the same data are serviced out of the page cache \cite{6507507}. Modern flagships go far beyond that, where Los Alamos’ \emph{Trinity} Sonexion Lustre tops out near \SI{1.6}{\tera\byte\per\second} for a 78 PB pool \cite{osti_1367056}. Even a single E1000 \gls{OSS} inside NERSC’s \emph{Perlmutter} can saturate \SI{41}{\giga\byte\per\second} read and \SI{27}{\giga\byte\per\second} write to one \gls{OST} \cite{lockwood2024architecture}. These traits explain why parallel file systems remain the choice for bulk sequential scans and multi‐terabyte tomography stacks.

Lustre separates responsibilities between dedicated \emph{metadata servers} (\gls{MDS}) that keep inodes and directory state on one or more \emph{metadata targets} (MDTs) and multiple \emph{object‑storage servers} (\gls{OSS}) that deliver the bulk data stored on \emph{object‑storage targets} (\gls{OST}s).  Files are \emph{striped} across a configurable number of \gls{OST}s (stripe count) with a tunable stripe width, enabling a single sequential transfer to engage hundreds of disks in parallel. The design of flagship systems such as Oak Ridge’s Spider‐3 sustains more than \SI{1}{\tera\byte\per\second} aggregate read bandwidth \cite{braam2019lustre, oral2013olcf}.

IBM \gls{GPFS} employs a distributed \emph{token‑based locking} protocol to coordinate metadata and data updates across all nodes, persisting mutations in replicated journals so that failed servers can recover without full replays. This mechanism provides stronger resilience and copes slightly better with so‑called metadata “storms” than Lustre, though at the cost of a more complex recovery state \cite{schmuck2002gpfs}.

\paragraph{Weaknesses for many small reads}
Parallel file systems raise aggregate bandwidth by slicing every file across many Object Storage Targets (\gls{OST}s/\gls{NSD}s). When workloads flip from multi-GB checkpoints to thousands of $4$–$64$\,\si{\kilo\byte} reads, the same striping logic backfires when workloads issue thousands of sub-megabyte reads. Intel’s LUG-2018 “Small File I/O” report shows that files smaller than the \gls{DoM} threshold generate disproportionately more RPCs per MiB, leading to significantly reduced bandwidth on multi-\gls{OST} Lustre systems \cite{gmitter2018smallfile}.

Even in a namespace-sharded file system like Lustre’s \gls{DNE}, a camera-style “one-file-per-frame” workflow still concentrates its create/unlink traffic in a single hot directory subtree. Production traces from 60 \gls{HPC} systems show that \SI{64}{\percent} of files are smaller than \SI{64}{\kilo\byte}. When a system is flushed with thousands of tiny \gls{HDFfive} or JPEG files, metadata operations increase exponentially. Based on these 60 different \gls{HPC} systems, research shows that metadata operations can account for up to \SI{80}{\percent} of total file system operations \cite{9768784}.

\Gls{HPC} administrators often impose per-user inode quotas because millions of tiny files overload Meta Target Devices \cite{carns2009small}. Therefore, monolithic containers such as \gls{HDFfive} can be preferred on-prem, whereas object stores favor chunk-per-object layouts (e.g., Zarr).

\subsubsection{POSIX-Centric Scientific Formats}
\label{sec:posix-centric-formats}
Most \gls{HPC} codes write \emph{monolithic containers}, a single \gls{POSIX}-seekable file that includes raw arrays and metadata. \gls{HDFfive} popularised this approach, while NeXus adopts the same file structure with beamline-specific naming conventions. The design is perfect for bulk, sequential, local parallel file system scans. However, the need to search through super-blocks and B-trees for every small slice makes it poorly suited to cloud object stores and interactive, many-small-read workflows, motivating the chunk-per-object formats.

\paragraph{Monolithic container philosophy}
The Hierarchical Data Format 5 (\gls{HDFfive}) stores every dataset, chunk, and attribute in a single byte‐addressable file whose internal super-block, B-trees, and heap tables, with the help of \gls{POSIX}, seek for navigation \cite{howison2010tuning}. Nexus, the de facto standard at many photon and neutron sources, layers a domain system on top of the same \gls{HDFfive} container, retaining identical I/O semantics while prescribing beamline-specific group names and units \cite{konnecke2015nexus}. This “all-in-one” layout simplifies file management but couples performance to the underlying file-system block size and to how well metadata caches handle random seeks.

\paragraph{Serial and MPIIO access}
Out-of-the-box \gls{HDFfive} access (via h5py, MATLAB, etc.) issues many small, non-contiguous \gls{POSIX} reads. Each rank that samples a \SIrange{4}{8}{\mega\byte} slice generates dozens of tiny, <\SI{64}{\kilo\byte} reads, leading to many metadata lookups. Small, non-contiguous selections generate many <\SI{64}{\kilo\byte} reads and metadata lookups; collective I/O reduces but does not eliminate this overhead \cite{Breitenfeld2022Parallel,9499420}. Single-file heritage makes many small-read interactive workloads sensitive to metadata hotspots, motivating chunk-per-object designs.

Even when using collective metadata I/O, each \gls{HDFfive} read still must fetch the superblock and descriptive metadata before reading the raw data. In the CCGrid’21 benchmarks on Summit and Cori, metadata I/O alone accounted for as much as  \approx58\% of the total read time \cite{9499420}. \gls{HDFfive}/NeXus excels for large, sequential scans and single-node post-processing, but its single-file, \gls{POSIX}-style heritage makes it vulnerable to metadata hotspots when handling many small reads, motivating chunk-per-object designs such as Zarr and Parquet.

\subsection{Cloud Object Storage Fundamentals}
\label{sec:cloud-object-storage-fundamentals}
Cloud object stores, exemplified by Amazon \gls{SThree}, provide a flat, immutable-object namespace, global durability, and a pay-as-you-go pricing model. They remove local capacity provisioning constraints but introduce \gls{HTTP}S-level latency and per-request charges that do not exist in local \gls{NVMe} or parallel file systems.

\subsubsection{Architectural model}
Amazon Simple Storage Service (\gls{SThree}) organizes data in \emph{buckets} that share a \emph{flat global namespace}, and directory hierarchies are only a key-naming convention. Objects are \emph{immutable}, meaning any modification creates a new version of that object/file. Since December 2020, \gls{SThree} guarantees \emph{strong read-after-write consistency} for all operations, removing the race conditions that earlier eventual-consistency semantics introduced \cite{AWSConsistency2020}.

\subsubsection{Request classes and cost drivers}
Every interaction with \gls{SThree} is an \gls{HTTP}S \gls{API} call in one of four core request classes. Each call is billed in addition to storage (\si{GB}\, month) and data egress charges \cite{AWSS3Pricing2025}.

\subsubsection{Latency characteristics}
Each request traverses a multi-AZ control plane and TLS handshake, giving time-to-first-byte latencies of \SIrange{100}{200}{\milli\second} for small objects \cite{AWSS3Performance2024}. In comparison, on-premises \gls{NVMe} RAID or parallel file systems typically deliver sub-millisecond metadata look-ups, and even \gls{AWS}’s own \gls{EFS} \gls{SSD} class reports $\approx\SI{0.25}{\milli\second}$ latencies \cite{AWSEFSLatency}. This gap explains why unmodified \gls{HPC} workloads often perform poorly on \gls{SThree}. Figure \ref{fig:latency-ladder} visualizes the comparison on a log scale, showing how the jump from \SI{0.1}{\milli\second} \gls{NVMe} reads \cite{haas2023modern} to \SI{0.25}{\milli\second} \gls{EFS} reads \cite{aws_efs_latency} and finally to \SIrange{100}{200}{\milli\second} \gls{SThree} requests \cite{aws_s3_latency} forces any cloud-native workflow to be able to handle round-trip cost through chunking, caching, and request batching.

\subsubsection{Performance-optimisation layers}
\begin{itemize}
  \item \textbf{Multipart uploads}: split objects ($\ge\SI{100}{\mega\byte}$) into \SIrange{5}{5000}{\mega\byte} parts that upload in parallel and resume after failure \cite{AWSS3MultipartDoc}.
  \item \textbf{Range GETs}: request only required byte spans, ideally aligned with the same \SIrange{8}{16}{\mega\byte} boundaries used during uploads \cite{AWSS3RangeGET}.
  \item \textbf{Prefix parallelism}: \gls{SThree} scales to at least \num{5500} GET/HEAD and \num{3500} write requests per \emph{prefix}. Optimally sharding key lifts can aggregate throughput to multi \si{TB/s} \cite{AWSS3Performance2024}.
\end{itemize}

These optimization strategies allow object storage to approach \gls{HPC}-class throughput, but latency for small, random slice reads remains higher than on local or \gls{NVMe}-backed file systems.

\section{Cloud-Native Models and Compression}
\label{sec:cloud-native-models-compression}
Object stores provide scale but add request latency, immutability, and per-request billing \cite{durbin2020cloud}. Cloud-native models partition arrays or tables into independently addressable objects to exploit concurrency while controlling slice-read cost.

\subsection{Cloud-Native Storage Models}
\label{sec:cloud-native-storage-models}
Cloud object stores such as Amazon \gls{SThree}, Azure Blob Storage, and Google Cloud Storage provide effectively unlimited capacity and global accessibility. However, they introduce request latency, immutable object semantics, and per-request billing, which clash with the low-latency, mutable-file assumptions of traditional \gls{HPC} formats \cite{durbin2020cloud}. To exploit cloud elasticity without prohibitive slice-read costs, a new generation of \emph{cloud-native storage models} has emerged, each rethinking how scientific arrays or tables are partitioned, compressed, and addressed in an object store.

This section surveys five representative approaches: \gls{HDFfive} served through the Highly Scalable Data Service (\gls{HSDS}), Zarr's chunk-per-object layout, Apache Parquet's columnar row-group design, TileDB's dense/sparse array storage, and \gls{CERN}'s page-oriented \gls{ROOT}/\gls{RNTuple} format. Each subsection highlights how the format maps its internal data units to cloud objects, which compression and indexing strategies it employs, and the trade-offs in latency and throughput.

    \begin{tabularx}{\linewidth}{@{}l l c c@{}}

      \midrule

\subsubsection{HDF5 + HSDS}
\label{sec:hdf5-hsds}
The \gls{HDFfive} ecosystem represents the most mature and widely adopted solution for storing complex scientific data, spanning disciplines from climate modeling to synchrotron beamline acquisition \cite{10.1145/1966895.1966900}. However, developers designed the format for low-latency, parallel file systems. When migrated naively to cloud object stores, its monolithic layout magnifies request latency and per-operation costs. To preserve \gls{HDFfive}’s rich data model while overcoming these cloud-specific bottlenecks, the Highly Scalable Data Service (\gls{HSDS}) was created as a stateless REST layer that shards chunks and metadata into individually addressable objects \cite{readey2020hsds}.

\paragraph{HDF5 fundamentals}
Hierarchical Data Format 5 (\gls{HDFfive}) is an open-source container, data model, and I/O library designed to store extensive, multidimensional scientific data efficiently \cite{10.1145/1966895.1966900}. An \gls{HDFfive} file consists of \emph{datasets} (n-dimensional arrays) organized in a \gls{POSIX}-style hierarchy of groups. Datasets may be either \emph{contiguously} or as fixed-size \emph{chunks}. Chunking enables transparent filter pipelines (e.g., \texttt{gzip}, \texttt{lz4}, \texttt{zstd}) and independent partial reads/writes. At the same time, the library’s \gls{MPIIO} pathway lets thousands of compute nodes access different chunks concurrently \cite{hdf5_chunking}. These strengths made \gls{HDFfive} the standard library/system used at X-ray, neutron, and electron facilities.

Placing a monolithic \gls{HDFfive} file on Amazon \gls{SThree} causes each \gls{POSIX} \texttt{read()} call to issue a separate \gls{HTTP} Range GET. Therefore, a single \SI{1}{\mega\byte} slice triggers two network round-trips (metadata + data), amplifying latency and incurring request fee costs that traditional \gls{HPC} deployments never experience \cite{hdf5_ros3}. Moreover, the file's internal B-tree indices are optimized for low-latency block storage, not for the \SIrange{100}{200}{\milli\second} object-store round-trip typical of Amazon \gls{SThree}.

The \emph{Highly Scalable Data Service} (\gls{HSDS}) re-implements the \gls{HDFfive} abstraction as a stateless REST \gls{API} \cite{readey2020hsds}. Internally, \gls{HSDS} maps every chunk and metadata item to separate objects (\gls{SThree}, Azure Blob, \gls{MinIO}, or \gls{POSIX}) and maintains small \gls{JSON} documents that map logical dataset coordinates to object keys. This exposes \gls{HDFfive} groups, datasets, and attributes over standard \gls{HTTP} requests.

\paragraph{Operational experience}
Production \gls{HSDS} clusters back multi-hundred-terabyte public archives, e.g., NREL’s 500\, TB Wind Toolkit dataset, enabling subsetting without full downloads \cite{draxl2024wtkled}. \gls{HSDS} retains \gls{HDFfive}’s rich ecosystem yet provides proper cloud-native capabilities.

Most Lustre and \gls{GPFS} installations cap the number of inodes a single user may allocate because millions of tiny files saturate the metadata target (MDT) servers long before disk bandwidth runs out \cite{gmitter2018smallfile}. Therefore, a monolithic \gls{HDFfive} container carries a practical on-prem advantage: \emph{one inode per file} and negligible directory pressure. By contrast, chunk-per-object formats such as Zarr can create $10^{5}$–$10^{7}$ objects for a single 1 TB tomography scan, a scenario many \gls{HPC} administrators actively discourage or block via strict inode quotas. The same characteristic becomes an asset in cloud object stores, where inodes do not exist and latency can be hidden behind massive parallelism for GET/PUT.

\paragraph{Redundant indexing and its performance cost}
\gls{HDFfive}’s internal super-block, heap tables, and fractal B-trees replicate several file-system duties to offer \gls{POSIX}-seekable random access \cite{howison2010tuning}. On low-latency local storage, this overhead is minor; however, when a single 4 MB slice is served from \gls{SThree}, it incurs two round-trips: first to fetch the B-tree node, then the data chunk, doubling both latency and request cost. Chunk-native layouts (Zarr, Parquet, \gls{ROOT}/\gls{RNTuple}) avoid this indirection because each chunk or page is already an independent object.

\subsubsection{Zarr}
\label{sec:zarr}

Zarr is an open-source system for storing chunked, compressed $n$-dimensional arrays as small objects \cite{zarrspecv3}. It partitions each array into regular \emph{chunks} and stores every chunk as an independent object (e.g., a file in a \gls{POSIX} system or a key in Amazon \gls{SThree}). Zarr supports codecs such as \texttt{gzip}, \texttt{lz4}, and \texttt{zstd}, and uses \gls{JSON} metadata files. The format requires no central server, which suits cloud object stores where high-latency, high-throughput parallel access dominates.

\paragraph{Cloud-native performance}
Because each chunk maps to a \gls{SThree} key, multiple parallel GETs can execute simultaneously, achieving high aggregate bandwidth. Time-to-first-byte per chunk on \gls{SThree} is typically \SIrange{100}{200}{\milli\second}; concurrency improves throughput rather than single-request latency. Write throughput scales similarly with thousands of concurrent PUTs (one per chunk), enabling high-rate ingestion at modern beamlines with acceptable overheads.

\paragraph{Growing ecosystem}
Researchers across various fields have adopted Zarr; \gls{GDAL} provides a native driver for geospatial rasters \cite{gdal2024zarr} while the bioimaging community standardized on \gls{OME}-Zarr for petabyte-scale microscopy archives \cite{moore2023ome}. A NumFOCUS-backed governance model and a public Zarr-specs \gls{RFC} process support long-term stability \cite{zarrspecv3}.

Zarr’s chunk-per-object design aligns well with the partial-read workloads studied in this report. However, its performance depends on chunk size, sharding, and metadata unification.

\subsubsection{Apache Parquet}
\label{sec:apache-parquet}
Apache Par, is an open, columnar storage format originally developed at Twitter and Cloudera to bring Dremel-style analytics to the Hadoop ecosystem. It organizes a file into one or more \emph{row groups}, and within each row group ev,ery column is stored contiguously as a \emph{column chunk} and compressed using lightweight compression and dictionary encoding. By reading only the required columns and row groups that satisfy a filter predicate, Parquet reduces I/O volume for wide, sparse tables. Parquet supports several compression codecs, such as Snappy, \texttt{gzip}, deflate, and BZIP2 \cite{vohra2016apache}. Within each row group, Parquet applies column-specific encodings—such as dictionary or run-length encoding—and independent compression, further shrinking the on-disk footprint and amplifying the format’s I/O-reduction advantage.

\paragraph{Cloud-native performance}
On Amazon \gls{SThree}, each row group is laid out as a large (typically \SIrange{64}{256}{\mega\byte}) contiguous byte range, allowing clients such as Apache Arrow’s vectorized reader or \gls{AWS} Athena to fetch gigabyte-scale slices with a single Range GET. The \gls{AWS} Athena pricing page states that converting data to compressed, columnar formats like Parquet “can save up to \SI{90}{\percent} per query and improve performance” compared with raw \gls{CSV} \cite{aws_athena_pricing}.

\paragraph{Ecosystem adoption}
Parquet has become the default on-disk file format throughout today’s analytics stack. Apache Spark uses Parquet as the \emph{default data source}, and Apache Iceberg likewise keeps its immutable data files in Parquet \cite{iceberg_spec}. In the in-memory layer, Pandas and Apache Arrow provide first-class readers/writers for Parquet \cite{pandas_read_parquet}. Primary cloud analytics services natively ingest Parquet, including Google BigQuery \cite{bq_parquet}, \gls{AWS} Glue \cite{aws_glue_parquet}, and Amazon Athena \cite{aws-athena-columnar}.

Parquet’s columnar design is well-suited to the tabular metadata portion of scattering experiments, where scientists frequently select a handful of columns across millions of rows. However, its row-group granularity (tens of MB) and lack of native $n$-D chunking can inflate latency for small pixel tiles.


\subsubsection{TileDB}
\label{sec:tiledb}
TileDB is an open-source array storage engine for both dense and sparse data, organizing writes to immutable, timestamped \emph{fragments}. \cite{Papadopoulos2016TileDB,TileDBDataLayout}. Each fragment contains attribute data serialized into \emph{data tiles}. For object stores, TileDB uses a virtual filesystem with native backends for \gls{SThree}, Azure Blob Storage, and GCS. On \gls{AWS} \gls{SThree}, it writes using multipart uploads to create append-only fragment objects \cite{TileDBBackends,TileDBS3}. The array directory contains the schema, per-fragment data, and fragment metadata \cite{TileDBFragmentMeta}.


\paragraph{Cloud mapping and object count}
Unlike chunk-per-object layouts, a single fragment typically produces a small, fixed set of objects. It generates one attribute file per attribute, one fragment-metadata file, one commit record, and the already-existing schema file. The total object count scales with the number of \emph{fragments} and attributes rather than the number of tiles, which reduces LIST/HEAD amplification on \gls{SThree} for large arrays \cite{TileDBDataLayout,TileDBFragmentMeta}. Excessive fragmentation, however, increases first-open overhead because readers must fetch per-fragment metadata \cite{TileDBConsolidateFragmentMeta}.

\paragraph{Reads and pruning}
Upon opening, TileDB loads fragment metadata and per-tile min-max statistics. The system then queries the pruned fragments and data tiles whose minimum-bounding rectangles (MBRs) do not intersect the requested subarray \cite{TileDBFragmentMeta,TileDBMBR}. Reads support ordered or unordered layouts, multi-range subarrays \cite{TileDBReadLayouts}.

\paragraph{Writes, immutability, and time travel}
All writes create new immutable fragments and commit files, enabling lock-free multiple-reader/multiple-writer behavior and consistent reads at a chosen timestamp range (“time traveling”). Fragment merging helps compact many small fragments into larger ones, allowing reclaimed space \cite{TileDBTimeTravel}.

\paragraph{Compression and filters}
TileDB applies a per-attribute filter pipeline to tiles. Supported compressors include \texttt{gzip}, Zstandard, \texttt{lz4}, RLE, BZIP2, and integer-oriented transforms (bit-shuffle, bit-width reduction, double-delta). Checksums (MD5/SHA-256) are available for integrity \cite{TileDBCompression,TileDBChecksums,TileDBEncryption}.

\subsubsection{ROOT / RNTuple}
\label{sec:root-rntuple}
\gls{ROOT} is an object-oriented C++ framework developed at \gls{CERN} to handle the petabyte-scale data streams of high-energy-physics experiments \cite{blomer2020evolution}. Its core storage abstraction, \gls{TTree}, stores events as rows and detector variables as \emph{branches}. The format splits each branch into contiguous \emph{baskets}, allowing readers to load them independently. This column-friendly layout lets analysis jobs load only the necessary branches, minimizing I/O and deserialization overhead, a property directly relevant to slice-level scattering analysis.

\paragraph{RNTuple redesign}
After two decades of incremental evolution, \emph{\gls{TTree}} showed architectural limits for modern heterogeneous hardware and cloud storage. The \gls{RNTuple} project, therefore, re-implements \gls{ROOT} I/O with a stricter columnar layout, page-based compression, and a self-describing, versioned metadata footer \cite{blomer2020evolution}. Pages (\(\approx\)\,\SIrange{8}{16}{\kilo\byte}) are grouped into clusters so that entirely columnar reads issue a single contiguous request, while sparse event selections fetch only the referenced pages. By decoupling metadata from data pages, \gls{RNTuple} avoids rewriting the entire file when appending events, which is critical for streaming detectors and results in improved partial reads.

\paragraph{Object-store back-end}
Through the generic \gls{ROOT} Page Source interface, pages can reside in \gls{POSIX} files, over \gls{HTTP}(S), or as individual \gls{SThree} objects \cite{rootRNTuple2025}. Scaling studies by Blomer showed near-linear throughput up to \(\mathcal{O}(10^{2})\) concurrent readers on a >100‐core \gls{HPC} cluster served by a \gls{DAOS} object store, achieving an aggregated read rate above \SI{35}{\giga\byte\per\second} before the storage system became the bottleneck \cite{blomer2024root}.

This architecture provides high-throughput, scalable, and selective access to petabyte-scale datasets on \gls{HPC} systems and in the cloud, which is relevant for slice-level scattering analyses.

\subsection{Compression Algorithms Reviewed}
\label{sec:compression-algorithms}
Lossless compression is a first-order lever for improving performance and reducing costs in cloud object–store workflows. Smaller chunks reduce \gls{SThree} egress and request fees, while faster codecs shorten the latency that dominates interactive partial reads in synchrotron experiments.

The focus is on three open-source codecs that form a spectrum of trade-offs: \emph{gzip/DEFLATE} (high ratio, high \gls{CPU}), \emph{\gls{LZfour}} (low ratio, ultra-low latency), and \emph{Zstandard} (\emph{\gls{ZSTD}}, balanced). All four backends under test (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}/\gls{RNTuple}) support \texttt{gzip}, \texttt{lz4}, and Zstandard (built-in or via standard filters/plugins).

\subsubsection{gzip}
\label{sec:compression-gzip}
GNU \texttt{gzip} has been the default lossless compression tool on Unix-like systems since 1992. \gls{RFC} 1952 formalizes \texttt{gzip}’s file format and header/trailer structure, and those specifications have remained patent-free and backward-compatible across three decades of scientific workflows \cite{deutsch1996rfc1952}.

\paragraph{Algorithmic design}
The compressor implements the \emph{DEFLATE} scheme, a cascade of \gls{LZseventyseven} sliding-window substitution, followed by static/dynamic Huffman coding, tunable via nine quality levels that trade compression time for compression ratio. Level 6 is the GNU default, while level 1 sacrifices a \(\approx\) 30\% ratio to gain 3–4\(\times\) speed \cite{deutsch1996rfc1952}.

\paragraph{Performance on scientific data}
Benchmarks on floating-point climate and remote-sensing datasets stored in \gls{netCDF}-4/\gls{HDFfive} show typical space savings of 1.6–2.2\(\times\) at levels 4–6. In these studies, \texttt{gzip} incurred 2–5\(\times\) higher \gls{CPU} costs than \texttt{lz4}, and decompression throughput saturated around \SI{500}{\mega\byte\per\second} per core \cite{delaunay2019evaluation,chen2023fcbench}.

\paragraph{Integration with chunked formats}
Native support for \texttt{gzip} exists in all five tested backends. Because \texttt{gzip} compresses each chunk independently, its compression ratio varies with chunk size and should be taken into account in these experiments. In the experiments, \texttt{gzip} is used as a “high-ratio, high-\gls{CPU}” reference, and its mature ecosystem guarantees consistent behavior across all five storage back ends. Its well-characterized latency overhead provides a baseline against which to measure the partial-read performance of newer codecs like Zstandard and \texttt{lz4}.

\subsubsection{LZ4}
\label{sec:compression-lz4}
Introduced in 2011, \texttt{lz4} emerged as a lightweight derivative of the Lempel–Ziv (\gls{LZseventyseven}) family, designed to maximize streaming throughput while keeping memory overhead to a minimum. Its open-source framing format defines a compact header, provides optional block and content checksums, and employs a skippable frame mechanism, allowing new features to be added without breaking older decoders. These attributes have led to widespread adoption in operating systems, high-performance storage engines, and scientific data formats where sub-millisecond decode latency is critical.

\paragraph{Algorithmic profile}
The codec emphasizes extremely fast byte-wise parsing and a greedy match-finder that limits back-references to \SI{64}{\kilo\byte}. Because of this, the compression runs at $>$\SI{500}{\mega\byte\per\second} per core while decompression routinely exceeds \SIrange{2}{3}{\giga\byte\per\second}, albeit with modest ratios (1.2–1.7\(\times\) on floating-point data) \cite{lz42025,7440278}. A high-compression variant \texttt{lz4hc} improves the ratio by $\sim$15\,\% at 3–5 \(\times\) the \gls{CPU} cost.

\paragraph{Empirical results on scientific workloads}
Almeida \emph{et al.} compared \gls{LZfour} with \gls{ZLIB} on \gls{ROOT} HEP and climate grids, reporting \SIrange{1.0}{1.2}{\giga\byte\per\second} decompression (versus \SI{120}{\mega\byte\per\second} for \gls{ZLIB}) at the expense of only a 5–10\,\% ratio loss \cite{almeida2014two}. The \gls{VLDB}’24 “\gls{FCBench}” study recently measured the \gls{CPU} variant bitshuffle with \gls{LZfour} across 33 floating-point datasets. The study showed that it sustained \SI{0.9}{\giga\byte\per\second} compression and \SI{1.2}{\giga\byte\per\second} decompression on \SI{64}{\kilo\byte} blocks while achieving a median compression ratio of 1.43 \cite{chen2023fcbench}.

\paragraph{Integration in storage formats}
As a codec, \texttt{lz4} filters are first-class options in \gls{HDFfive} (\texttt{H5Z\_LZ4}), Zarr v3, Parquet, and TileDB. Because the \texttt{lz4} \SI{64}{\kilo\byte} match window limits cross-chunk redundancy, chunk sizes above \SIrange{1}{2}{\mega\byte} yield diminishing returns, which for this study aligns well with \gls{SThree} request-cost sweet spots.

In our benchmarks, \texttt{lz4} represents the “low-latency, low-\gls{CPU}” option, serving as the low-latency reference alongside \texttt{gzip} and \texttt{zstd}. The benchmarks examine how far compression ratio can be traded for lower partial-read latency without materially increasing monthly \gls{SThree} storage costs.

\subsubsection{zstd}
\label{sec:compression-zstd}
Zstandard (\texttt{zstd}) was released in 2016 and standardized by the IETF as \gls{RFC} 8878 \cite{collet2021rfc8878}. It combines an \gls{LZseventyseven} dictionary back-reference engine with Finite-State Entropy (\gls{FSE}) coding. It supports window sizes up to 128 MiB and offers 23 quality levels ($-7$ to 22), optional long-range mode, and trained dictionaries (negative values activate ultra-fast modes that trade ratio for speed). Decompression speed is deliberately kept almost constant across levels, whereas compression trades \gls{CPU} for ratio.

\paragraph{Throughput and ratio characteristics}
According to the \texttt{zstd} manual, the fastest compression mode exceeds \SI{200}{\mega\byte\per\second} per core, while the decoder sustains $>$\SI{500}{\mega\byte\per\second} per core on commodity x86 \gls{CPU}s \cite{zstdman2025}.

Promberger \emph{et al.}\ measured \texttt{zstd} level 2 on a 4.9 GB \gls{LHCb} collision dataset and found that its \emph{compression} throughput was roughly 2–3 \(\times\) higher than that of \emph{\gls{ZLIB}} level 2 while achieving an almost identical compression ratio, \cite{promberger2023characterization}.

Delaunay et al. found that “Shuffle + Zstandard-2” compresses \gls{CFOSAT} and \gls{SWOT} remote-sensing files about 1.4 \(\times\) to 7 \(\times\) faster than the mission’s baseline “Shuffle + Deflate-3/4”. It delivers virtually identical space savings, accelerating decompression by up to seven-fold \cite{delaunay2019evaluation}. Across the full 33-dataset \gls{FCBench} suite, the \gls{VLDB}’24 study reports that a \emph{bitshuffle+}\texttt{zstd} pipeline achieves a harmonic-mean compression ratio of 1.47, while sustaining compression and decompression throughputs of $\sim\!\SI{1.4}{\giga\byte\per\second}$ and $\sim\!\SI{1.3}{\giga\byte\per\second}$, respectively  \cite{chen2023fcbench}.

\paragraph{Integration in scientific formats}
As a codec, \texttt{zstd} is a first-class option in Parquet and TileDB, and is available as an extension for \gls{HDFfive} and Zarr v3. With \gls{FSE} contexts resetting per block, 1–4 MiB chunks maximize the ratio without inflating \gls{SThree} request counts. \texttt{zstd} occupies the “balanced ratio/latency” middle ground between \texttt{gzip} (high ratio, high \gls{CPU}) and \texttt{lz4} (low ratio, low \gls{CPU}) in the study.



\section{Summary and Link to Problem Statement}
\label{sec:summary-problem-statement}

The background above shows how accelerating detector output and evolving collaboration models outpace traditional \gls{HPC} storage, while object storage introduces latency–cost trade-offs. The key insights, mapped directly to the thesis problem, are:

\begin{itemize}
  \item \textbf{Data rates:} Multi-\si{\giga\byte\per\second} streams and multi-\si{\tera\byte} experiments are routine.
  \item \textbf{Mismatch:} Parallel file systems deliver bulk throughput but suffer under many small reads; S3 scales throughput via concurrency but has \SIrange{100}{200}{\milli\second} TTFB per request.
  \item \textbf{Rise of cloud-native, chunk- or column-based formats:} Zarr, Parquet, TileDB, and \gls{ROOT}/\gls{RNTuple} reorganize data into independently addressable objects, promising lower slice-read latency and better cost control.
  \item \textbf{Thesis contribution and practical significance:} Prototype ingestion for all five formats, quantitative benchmarking across small-slice and full-scan patterns, and a decision matrix that informs near-real-time experimental feedback, cloud spend, and next-generation scientific data platforms.
\end{itemize}

We benchmark four cloud-native storage formats (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{RNTuple}) and three compression algorithms (\texttt{gzip}, \texttt{lz4}, \texttt{zstd}) under controlled workloads and derive guidelines for optimizing cloud-native workflows for data-intensive synchrotron and neutron-scattering experiments.

Within this \gls{DSR} framing, the primary artifacts are (i) the storage and compression configurations that implement alternative cloud-native layouts and (ii) the decision matrix that encodes their performance and cost trade-offs for beamline scientists and engineers working on \gls{AWS} \gls{SThree}.

On the problem-driven side, the study targets three challenges: the massive data volumes generated by modern synchrotron and neutron facilities, the need for rapid, selective retrieval, and the need for cost-efficient cloud storage. \subsubsection{Step 1: Planning the Experiment}

  \item \textbf{Workload.} Full sequential scans over the $\sim$20 GiB array. Replication and isolation: Appendix \ref{app:a2-run-qc}.
  \item \textbf{Estimands.} GM throughput (GiB/s) with 95\% intervals; 95th percentile scan time. Statistical settings: Appendix \ref{app:a3-stats}.
  \item \textbf{Scope.} Descriptive, session-conditional.
\end{itemize}
\label{sec:methods-rq2}


\subsubsection{RQ3 — Cost posture and mechanisms}
\label{sec:methods-rq3}

\begin{itemize}
  \item \textbf{Service/request metrics.} Per-session S3 GET counts, downloaded bytes, and latency percentiles at 1-minute granularity (Appendix \ref{app:a4-metrics}). Derive GETs per repetition and GETs per GiB (descriptive only).
  \item \textbf{Storage metrics.} Stored bytes on S3 per \{format, codec\}, counting data+metadata objects; compression ratios relative to raw baseline; object counts to characterise layout/objectization.
  \item \textbf{Linkage.} Relate GM latency (RQ1) and GM throughput (RQ2) to GETs/GiB and objectization. CloudWatch latencies are contextual, not causal; no inference can be made from service/request metrics.
\end{itemize}

\section{Metrics, Statistics, and Scoring}
\label{sec:methods-metrics}
This section turns measurements into evidence by defining estimands, quantifying uncertainty, and scoring alternatives so the decision matrix reflects speed, reliability, and efficiency. The estimators and uncertainty procedures here apply unchanged to RQ1–RQ3 as specified in \ref{sec:methods-rq-map}.

\subsection{Performance Metrics and Evaluation Criteria}
We evaluate each format with:

\begin{itemize}
  \item \textbf{Latency (slice and full):} GM time with dependence-robust 95\% \glspl{CI} (log-scale analysis; settings in Appendix \ref{app:a3-stats}). We also report the 95th percentile with 95\% intervals (Appendix \ref{app:a3-stats}).
  \item \textbf{Throughput (full scans):} GM GiB/s derived from bytes/time, analyzed on the log scale with MBB 95\% \glspl{CI}.
  \item \textbf{Request intensity:} GETs per repetition and GETs per GiB from per-session S3 aggregates (Appendix \ref{app:a4-metrics}).
  \item \textbf{Compression:} total stored bytes on \gls{SThree} and compression ratio relative to the raw baseline.
\end{itemize}

Cross-format contrasts are reported as \emph{descriptive} GM time ratios within each codec$\times$pattern family.

\subsection{Decision-matrix scoring (normalization and weights)}
For downstream selection, we compute normalized 0–100 scores per codec\(\times\)pattern using robust min–max scaling within that family (lower bound = 5th percentile, upper bound = 95th percentile, clipped).

\begin{itemize}
    \item \textbf{Slice weights:} GM latency 0.60 (lower better), \(p_{95}\) 0.20 (lower), GETs/GiB 0.10 (lower), stored GiB 0.10 (lower).
    \item \textbf{Full-scan weights:} throughput 0.60 (higher), GETs/GiB 0.15 (lower), stored GiB 0.15 (lower), \(p_{95}\) 0.10 (lower).
\end{itemize}

League tables are ranked by the primary objective (slice: GM latency; full: throughput), with tie-breakers matching the Results section.

\subsection{Statistical methods}
Timings are positive and multiplicative, so we analyze $\ln(\text{time})$ per cell (format$\times$codec$\times$pattern).

Primary estimands are:
\begin{itemize}
  \item \textbf{Geometric-mean (GM) time} with 95\% intervals on the log scale, back-transformed. Bootstrap settings are in Appendix \ref{app:a3-stats}.
  \item \textbf{Tail latency} ($p_{95}$) with 95\% intervals on the original scale; sensitivity procedures are in Appendix \ref{app:a3-stats}.
  \item \textbf{Full-scan throughput} (GiB/s) computed from bytes/time, analyzed on the log scale with the same interval procedure.
\end{itemize}

Within each codec$\times$pattern, cross-format contrasts are reported as GM time \emph{ratios} versus Zarr and are \textbf{descriptive, session-conditional}. Diagnostics include Q–Q plots on $\ln(\text{time})$, lag-1 autocorrelation, and a run-order trend test (Appendix \ref{app:a2-run-qc}).

Per-session \gls{SThree} aggregates are used descriptively only; identifiers and statistics are listed in Appendix \ref{app:a4-metrics}. We do not average percentiles across sessions or attach inferential intervals to service metrics. Warm-up and replication policy are defined in Appendix \ref{app:a2-run-qc}.

\subsection{Uncertainty and confounders in AWS}
\Gls{AWS} introduces time-varying latency and variance that cannot be fully controlled. We mitigated this issue by using a single region with the \gls{SThree} bucket co-located, a Gateway VPC endpoint, and fixed client settings. Operational controls and randomization are documented in Appendix \ref{app:a2-run-qc}. Formats were executed in \emph{separate sessions} with no cross-format overlap. Consequently, cross-format contrasts are \textbf{descriptive, session-conditional}. Inference is limited to within-cell estimands (GM, \gls{Pninetyfive}, throughput) with dependence-robust bootstrap \glspl{CI}. CloudWatch aggregates are per-session and reported descriptively (no inference, no cross-session averaging of percentiles).

\paragraph{Deviation: Parquet pilot-only}
Parquet was piloted but excluded from the timed results due to high metadata open time and rapid object growth observed in the pilot runs. The pilot and rationale are documented in Chapter \ref{ch:whatYouDid}, where Parquet is presented only qualitatively. Timed comparisons cover four formats: \gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{RNTuple}.



\section{Data Collection and Reproducibility}
\label{sec:methods-data-reprod}
This section specifies data sources, sampling, instrumentation, and release artifacts needed to rerun the experiments.

\subsection{Data Collection}
\label{sec:dataCollection}
The data‐collection plan for this thesis centers on a single dataset built from 80 real seed frames and synthetically expanded to \(\sim\)\SI{20}{\gibi\byte} (\(\sim\)1{,}300 frames). These frames statistically replicate the size, structure, and access patterns of real synchrotron and neutron experiments. Generating datasets on demand from a few real frames (rather than distributing the entire raw beamline dataset) avoids licensing constraints and guarantees that every experiment can be reproduced bit-for-bit.


\subsubsection{Data Sources}
Detector stack ($\sim$\SI{20}{\gibi\byte}): $\sim$1{,}300 \gls{CBF} frames at 16-bit depth derived from 80 seed frames from one experiment. A jitter–noise routine perturbs intensity, offset, spatial shifts, and noise to synthesize the remaining frames (Appendix \ref{app:a7-synthesis}).

\subsubsection{Sampling Strategy}
Two patterns were executed on the same dataset. For the slice workload, each run reads one randomly selected frame (\(\sim\)\SI{15.82}{\mebi\byte}) and does not enforce cross-format chunk alignment. For the scanning workload, the entire \SI{20}{\gibi\byte} dataset is read sequentially. Within-session run order was randomized with a fixed seed, and no cross-format concurrency occurred.


\subsubsection{Instrumentation and Metric Logging}
Full-scan time is measured from the first GET dispatch to the last byte received, and slice-read time is per selected frame. Throughput equals bytes divided by time. We therefore collect the following data:

\begin{enumerate}
  \item \textbf{Client} start/stop timestamps and bytes per run.
  \item \textbf{Per-session S3 aggregates:} request counts, bytes, and latency percentiles (identifiers and statistics in Appendix \ref{app:a4-metrics}).
  \item \textbf{\gls{SThree} sizes} per format–codec for compression calculations.
\end{enumerate}


\subsubsection{Validity and Reliability Measures}
No explicit OS cache flushes were performed between runs. Five warm-ups amortize cold-start effects (DNS, TLS, \gls{TCP}, metadata caches). Warm-up and replication policy are specified in Appendix\ref{app:a2-run-qc}.


\subsubsection{Reproducibility and availability}
Random seeds are fixed and logged with per-run timers, and CloudWatch aggregates are saved as \gls{JSON} with run IDs. The code and notebooks are released on GitHub with a small public data subset sufficient to reproduce representative results; artifact versions, object paths, formats, codec settings, and synthesis seeds are documented in Appendices \ref{app:a5-libraries} and \ref{app:a7-synthesis}.

\chapter{What you did}
\label{ch:whatYouDid}
This chapter documents how the artifacts were built and run. It specifies the dataset and augmentation strategy, the \gls{AWS} environment and client software, how each backend (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}, Parquet) was ingested on \gls{SThree}, the monitoring and logging setup, and deviations from the plan, including the pilot-only evaluation of Parquet.


\section{Dataset and preprocessing}
All experiments used a single detector stack derived from 80 real \texttt{CBF} frames and expanded to $\sim$20\, GiB (\,$\sim$1{,}300 frames\,).

\subsection{Raw structure}
Each detector exposure is a dense two-dimensional frame. The specifications below fix the frame geometry, axis conventions, numeric encoding, byte size, and the theoretical versus empirically observed value range used for all subsequent ingestion and synthetic data generation.

\begin{itemize}
  \item Array shape per frame: $(2880, 2880)$.
  \item Axes: slow = rows, fast = columns (units: pixels).
  \item \texttt{dtype}: \texttt{uint16} (bit depth 16).
  \item Endianness: native little-endian.
  \item Per-frame size: \SI{16588800}{\byte} (\SI{15.82}{\mebi\byte}).
  \item Value range (theoretical): $[0, 65535]$.
  \item Value range (observed, raw): $[0, 1199]$.
\end{itemize}


\subsection{Preprocessing and synthetic augmentation}
We started from $80$ raw \texttt{CBF} detector frames. Frames were enumerated in zero-based order, and recorded in a manifest that fixes the frame-index \,$\rightarrow$\, key mapping used later during ingestion. No resampling, normalization, or pixel edits were applied before augmentation.

\subsubsection{Augmentation method}
To scale the corpus for I/O benchmarking while preserving frame geometry and \texttt{uint16} encoding, additional frames were synthesized from the real frames using simple, distribution-preserving perturbations:

\begin{itemize}
  \item Intensity gain: multiply by $g\in[0.85,1.15]$.
  \item Local contrast scale around the frame mean: factor $c\in[0.9,1.1]$.
  \item Spatial jitter: with probability $0.8$, apply integer circular shifts up to $\pm16$\,px on each axis.
  \item Additive noise: with probability $0.9$, add zero-mean Gaussian noise with $\sigma\approx 20$ counts.
  \item Clip to $[0,65535]$ and cast back to \texttt{uint16}.
\end{itemize}

Random choices used fixed Python and NumPy seeds (Appendix \ref{app:a7-synthesis}).

\subsubsection{Size targeting and parallelization}
We targeted a detector stack of $\sim$\SI{20}{\gibi\byte} by estimating average slice size and computing the required frame count. Outputs were written as \gls{CBF} frames and then uploaded to \gls{AWS} \gls{SThree} (implementation details in Appendix \ref{app:a7-synthesis}).

All experiments ran in a single \gls{AWS} region (\texttt{eu-north-1}) on one \gls{ECtwo} node, with all artifacts stored in one \gls{SThree} bucket. \gls{HDFfive} used a local \gls{HSDS} service; Zarr, TileDB, \gls{ROOT}, and the Parquet pilot wrote directly to \gls{SThree} via client libraries. \gls{SThree} bucket analytics and CloudWatch request metrics captured request counts, bytes, and service latencies per session.

\subsection{Region and bucket}
The benchmark used a single \gls{SThree} bucket in \texttt{eu-north-1}, with distinct prefixes for inputs, intermediate artifacts, and final format stores (\gls{HDFfive}/\gls{HSDS}, Zarr, TileDB, \gls{ROOT}, Parquet). The exact bucket name and prefixes are listed in Appendix \ref{app:a1-testbed}.

\section{Storage layouts, codecs, and objectization}
This section summarizes how the array was mapped to \gls{SThree} for each format.

\subsection{Common design and parity}
\begin{itemize}
  \item Logical array for all stores: $(N,2880,2880)$, $N\approx 1300$, \texttt{uint16}.
  \item One frame per chunk/tile: $(1,2880,2880)$ to keep read units comparable.
  \item Codecs targeted: \texttt{gzip}, \texttt{lz4}, \texttt{zstd}. Parquet used only \texttt{gzip} and \texttt{lz4}.
  \item Frame enumeration: zero-based; source files named \texttt{slice\_\{index\}.cbf}.
  \item Concurrency: threaded frame loading; batch writes by contiguous index slices.
\end{itemize}


\subsection{HDF5 via HSDS}
\gls{HSDS} serves \gls{HDFfive} on the \gls{ECtwo} node; we record domain paths, dataset geometry, chunking and codec settings. \gls{HSDS} manages \gls{SThree} keys and metadata; one frame per chunk preserves parity with other stores.

\textbf{Layout:}
\begin{itemize}
  \item Dataset: shape $(N,2880,2880)$, chunks $(1,2880,2880)$, \texttt{uint16}.
  \item Compression: \texttt{gzip}, \texttt{lz4}, or \texttt{zstd} at library default levels.
  \item Objectization: approximately one chunk object per frame plus \gls{HSDS} metadata/index objects.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item Frames were written in batches of $64$ into contiguous slices of the dataset using the \gls{HSDS} client.
  \item Host-level threading parallelized frame decoding and I/O (implementation details in Appendix \ref{app:a6-schemas}).
\end{itemize}

\subsection{Zarr on S3}
Zarr uses one chunk per frame; here we record store paths, array geometry, chunking parity, codecs, and the write procedure.

\textbf{Layout:}
\begin{itemize}
  \item Array: shape $(N,2880,2880)$, chunks $(1,2880,2880)$, \texttt{uint16}.
  \item Compression: \texttt{gzip}, \texttt{zstd}, or \texttt{lz4} with moderate compression level ($\approx 3$).
  \item Metadata: default Zarr metadata files without consolidation.
  \item Objectization: approximately one chunk object per frame plus metadata files.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item Frames were written in batches of $64$ as contiguous slices, with threaded frame loading.
\end{itemize}

\subsection{Apache Parquet on S3}
Frames were tabularized as rows with 2D rows as fixed-size lists. \textit{Note:} Parquet was piloted only and is excluded from timed results due to an operational stop (see section \ref{subsubsec:parquet-pilot-exclusion}).

\textbf{Layout:}
\begin{itemize}
  \item Files: one Parquet file per codec under a dedicated prefix.
  \item Schema: $2880$ columns \texttt{row\_0}\dots\texttt{row\_2879}, each \texttt{list<fixed\_size=2880, uint16>}.
  \item Row groups: one appended row per frame (writer defaults).
  \item Compression: \texttt{gzip} or \texttt{lz4}; dictionaries disabled.
  \item Objectization: single Parquet object per codec.
\end{itemize}

\textbf{Ingestion:}
\begin{itemize}
  \item For each frame, per-row arrays were assembled into a one-row table and appended to the Parquet file (Appendix \ref{app:a6-schemas}).
\end{itemize}


\subsubsection{Parquet pilot and exclusion (deviation)}
\label{subsubsec:parquet-pilot-exclusion}

Parquet was implemented as a single file with $2880$ list-of-$2880$ \texttt{uint16} columns (\texttt{row\_0}\dots\texttt{row\_2879}), one appended row per frame, with \texttt{gzip} and \texttt{lz4} compression; dictionaries disabled.

\textbf{Observed during pilot:}
\begin{itemize}
  \item File size: a single Parquet object of $\sim$\SI{34}{\gibi\byte} for a $\sim$\SI{20}{\gibi\byte} raw stack.
  \item Metadata open: \SIrange{3}{4}{\minute} to load schema, footer, and column indexes on the \gls{ECtwo} test node; repeated attempts to load the \texttt{gzip} file led to instance crashes.
  \item Read smoke test: one frame decoded after metadata load; further timing runs were halted.
\end{itemize}

\textbf{Decision:}
\begin{itemize}
  \item Operational stop after an initial write and smoke read. Rationale: metadata load time and object size would make the full benchmark impractical within the experiment budget.
  \item Consequence: Parquet is omitted from timed latency/throughput results; artifacts are retained for transparency and discussed qualitatively in chapter \ref{ch:discussion}.
\end{itemize}


\subsection{TileDB dense array}
TileDB stores a dense array with frame-sized tiles and immutable fragments; this records the domain, filters, and fragment layout.

\begin{itemize}
  \item URIs: one TileDB array per codec under a dedicated prefix.
  \item Domain dims: \texttt{file: [0,N-1]}, \texttt{y: [0,2879]}, \texttt{x: [0,2879]}.
  \item Tile extents: $(1,2880,2880)$ (full-frame tiles).
\end{itemize}

\textbf{Filters:}
\begin{itemize}
  \item \texttt{gzip} (\texttt{level=3}), \texttt{lz4} (\texttt{level=3}), \texttt{zstd} (\texttt{level=3}) as attribute filter lists.
\end{itemize}

\textbf{Fragments and objectization:}
\begin{itemize}
  \item Writes executed in batches of $64$ frames per task; each task produced a fragment.
  \item Expected fragments: $\lceil N/64\rceil$ (no post-write consolidation or vacuum).
  \item Each fragment contributes internal files (data, metadata, footers) under the array URI.
\end{itemize}

\subsection{ROOT / RNTuple}
\gls{ROOT} encodes all frames into a single file per codec; this notes the tree layout, compression, and access pattern.

\textbf{Tree layout:}
\begin{itemize}
  \item Files: one \gls{ROOT} file per codec under a dedicated prefix.
  \item \texttt{TTree} \texttt{img\_tree} with one branch \texttt{data} of length $2880\times2880$ \texttt{uint16}; one entry per frame.
\end{itemize}

\textbf{Compression:}
\begin{itemize}
  \item \texttt{gzip}: algorithm \texttt{kZLIB}, level $3$; \texttt{lz4}: \texttt{kLZ4} (default level); \texttt{zstd}: \texttt{kZSTD} (default level).
\end{itemize}

\textbf{Objectization:}
\begin{itemize}
  \item Single \gls{ROOT} object per codec. Selective reads use \gls{HTTP}/\gls{SThree} range-GETs into baskets/pages.
\end{itemize}

\subsection{RQ hooks (layouts)}
\begin{itemize}
  \item \textbf{RQ1 (interactive slices):} Frame-aligned chunks/tiles $(1,2880,2880)$ to match the slice unit.
  \item \textbf{RQ2 (full scans):} Fragmenting and page/cluster settings that enable long sequential reads.
  \item \textbf{RQ3 (cost posture):} Object counts per backend, metadata consolidation status (e.g., Zarr consolidated metadata; TileDB fragment consolidation), and stored bytes per codec.
\end{itemize}




\section{Execution, logging, and quality control}
\label{sec:execution-logging-qc}
This section summarizes the run protocol for each \{format$\times$codec$\times$pattern\} cell, along with the associated logging and quality-control checks.

\subsection{Execution protocol}
All reads ran on a single \gls{ECtwo} node in \texttt{eu-north-1}. For each \emph{format} $\times$ \emph{codec} $\times$ \emph{pattern}, we used a fixed warm-up followed by timed runs, with no cross-format concurrency (Appendix \ref{app:a2-run-qc}).

\subsubsection{Sessions and schedule}
Each \emph{session} targeted one cell (format, codec, pattern) and consisted of a small warm-up phase, an idle gap, and a block of timed repetitions; exact counts and timings are detailed in Appendix \ref{app:a2-run-qc}. Between sessions, formats did not overlap. \Gls{HSDS}, Zarr, TileDB, and \gls{ROOT} were run in separate sessions.

\subsubsection{Randomization and seeding}
A fixed seed ensured reproducibility. Slice workloads used precomputed random frame indices; full scans iterated over all frames (sampling details in Appendix \ref{app:a2-run-qc}).

\subsubsection{Timing definition}
Per run, we measured wall-clock time using a high-resolution timer around a single read call. The timer includes network transfer, decompression, and client decode; log serialization is outside the timer.


\subsubsection{CloudWatch capture}
\gls{SThree} bucket request metrics were enabled and queried per session for:
\begin{itemize}
  \item \texttt{GetRequests Sum}, \texttt{BytesDownloaded Sum}
  \item \texttt{FirstByteLatency Average} and \texttt{$p_{95}$}
  \item \texttt{TotalRequestLatency Average} and \texttt{$p_{95}$}
\end{itemize}

Warm-ups precede the timed window by \(\ge\)2\, minutes to keep aggregates attributable to the timed runs.

\subsubsection{Inclusion, failures, and retries}
Warm-ups are excluded by design. A timed run is included if the read returns successfully. If a read raised an exception or timed out, that repetition was re-attempted.

\subsubsection{Caching and connections}
Default client behavior was used. No explicit OS page-cache flushes. \Gls{HTTP} keep-alive and connection pooling are left to \texttt{fsspec/s3fs}, \texttt{boto3}, \texttt{h5pyd}, \texttt{tiledb} VFS, and \texttt{uproot}. No application-level prefetching was enabled in the read loops.

\subsubsection{Run IDs, filenames, and logs}
Each session emitted a monotonic \texttt{run\_id}, and timed samples and CloudWatch aggregates were stored as \gls{JSON} with format/codec/pattern identifiers (log schema in Appendix \ref{app:a4-metrics}).

\subsubsection{RQ hooks (protocol \& logging)}
\begin{itemize}
  \item \textbf{RQ1:} Timer scope per slice; exclude warm-ups; include $50$ timed runs; log per-run times.
  \item \textbf{RQ2:} Timer scope per full scan; compute bytes/time to derive throughput; log per-run times.
  \item \textbf{RQ3:} Per-session CloudWatch exports (\texttt{GetRequestsSum}, \texttt{BytesDownloadedSum}, FirstByte/TotalRequest \{avg,$p_{95}$\}) and S3 inventory for stored bytes and object counts.
\end{itemize}



\subsection{Quality control, exclusions, and deviations}
Runs followed the fixed warm-up and timing protocol; integrity checks verified shapes and dtypes, and only successful timed reads were included.

\textbf{Quality control:}
\begin{itemize}
  \item Inclusion: $5$ warm-ups excluded; $50$ timed repetitions included per cell.
  \item Isolation for \gls{SThree} metrics: warm-ups \(\rightarrow\) idle gap \(\ge\)2\,min \(\rightarrow\) timed runs.
  \item Integrity checks: spot decode of returned arrays; shape \(=(2880,2880)\), dtype \texttt{uint16}.
  \item CloudWatch capture: session-scoped queries saved as \gls{JSON}; notebook timers saved per run.
\end{itemize}

\textbf{Exclusion rules:}
\begin{itemize}
  \item Exclude if: timeout, \gls{HTTP} 5xx, partial read, decode error.
  \item Handling: if an exclusion condition occurred, the affected test was re-run.
\end{itemize}

\textbf{Deviations from plan:}
\begin{itemize}
  \item \textbf{Parquet pilot-only} Writing and a smoke read revealed impractical metadata open times and a single huge object; Parquet was omitted from timed results and kept for qualitative discussion.
\end{itemize}

\chapter{Results and Analysis}
\label{ch:resultsAndAnalysis}
This chapter reports the empirical results of benchmarking four storage backends on Amazon \gls{SThree}, \gls{HDFfive} via \gls{HSDS}, Zarr, TileDB, and \gls{ROOT}/\gls{RNTuple} under two workload patterns on a single $\sim$20 GiB detector stack ($\sim$1{,}300 frames, \texttt{uint16}). Parquet is included as a pilot-only storage engine (no timed results). Each backend is evaluated with three codecs (\texttt{gzip}, \texttt{lz4}, \texttt{zstd}). We present outcomes for (i) partial retrieval of a single frame ($\sim$15.82 MiB), and (ii) full sequential scans of the dataset.

Metrics encompass client-observed timing, service-side behavior, and storage footprint, with timings analyzed on a log scale. For each {format$\times$codec$\times$pattern} cell, we report geometric-mean (GM) time with dependence-robust 95\% \glspl{CI} via a moving-block bootstrap (MBB; settings in Appendix \ref{app:a3-stats}). Tail behavior is summarized by $p_{95}$ with the same procedure. For full scans, we also report throughput (GiB/s) derived from bytes/time. Storage footprint is reported as stored bytes and compression ratio relative to the raw array. Request intensity (GETs/rep, GETs/GiB) is derived from CloudWatch session aggregates.

Cross-format contrasts are \textbf{descriptive, session-conditional} because formats run in separate sessions. Warm-ups are excluded; $n=50$ timed repetitions per cell are analyzed.

This chapter is organised by \emph{RQ1} (interactive slice latency, §\ref{sec:rq1-results}), \emph{RQ2} (full-dataset throughput, §\ref{sec:rq2-results}), and \emph{RQ3} (cost posture and mechanisms, §\ref{sec:rq3-results}).

\subsubsection{S3 object sizes and compression ratios}
\label{subsec:comp_ratio}
This section enumerates the total stored bytes on \gls{SThree} for each {format, codec} and reports compression ratios relative to the uncompressed array baseline. Stored bytes are computed by summing the sizes of all objects under the format–codec prefix (data and metadata files included). The compression baseline is the raw pixel payload of the logical array, not container files. Let $N$ be the number of frames. With frame shape $(2880,2880)$ and 16-bit depth, the baseline size is

\begin{equation}
\label{eq:compression_ratio}
  R_{f,c} \coloneqq \frac{B_{\text{raw}}}{B^{\text{stored}}_{f,c}},\qquad
  B_{\text{raw}} \coloneqq N \times 2880 \times 2880 \times 2 \text{bytes}.
\end{equation}

For $N=1{,}300$, $B_{\text{raw}}=21{,}565{,}440{,}000\ \text{bytes}$ ($\approx 20.08\,\text{GiB}$). Figure \ref{fig:stored_bytes} reports absolute stored size and Figure \ref{fig:compression_rates} shows the corresponding compression ratios.

\subsubsection{GETs per repetition and per GiB}
We summarize request intensity from CloudWatch \emph{session} aggregates. All $n$ timed runs in a cell (format$\times$codec$\times$pattern) contribute to one set of counts. Let $G$ be \texttt{GetRequestsSum} and $B$ be \texttt{BytesDownloadedSum}. Counts include \gls{SThree} \texttt{GET} only; \texttt{HEAD}/\texttt{LIST}/\texttt{PUT} are excluded. Warm-ups are excluded and separated temporally from the timed window.

\textbf{Per-repetition intensity}:
\begin{equation}
  \label{eq:gets_per_rep}
  \widehat{\lambda}_{\mathrm{rep}}=\frac{G}{n}.
\end{equation}

\textbf{Volume-normalized intensity}:
  \begin{equation}
  \label{eq:gets_per_gib}
  \widehat{\lambda}_{\mathrm{GiB}}=\frac{G\,2^{30}}{B}.
\end{equation}

Here $n$ is the number of timed repetitions in the cell; $\widehat{\lambda}_{\mathrm{GiB}}$ is measured in GETs per GiB.

Rates are descriptive and session-conditional. Table \ref{tab:req_intensity} lists $\widehat{\lambda}_{\mathrm{rep}}$ and $\widehat{\lambda}_{\mathrm{GiB}}$ for all cells. \chapter{Discussion}
\label{ch:discussion}
This chapter interprets the results, links them to layout and request behavior, and states the limits; all cross-format contrasts remain descriptive and session-conditional. It then answers \emph{RQ1} (slice latency; Section \ref{sec:rq1-results}), \emph{RQ2} (scan throughput; Section \ref{sec:rq2-results}), and \emph{RQ3} (cost posture; Section \ref{sec:rq3-results}), followed by the decision matrix and threats to validity.

\section{Answers to the research questions}
\label{sec:discussion-bottomline}
This section reports winners by workload and codec, using GM latency (slices) and GM throughput (full scans) with dependence-robust 95\% \glspl{CI} and $p_{95}$ for tail risk. All contrasts are \emph{descriptive} and \emph{session-conditional}.

\subsection{Answer to RQ1 — Interactive slice latency}
\label{sec:ans-rq1}
Single‑frame reads have two stress areas: (i) layout/objectization, which sets how many objects and round–trips each request touches, and (ii) decode cost, which depends on the codec and the library path. We judge the winners by geometric mean (GM) latency with dependence-robust 95\% \glspl{CI} and use $p_{95}$ to flag tail risk. The references below point to the slice tables and figures for each codec.

\textbf{Zarr is the clear winner} for \texttt{zstd} slices. Its GM \gls{CI} lies fully below TileDB’s, which is second, followed by \gls{HDFfive}/\gls{HSDS} and then \gls{ROOT}. The $p_{95}$ ordering mirrors the center, indicating Zarr combines a fast typical latency with controlled tails. Mechanistically, this matches a chunk–per–frame layout that amortizes \gls{SThree} RTT via client concurrency, while \texttt{zstd} keeps the decode cost moderate. See Table \ref{tab:slice_zstd_mbb} and Figs. \ref{fig:slice_zstd_gm_mbb}, \ref{fig:slice_zstd_p95_mbb}, \ref{fig:slice_zstd_ratios_point}. GM deltas show that Zarr is $\approx 12\%$ faster than TileDB (Table \ref{tab:slice_zstd_mbb}).

\textbf{Zarr remains fastest} on GM under \texttt{lz4}. \textbf{TileDB and \gls{HDFfive}/\gls{HSDS} are close} behind it, with overlapping \glspl{CI} between those two, and \gls{ROOT} is slowest. A trade–off appears in the tails: Zarr’s $p_{95}$ is higher and has wider CIs than TileDB and \gls{HDFfive}/\gls{HSDS}, consistent with \texttt{lz4}’s bias toward decode speed over compactness. If an application is strongly tail–sensitive, TileDB’s lower and more stable $p_{95}$ may offset its slightly higher GM. See Table \ref{tab:slice_lz4_mbb} and Figs. \ref{fig:slice_lz4_gm_mbb}, \ref{fig:slice_lz4_p95_mbb}, \ref{fig:slice_lz4_ratios_point}. GM deltas show that Zarr is $\approx 22\%$ faster than TileDB and $\approx 27\%$ faster than \gls{HDFfive} via \gls{HSDS} (Table \ref{tab:slice_lz4_mbb}).

\textbf{TileDB wins} \texttt{gzip} slices with non-overlapping GM \glspl{CI} versus Zarr. Zarr is next and outperforms \gls{HDFfive}/\gls{HSDS}, where \gls{ROOT} again is slowest by a wide margin. This pattern aligns with \texttt{gzip}’s higher \gls{CPU} cost, which leads to TileDB’s fewer, larger fragments reducing request overhead enough to compensate for \texttt{gzip} decode, while Zarr’s per–frame objects incur more round–trips. Ordering is consistent in $p_{95}$ and in the Zarr–referenced ratio view. See Table \ref{tab:slice_gzip_mbb} and Figs. \ref{fig:slice_gzip_gm_mbb}, \ref{fig:slice_gzip_p95_mbb}, \ref{fig:slice_gzip_ratios_point}. GM deltas show that TileDB is $\approx 17\%$ faster than Zarr (Table \ref{tab:slice_gzip_mbb}).

Across codecs in this dataset, the winner patterns align with evidence of request intensity: lower GETs/GiB are associated with lower GM latency for Zarr and TileDB. At the same time, \gls{ROOT}’s single–object layout shows that “few GETs” does not guarantee speed, because paging and decode path overhead dominate. See Fig. \ref{fig:cross_slice_latency_vs_gets} and Table \ref{tab:cross_slice_latency_vs_gets}.

Nonparametric summaries reproduce the same slice rankings by codec, and Harrell–Davis $p_{95}$ with an $\ell$–grid preserves ordering, including the heavier tails for \texttt{lz4}/Zarr. See Fig. \ref{fig:np_slice_ratios_grid}; Tables \ref{tab:np_slice_gzip_median}, \ref{tab:np_slice_lz4_median}, \ref{tab:np_slice_zstd_median}, and the tail–sensitivity artifacts in Fig. \ref{fig:tail-slice-p95-hd-ci-vs-L} and Tables \ref{tab:tail-slice-gzip-p95-selected}–\ref{tab:tail-slice-zstd-p95-selected}.

\subsection{Answer to RQ2 — Full-dataset throughput}
\label{sec:ans-rq2}
Full–dataset reads test sustained sequential delivery and decode under continuous concurrency. We judge winners by geometric-mean (GM) \emph{throughput} (GiB/s) with dependence–robust 95\% \glspl{CI} derived from GM time on the log scale, and use $p_{95}$ times to check stability. All cross–format contrasts are \emph{descriptive} and \emph{session–conditional}. Across \texttt{zstd}, \texttt{lz4}, and \texttt{gzip}, \textbf{TileDB leads by a wide margin}, \textbf{Zarr is consistently second}, and \textbf{\gls{HDFfive}/\gls{HSDS} and \gls{ROOT} come last}.

Effect sizes vs Zarr show that TileDB is $\approx$3.16$\times$ faster under \texttt{gzip} (11{,}254 ms vs 35{,}598 ms), $\approx$2.17$\times$ under \texttt{lz4} (13{,}602 ms vs 29{,}483 ms), and $\approx$2.92$\times$ under \texttt{zstd} (10{,}384 ms vs 30{,}365 ms); Table \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}.

Under \texttt{zstd}, \textbf{TileDB is the clear throughput leader.} Zarr is a distant second, and \gls{HDFfive}/\gls{HSDS} and \gls{ROOT} are far behind. GM time and its \gls{CI} show clean separation, and the ratio view reinforces TileDB’s advantage. $p_{95}$ times follow the same ordering, indicating stable long–scan behavior. See Table \ref{tab:full_zstd_mbb} and Figs. \ref{fig:full_zstd_gm_mbb}, \ref{fig:full_zstd_p95_mbb}, \ref{fig:full_zstd_ratios_point}.

Under \texttt{lz4}, \textbf{TileDB remains first and Zarr second.} Faster decode narrows absolute times but does not change ranks. \Gls{HDFfive}/\gls{HSDS} and \gls{ROOT} stay well behind. $p_{95}$ times are tight for TileDB and Zarr, consistent with sustained data streaming. See Table \ref{tab:full_lz4_mbb} and Figs. \ref{fig:full_lz4_gm_mbb}, \ref{fig:full_lz4_p95_mbb}, \ref{fig:full_lz4_ratios_point}.

Under \texttt{gzip}, \textbf{TileDB still leads and Zarr is second.} \texttt{gzip}’s higher \gls{CPU} cost lifts absolute times for all formats, but ordering is unchanged. \Gls{HDFfive}/\gls{HSDS} and \gls{ROOT} remain the slowest. $p_{95}$ is consistent with the GM picture. See Table \ref{tab:full_gzip_mbb} and Figs. \ref{fig:full_gzip_gm_mbb}, \ref{fig:full_gzip_p95_mbb}, \ref{fig:full_gzip_ratios_point}.

In these experiments, throughput patterns align with request intensity and layout: TileDB attains high throughput with moderate GETs/GiB, thanks to fragment–backed long reads. Zarr has higher GETs/GiB yet parallelizes effectively, whereas \gls{HDFfive} via \gls{HSDS} shows higher GETs/GiB but poorer streaming performance. \Gls{ROOT} has few GETs/GiB but still has low throughput because its single–object layout and paging/decode overhead dominate. See Fig. \ref{fig:cross_full_throughput_vs_gets} and Table \ref{tab:cross_full_throughput_vs_gets}.

CloudWatch FirstByte and TotalRequest latencies are stable within sessions and do not track the large cross–format gaps in client timings; the dominant drivers are layout and decode rather than differences in \gls{SThree} service timing. See Figs. \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}.

Nonparametric centers yield the same ranks across codecs, and the HD $p_{95}$ sensitivity maintains the ordering. See Fig. \ref{fig:np_full_ratios_grid} and Tables \ref{tab:np_full_gzip_median}, \ref{tab:np_full_lz4_median}, \ref{tab:np_full_zstd_median}, see also Fig. \ref{fig:tail-full-p95-hd-ci-vs-L} and Tables \ref{tab:tail-full-gzip-p95-selected}–\ref{tab:tail-full-zstd-p95-selected}.

\subsection{RQ3 — Cost posture and mechanisms (summary)}
\label{sec:ans-rq3}
Chunk/fragment layouts (Zarr, TileDB) produce low–to–moderate GETs/GiB and are associated with lower GM slice latency and higher scan throughput in this dataset. In contrast, \gls{HSDS} yields higher GETs/GiB and \gls{ROOT} is the counterexample: few GETs yet slow due to single-object paging and decode; see §\ref{sec:rq3-results}, Fig. \ref{fig:cross_slice_latency_vs_gets}, and Fig. \ref{fig:cross_full_throughput_vs_gets}. Storage posture is codec-driven overall (zstd $\approx$ gzip $<$ lz4), with a significant inflation for \texttt{lz4}+\gls{HSDS} compared with Zarr/TileDB at the same payload (Table \ref{tab:object_counts}, Fig. \ref{fig:stored_bytes}, Fig. \ref{fig:compression_rates}). S3 FirstByte/TotalRequest latencies are stable across sessions and do not explain cross-format gaps; they serve as context only (Fig. \ref{fig:cw_firstbyte_grid}, Fig. \ref{fig:cw_total_grid}). Mechanistically, objectization determines request patterns, and the codec determines the bytes transferred; together, they explain the client timings observed in \ref{sec:rq1-results}–\ref{sec:rq2-results}.


\section{RQ3 interpretation: mechanisms and cost posture}
\label{sec:discussion-mechanisms-cost}
We explain the observed rankings by linking objectization and GETs per GiB to client timings. CloudWatch service latencies are treated as context, where codec trade-offs and request and storage posture complete the picture.

\subsection{Mechanisms explaining outcomes}
This section explains \emph{why} the observed orderings occur. We link layout-driven objectization and request intensity (GETs/GiB) to client timings, show that \gls{SThree} service latencies are stable and not causal, and summarize codec \gls{CPU}–bytes trade-offs.

\subsubsection{Objectization and layout}
Objectization for each storage backend determines the request pattern. Zarr/\gls{HSDS} materializes roughly one data object per frame (plus metadata), TileDB writes a small number of immutable fragments (each with internal files), and \gls{ROOT}/\gls{RNTuple} stores a single large object. Per–frame layouts expose more opportunities for client concurrency, fragment layouts trade fewer objects for long sequential reads, and single–object layouts minimize GET count but constrain parallelism to range requests within one key. This matches the data in Table \ref{tab:object_counts} and Fig. \ref{fig:object_counts}. In practice, concurrency benefits Zarr and TileDB, while \gls{ROOT} shows few GETs but slow performance because paging and decoding dominate once request latency is amortized.

\subsubsection{Request intensity vs client timing}
In this experiment, lower request intensity is associated with better client outcomes in both chunked and fragmented stores. Fewer GETs/GiB are associated with lower slice GM and higher full-scan throughput for Zarr and TileDB (Fig. \ref{fig:cross_slice_latency_vs_gets}, Fig. \ref{fig:cross_full_throughput_vs_gets}, Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets}). The pattern is not universal: \gls{ROOT} has very low GETs/GiB yet poor latency and throughput because the single-object layout, small pages, and decode costs limit effective parallelism. GETs/GiB explains part of the variance; layout and decode paths account for the rest.

\subsubsection{Service latencies are not the driver}
CloudWatch \emph{FirstByteLatency} and \emph{TotalRequestLatency} are stable within sessions (both averages and $p_{95}$) and do not track the large cross–format gaps in client timings. The dominant factors are request pattern and decode path rather than “faster \gls{SThree}.” These metrics provide context, not causal evidence (Figs. \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\subsubsection{Codec effects}
Codecs trade \gls{CPU} for bytes. \texttt{lz4} minimizes decode time and helps latency where per–chunk \gls{CPU} dominates. \texttt{zstd} strikes a balance between compression and decoding, while \texttt{gzip} yields the smallest stored size but is slower to decode. Stored size is primarily codec–driven (typically \texttt{zstd}\,$\approx$\,\texttt{gzip}\,$<$\,\texttt{lz4}), but format deltas are large under \texttt{lz4}: in our data, \gls{HDFfive} via \gls{HSDS} stored 19.17\,GiB vs Zarr 10.40\,GiB and TileDB 15.56\,GiB (Table \ref{tab:object_counts}, Figs. \ref{fig:stored_bytes}, \ref{fig:compression_rates}). \texttt{lz4}+\gls{HSDS} should therefore be treated as storage-heavy. These trade–offs align with the winners in Section \ref{sec:discussion-bottomline} where Zarr leads \texttt{zstd}/\texttt{lz4} slices while TileDB leads \texttt{gzip} slices (Tables \ref{tab:slice_zstd_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_gzip_mbb}). TileDB dominates full-scan throughput across codecs (Tables \ref{tab:full_zstd_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_gzip_mbb}).


\subsection{Cost and storage posture}
Stored size is mostly codec-driven, but \texttt{lz4} shows substantial format variation (\gls{HSDS} 19.17\,GiB vs Zarr 10.40\,GiB vs TileDB 15.56\,GiB, see Table \ref{tab:object_counts}). For compact storage, prefer \texttt{zstd} or \texttt{gzip} and avoid \texttt{lz4}+\gls{HSDS} unless storage is unconstrained.

\subsubsection{Request cost proxy}
For slice-heavy workloads, watch \emph{GETs/GiB}. In this experiment, \textbf{TileDB} and \textbf{Zarr} deliver lower GETs/GiB at competitive or better latency than \textbf{\gls{HDFfive}/\gls{HSDS}}. This indicates a more favorable request-cost posture at equal performance. See Table \ref{tab:cross_slice_latency_vs_gets} and Fig. \ref{fig:cross_slice_latency_vs_gets}.

\subsubsection{Storage cost proxy}
Stored size is mainly \emph{codec-driven}, where \texttt{zstd} and \texttt{gzip} compress more than \texttt{lz4}. Between-format differences at a fixed codec are small and are consistent with additional layout metadata rather than payload differences. See Figs. \ref{fig:stored_bytes}, \ref{fig:compression_rates}.

\subsubsection{Counterexample}
\textbf{\gls{ROOT}} shows that a few requests do not imply speed or efficiency. It has the lowest \emph{GETs/GiB} yet poor slice latency and scan throughput due to single-object paging and decode overhead. See Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets} and the per-codec MBB results (slices: Tables \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb}; full scans: Tables \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}).


\section{Threats to validity and limits}
\label{sec:threats-validity}
We test whether conclusions hold under alternative centers and dependence. We check shape and serial dependence, confirm medians, and probe tails with the Harrell-Davis estimator.

\subsection{Distribution shape and robustness}
We verify that the modeling choices are appropriate and yield results similar to those of other estimators. We assess shape and serial dependence to justify log–time analysis with the moving–block bootstrap (MBB), then confirm rankings with median centers, and finally test tail stability with Harrell–Davis $p_{95}$.

\subsubsection{Shape and dependence}
Log–time is appropriate, and serial dependence is present. The diagnostics table shows frequent non-normality in the raw time series and improved behavior in $\ln(\text{time})$, while positive lag-1 autocorrelation is observed across all cells. This both motivates analyzing centers on the log scale and using MBB \glspl{CI} that respect dependence (Table \ref{tab:timing_diag_main}). Q–Q grids on $\ln(\text{time})$ support the transformation, and run-order traces show no systematic drift beyond short-range dependence (Appendix Figs. \ref{fig:appendix_qq_grid}, \ref{fig:appendix_drift_grid}). Together, these justify GM on log–time with dependence-robust \glspl{CI}.


\subsubsection{Center robustness}
Median-based rankings match GM across codecs and patterns. Descriptive median ratios reproduce the slice and full-scan orderings, and rank-agreement tables show identical ranks to GM within each codec (Figs. \ref{fig:np_slice_ratios_grid}, \ref{fig:np_full_ratios_grid} and Tables \ref{tab:np_slice_gzip_median}, \ref{tab:np_slice_lz4_median}, \ref{tab:np_slice_zstd_median}, \ref{tab:np_full_gzip_median}, \ref{tab:np_full_lz4_median}, \ref{tab:np_full_zstd_median}, and \ref{tab:np_slice_gzip_rank}, \ref{tab:np_slice_lz4_rank}, \ref{tab:np_slice_zstd_rank}, \ref{tab:np_full_gzip_rank}, \ref{tab:np_full_lz4_rank}, \ref{tab:np_full_zstd_rank}).


\subsubsection{Tail robustness}
Orderings are stable under Harrell–Davis $p_{95}$ with an $\ell\in\{4,6,8,10\}$ block-length grid, where we report the widest dependence-robust \gls{CI} per cell. The notable exception is \texttt{lz4}/Zarr, which shows heavier tails relative to its peers, but this does not overturn the winner hierarchy established by GM and median centers (Figs. \ref{fig:tail-slice-p95-hd-ci-vs-L}, \ref{fig:tail-full-p95-hd-ci-vs-L} and Tables \ref{tab:tail-slice-gzip-p95-selected}, \ref{tab:tail-slice-lz4-p95-selected}, \ref{tab:tail-slice-zstd-p95-selected}, \ref{tab:tail-full-gzip-p95-selected}, \ref{tab:tail-full-lz4-p95-selected}, \ref{tab:tail-full-zstd-p95-selected}).


\subsection{Validity and limits}
We state what the measurements support and where they do not generalize. Internal checks and external scope are made explicit so readers interpret results correctly.

\subsubsection{Internal checks}
All planned runs were completed without failure, and warm-ups were excluded by design. Run order was randomized with a fixed seed. Serial dependence is handled via the moving-block bootstrap, and the log-time choice is supported by shape diagnostics (Section \ref{sec:run-inclusion-and-coverage}, Table \ref{tab:timing_diag_main}).


\subsubsection{External validity}
Findings reflect a single dataset, a single region, and a single client, with two access patterns and three codecs. Cross-format contrasts are \emph{descriptive} and \emph{session-conditional}. CloudWatch service metrics are used solely for descriptive context, not as causal evidence (Figs. \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\section{Deviations and exclusions}
Parquet was piloted only and excluded from timed comparisons. When we scaled to complete ingestion and attempted full-dataset scans, a single large object (\(\sim\)34\, GiB for a \(\sim\)20\, GiB raw stack) incurred 3–4, min metadata open time and intermittent client instability on the \texttt{gzip} file, making it unsuitable for frame-granularity reads and unattractive even for bulk scans in this setup. The root cause is objectization and file semantics: a single-object, columnar Parquet file offers few opportunities for request-level parallelization and concentrates footer/metadata work at open. We therefore retain Parquet as a qualitative caution for $n$-D image stacks on \gls{SThree} single-object layouts and exclude it from quantitative timing (Chapter \ref{ch:resultsAndAnalysis}). A partitioned Parquet dataset with row-grouping aligned to frames might alter objectization, but designing and validating that variant was out of scope.

\chapter{Conclusions and Future Work}
\label{ch:conclusionsAndFutureWork}
Zarr yields the lowest slice latency under \texttt{zstd} and \texttt{lz4}, where TileDB wins slices under \texttt{gzip}. TileDB dominates full‑scan throughput across codecs by 2.2–3.2$\times$ vs Zarr, with stable tails. \Gls{ROOT} remains slow for frame‑random reads despite a few GETs.

Layout and request behavior explain the backend differences. Per-frame objectization (Zarr, \gls{HDFfive} via \gls{HSDS}) and fragment layouts (TileDB) expose client concurrency, whereas a single-object layout (\gls{ROOT}) minimizes GETs but constrains parallelism and incurs paging/decode overhead. Codec choice trades \gls{CPU} for bytes, with \texttt{zstd} and \texttt{gzip} more compact than \texttt{lz4}. In our data \gls{HDFfive} via \gls{HSDS} with \texttt{lz4} stored 19.17\, GiB versus Zarr 10.40\, GiB and TileDB 15.56\, GiB at the same payload size, indicating a storage-heavy configuration.

Winners are judged by geometric-mean (GM) latency for slices and GM throughput for full scans with dependence-robust 95\% \glspl{CI} and Harrell–Davis $p_{95}$ for tails. Findings reflect one $\sim$20\, GiB dataset, one region (eu-north-1), and one client; CloudWatch service latencies are used as context, not as causal drivers.

The remainder of the chapter provides a closing synthesis, decision-oriented recommendations, backend-specific operational implications, and a prioritized agenda for future work. Conclusions map to RQ1–RQ3 and reference Chapter \ref{ch:resultsAndAnalysis} (sections \ref{sec:rq1-results}, \ref{sec:rq2-results}, \ref{sec:rq3-results}).

\section{Closing synthesis}
Across single-frame slices and full scans, the ordering is consistent and session-conditional. For slices, \textbf{Zarr} is fastest under \texttt{zstd} and \texttt{lz4}, while \textbf{TileDB} wins under \texttt{gzip}. \textbf{\gls{HDFfive}/\gls{HSDS}} is slower than Zarr and TileDB but substantially faster than \textbf{\gls{ROOT}}, which is slowest. For full scans, \textbf{TileDB} delivers the highest throughput across all codecs by a wide margin, with \textbf{Zarr} second and \textbf{\gls{HDFfive}/\gls{HSDS}} and \textbf{\gls{ROOT}} far behind. The mechanism is objectization plus request intensity: per-frame objects (Zarr/\gls{HSDS}) and fragments (TileDB) enable client concurrency. In contrast, a single object (\gls{ROOT}) minimizes GETs but limits parallelism and pays paging/decode overhead. In this dataset, \emph{few GETs} therefore does not imply speed; this appears in the cross-metric views (\ref{tab:cross_slice_latency_vs_gets}, \ref{tab:cross_full_throughput_vs_gets}). Cost properties follow: request cost tracks GETs/GiB (important for slice-heavy use), while stored GiB is codec-driven in our measurements (\texttt{zstd}$\approx$\texttt{gzip} $<$ \texttt{lz4}). Therefore, choose \texttt{zstd} or \texttt{gzip} when storage dominates and \texttt{lz4} when \gls{CPU}/latency dominates. If one backend must serve both interactive slices and bulk scans, start with \emph{Zarr+\texttt{zstd}} for UI latency, accepting lower scan throughput. However, if scans dominate, choose \emph{TileDB+\texttt{zstd}} and keep frame‑aligned tiles.




\section{Practitioner choices (decision matrix hook)}
This section turns the empirical rankings into concrete decisions. Choices are related to the primary objective of each workload. All evidence is descriptive and session–conditional, and ties back to the league tables and per–codec slice/full results.



\subsection{RQ1 — Interactive slice latency (latency–first)}
\begin{itemize}
    \item \textbf{Default:} \emph{Zarr + \texttt{zstd}}. It delivers the lowest slice GM with controlled tails across our setting, and scales with client concurrency (Tables \ref{tab:league-slice-zstd}, \ref{tab:slice_zstd_mbb}).
    \item \textbf{If gzip is mandated:} \emph{TileDB + \texttt{gzip}}. TileDB’s fragment layout offsets \texttt{gzip}’s \gls{CPU} cost and wins on GM with non-overlapping \glspl{CI} versus Zarr (Tables \ref{tab:league-slice-gzip}, \ref{tab:slice_gzip_mbb}).
    \item \textbf{Caution:} Avoid \emph{\gls{HSDS}+\texttt{lz4}} if storage cost matters because it stored 19.17\,GiB vs Zarr 10.40\,GiB at the same codec (Table \ref{tab:object_counts}).
    \item \textbf{Avoid for frame-random reads:} \emph{\gls{ROOT}}. Few GETs do not translate to low latency due to paging and decode (Tables \ref{tab:league-slice-gzip}, \ref{tab:league-slice-lz4}, \ref{tab:league-slice-zstd} and Tables \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb}).
\end{itemize}


\subsection{RQ2 — Full-dataset throughput (throughput–first)}
\begin{itemize}
    \item \textbf{Default:} \emph{TileDB + \gls{ZSTD} or \gls{LZfour}}. TileDB dominates full-scan throughput across codecs. Choose \texttt{lz4} if \gls{CPU} is tight, \texttt{zstd} if space matters (Tables \ref{tab:league-full-zstd}, \ref{tab:league-full-lz4} and Tables \ref{tab:full_zstd_mbb}, \ref{tab:full_lz4_mbb}).
    \item \textbf{Second choice when ecosystem fit matters:} \emph{Zarr} (any of \texttt{zstd}/\texttt{lz4}/\texttt{gzip}) trades some throughput for broader tooling while retaining stable streaming of data (Tables \ref{tab:league-full-gzip}, \ref{tab:league-full-lz4}, \ref{tab:league-full-zstd} and Tables \ref{tab:full_gzip_mbb}, \ref{tab:full_lz4_mbb}, \ref{tab:full_zstd_mbb}).  
\end{itemize}


\subsection{Weight sensitivity}
Top selections remain stable under the stated weights, as the selected weights do not alter the winners in our data. Where near-ties appear within a codec×pattern bucket, we call them out in the league tables and recommend using the tie-breakers (slice: $p_{95}\!\rightarrow$ GETs/GiB $\rightarrow$ stored GiB and for full scan GM time $\!\rightarrow$ GETs/GiB $\rightarrow$ stored GiB). \section{Operational implications}
This section converts the Results into backend-specific operational actions. Recommendations cover metadata consolidation, prefix sharding, chunk/tile sizing, fragment consolidation, cache tuning, and read-page batching. Measured object counts justify each item, GETs/GiB, and $p_{95}$ tails.

\subsection{Zarr}
\textbf{Consolidate metadata} to cut LIST/HEAD fan-out and reduce cold-open overhead; unconsolidated layouts inflate object count and amplify per-request latency (Fig. \ref{fig:object_counts}). \textbf{Shard prefixes} (e.g., hash or date shards) to distribute keys across \gls{SThree} partitions and avoid hot prefixes as datasets grow. \textbf{Keep frame–sized chunks} \((1,\cdot,\cdot)\) for frame–granularity reads and adjust only if the access unit changes. \textbf{Monitor tails on \texttt{lz4}}: slice \(p_{95}\) is heavier for Zarr+\texttt{lz4}; prefer \texttt{zstd} for tighter latency envelopes or mitigate with concurrency and consolidated metadata (Fig. \ref{fig:slice_lz4_p95_mbb}, Fig. \ref{fig:object_counts}).


\subsection{TileDB}
\textbf{Manage fragment counts}: each write produces an immutable fragment, where many small fragments raise metadata work. Schedule \textbf{fragment consolidation} when counts grow to keep open/scan overhead low (Table \ref{tab:object_counts}). \textbf{Align tile extents} to the access unit (frame–aligned tiles for these arrays) to preserve long sequential reads. These practices sustain \textbf{scan dominance} observed across codecs (Figs. \ref{fig:full_gzip_gm_mbb}, \ref{fig:full_lz4_gm_mbb}, \ref{fig:full_zstd_gm_mbb}) and the favorable throughput vs GETs/GiB posture (Fig. \ref{fig:cross_full_throughput_vs_gets}).

\subsection{HSDS (HDF5)}
\textbf{Account for REST fan–out} and \textbf{many small objects}: chunk and metadata requests add round–trips (Table \ref{tab:object_counts}). Provision and tune \textbf{server–side caches} (dataset/chunk caches) and concurrency to hide latency, and right-size chunks to reduce request pressure where feasible. CloudWatch service latencies are stable across sessions, so speedups must come from reducing fan–out or improving caching, not from “faster \gls{SThree}” (Figs. \ref{fig:cw_firstbyte_grid}, \ref{fig:cw_total_grid}).

\subsection{ROOT/RNTuple}
\textbf{Batch page reads} and \textbf{avoid per–frame random access}: issue ranged reads and increase read windows so many small pages are fetched together. Prefer workflows that \textbf{scan clusters} over frame–random access for images. Remember that \textbf{few GETs do not imply speed}: single–object layout plus paging/decode keeps latency high despite low GETs/GiB (Tables \ref{tab:cross_slice_latency_vs_gets}, \ref{tab:slice_gzip_mbb}, \ref{tab:slice_lz4_mbb}, \ref{tab:slice_zstd_mbb}).



\section{Future work}
The agenda below targets the highest-leverage uncertainties revealed by the results. Each item is derived from observed mechanisms and aims to either de-risk tail behavior or generalize beyond a single dataset, region, or client.

\begin{itemize}
  \item \textbf{Multi-client scaling and caches.} Test contention and gateway cache effects (\gls{HSDS}/Zarr); report impact on GM and $p_{95}$ under load.
  \item \textbf{Consolidation strategies.} Evaluate Zarr metadata consolidation and TileDB fragment consolidation on GETs/GiB, open time, and tails.
  \item \textbf{Codec/filter and layout sweep.} Include Snappy, bitshuffle{+}\gls{ZSTD} levels, and ZFP, and sweep chunk/tile sizes aligned to target access units.
  \item \textbf{Datasets and patterns.} Extend to sparse or multi-detector stacks; include batched/random windows and mixed read/write.
  \item \textbf{Platforms and cost surfaces.} Compare regions/clouds and on-prem \gls{PFS}; model request+storage+egress cost surfaces for typical workloads.
  \item \textbf{Decision matrix v2.} Add weight-sensitivity visualization, per-site presets, and a one-page selection checklist.
  \item \textbf{Cold‑open and metadata experiments.} Quantify Zarr \texttt{consolidate\_metadata()} vs. unconsolidated stores and TileDB fragment consolidation on cold‑open time, GETs/GiB, and $p_{95}$ tails.
\end{itemize}

\label{app:a3-stats}

\begin{itemize}

  \item \textbf{BytesDownloadedSum}: \texttt{BytesDownloaded}, statistic \texttt{Sum} (Bytes).

\[
\text{GETs/run}=\frac{\text{GetRequestsSum}}{n_{\text{runs}}},\quad
\text{GETs/GiB}=\frac{\text{GetRequestsSum}}{\text{BytesDownloadedSum}/2^{30}},\quad
\text{Throughput (GiB/s)}=\frac{\text{BytesDownloadedSum}/2^{30}}{\text{total scan time (s)}}

Frames were written in batches of 64 into contiguous slices of the dataset using the \gls{HSDS} client with host-level threading for frame decode and I/O.\\
\textbf{Zarr.} Store \texttt{s3://\dots/zarr/\{gzip|lz4|zstd\}.zarr}; array \texttt{/data}; codecs as above; unconsolidated metadata. Frames were written in batches of 64 contiguous slices, with threaded frame loading and a single chunk per frame.\\
\textbf{TileDB.} URI \texttt{s3://\dots/tiledb/\{gzip|lz4|zstd\}.tdb}; domain dims \texttt{file:[0,N-1]}, \texttt{y:[0,2879]}, \texttt{x:[0,2879]}; tile extents $(1,2880,2880)$. Writes were grouped into fragments of 64 frames each (no post-write consolidation), so the expected fragment count is $\lceil N/64\rceil$.\\
\textbf{\gls{ROOT}/\gls{RNTuple}.} File \texttt{s3://\dots/root/\{gzip|lz4|zstd\}.root}; \texttt{TTree img\_tree} with branch \texttt{data} ($2880\times2880$ \texttt{uint16}); one entry per frame. Entries were appended sequentially, one frame per event, with \texttt{gzip}, \texttt{lz4}, or \texttt{zstd} compression.\\
\textbf{Parquet (pilot only).} Single file; 2880 list-of-2880 \texttt{uint16} columns; one row per frame; dictionaries disabled; rows appended sequentially with \texttt{gzip} or \texttt{lz4} compression only.

\subsection{Data synthesis parameters}
\label{app:a7-synthesis}
\textbf{Seeds/RNG.} Global seed \texttt{979969114}. Python \texttt{random} and NumPy \texttt{Generator} (PCG64) seeded deterministically; per-frame seeds derived from global seed and frame index.\\
\textbf{Augmentation.} From 80 real \texttt{CBF} frames: intensity gain $g\in[0.85,1.15]$; local contrast $c\in[0.9,1.1]$; spatial jitter with prob 0.8 (integer circular shifts up to $\pm16$\,px); additive Gaussian noise with prob 0.9 ($\sigma\approx20$ counts); clip to $[0,65535]$; cast to \texttt{uint16}.\\
\textbf{Targeting.} Compute frames to reach $\sim$20\,GiB; write \texttt{slice\_\{index\}.cbf}; ingest to stores.

\subsection{Parquet pilot notes}
\label{app:a8-parquet}
Single-object Parquet with \texttt{gzip}/\texttt{lz4}; $\sim$34\,GiB object for a $\sim$20\,GiB raw stack; metadata open \SIrange{3}{4}{\minute}; intermittent client instability on \texttt{gzip}. Pilot halted; Parquet excluded from timed results; retained for qualitative discussion.
